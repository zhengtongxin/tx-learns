Webhooks and sub-workflowsWebhook 与子工作流

Make workflows reusable, resilient and safe to call from other apps · ~13 min · hands-on让工作流可复用、能扛故障，并且能被其他应用安全调用 · 约 13 分钟 · 动手做

Step 1 · Split big flows into parts第 1 步 · 把大流程拆成部分

Learn先学

A workflow that does everything is hard to read and hard to fix. Move a repeated job, like "look up a customer", into its own workflow that starts with an Execute Workflow Trigger. Call it from others with an Execute Workflow node.

什么都做的工作流既难读又难修。把重复出现的活，比如“查客户”，放进自己的工作流，用 Execute Workflow Trigger 开头。其他工作流用 Execute Workflow 节点来调用它。

Fix a sub-workflow once and every caller gets the fix. Give it clear inputs and one clear output.

子工作流修一次，所有调用方都跟着好。给它明确的输入和一个明确的输出。

Step 2 · Plan for things to fail第 2 步 · 预先想到会出错

Learn先学

• Retry On Fail on any node that calls the outside world, with a short wait.
• Error workflow: a separate workflow that starts with an Error Trigger and messages you which workflow failed and where.
• Batches and waits: a Loop Over Items node with a Wait keeps you under an API's rate limit.

• 凡是要访问外部的节点，都开 Retry On Fail，中间隔一小会儿。
• 错误工作流：单独一个以 Error Trigger 开头的工作流，告诉你哪个工作流在哪里失败了。
• 分批与等待：用 Loop Over Items 加 Wait，就不会超过接口的限速。

Set the error workflow in each workflow's settings. Otherwise failures happen silently.

在每个工作流的设置里指定错误工作流，否则失败会悄无声息。

Workflow "{{ $json.workflow.name }}" failed at node "{{ $json.execution.lastNodeExecuted }}": {{ $json.execution.error.message }}

Sort each one.

给每一项分类。

Step 3 · Let other apps call you第 3 步 · 让其他应用调用你

Learn先学

Apps such as forms, payment tools and ElevenLabs can call your webhook. Treat the webhook like a public front door.

表单、支付工具和 ElevenLabs 这类应用都可以调用你的 webhook。要把 webhook 当成对外的大门。

• Authenticate: require a secret in a header and check it first.
• Validate: reject a request that lacks the fields you expect.
• Respond fast: answer quickly, and do slow work after.

• 认证：要求请求头带密钥，并最先校验。
• 校验：缺少你要的字段，就拒绝。
• 快速回应：先快速回答，慢的活放后面。

Step 4 · Build a protected webhook第 4 步 · 搭一个受保护的 webhook

Do it动手

Add a Webhook node, set Method to POST and Path to lead. Under Authentication choose Header Auth and create a credential: name X-Api-Key, value a long random string. n8n now rejects any call without that header before your workflow runs. Add a Respond to Webhook node at the end, or set Respond to “Immediately” if the slow work can happen afterwards.

添加一个 Webhook 节点，Method 选 POST，Path 填 lead。Authentication 选 Header Auth，新建凭证：名称 X-Api-Key，值填一长串随机字符。这样没带这个请求头的调用，在进入你的工作流之前就会被 n8n 拒绝。最后加一个 Respond to Webhook 节点；如果慢的工作可以放到后面做，就把 Respond 设为 “Immediately”。

While you build, click “Listen for test event” and call the Test URL. It only works while n8n is listening. After you activate the workflow, use the Production URL instead (/webhook/lead rather than /webhook-test/lead).

搭建时点 “Listen for test event”，再调用测试地址（Test URL），它只在 n8n 正在监听时有效。激活工作流之后，改用正式地址（Production URL），即 /webhook/lead，不是 /webhook-test/lead。

curl -X POST "https://YOUR-N8N/webhook-test/lead" \ -H "X-Api-Key: YOUR-SECRET" \ -H "Content-Type: application/json" \ -d '{"name":"Mei","email":"mei@example.com"}' # without the -H "X-Api-Key" line, n8n refuses the call

Then check three things: the right key works, a missing or wrong key is refused, and a body without email is rejected by an IF node that checks it before anything else runs.

然后检查三件事：正确的密钥能通过；缺少或错误的密钥被拒绝；缺少 email 的请求体会被最前面的 IF 节点拦下，不再往下执行。

Now make it yours现在把它变成你的

Takeaways要点回顾

• Reusable jobs become sub-workflows.
• Retry temporary faults; fix permanent ones.
• Batch and wait to respect rate limits.
• An error workflow is how failures reach you.
• A webhook is a front door: authenticate, validate, answer fast.

• 可复用的活做成子工作流。
• 临时故障重试，永久故障修正。
• 分批并等待，遵守限速。
• 错误工作流是让故障通知到你的办法。
• Webhook 是大门：认证、校验、快速回答。
