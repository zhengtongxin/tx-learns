Team workflows and debugging团队流程与调试

Use agents inside a team workflow, and give them what they need to debug · ~14 min · concepts把智能体放进团队流程，并给它调试所需要的东西 · 约 14 分钟 · 讲概念

Step 1 · One loop for the team第 1 步 · 团队共用一个循环

Learn先学

A steady loop works for people and agents alike: explore the code, plan, build in small steps, test, commit, open a pull request (PR: a proposed change that others review before it joins the main code). Ask for the plan before the code.

有一个稳定的循环，人和智能体都适用：探索代码、计划、分小步构建、测试、提交、发起拉取请求（PR：一份先让别人审阅、再并入主代码的改动提议）。先要计划，再要代码。

For a team, share what the agent reads: commit AGENTS.md (a notes file the agent reads at the start of a session), custom commands and skills (see the lesson on MCP, skills and plugins). Everyone gets the same test command, the same rules, the same checks in continuous integration (CI), which runs the tests automatically on every change.

对团队来说，要共享智能体读的东西：提交 AGENTS.md（智能体每次开始工作时读的笔记文件）、自定义命令和技能（见“MCP、技能与插件”那一课）。每个人都有同一条测试命令、同一套规矩、持续集成（CI，每次改动都会自动跑测试）里同样的检查。

Step 2 · You still own the review第 2 步 · 审阅仍归你

Learn先学

Agent-written code is code you are responsible for. Read the diff (the lines the change adds and removes) like a colleague's: does it match the plan, are there tests, any new dependency (a library the code now needs), any secret (a key or password that must never be committed), any change you did not ask for?

智能体写的代码，你要负责。像读同事的代码那样读它的改动（改动新增和删除的那些行）：和计划一致吗？有测试吗？有没有新依赖（代码现在需要的某个库）、有没有密钥（绝不能提交的钥匙或密码）、有没有你没要求的改动？

Keep pull requests small and single-purpose. A 2,000-line agent diff is a review nobody can do, and the checks are only as good as the review behind them.

拉取请求要小而专一。2,000 行的智能体改动没人审得了，而检查的可靠程度，取决于背后那次审阅。

Step 3 · Debugging with an agent第 3 步 · 和智能体一起调试

Learn先学

Give it the evidence: the exact error, how to reproduce it, what you expected. Ask for causes first, then a fix. Best of all, ask it to write a failing test that captures the bug, then make it pass.

把证据给它：准确的报错、复现的办法、你期望的结果。先让它找原因，再给修复。最好的做法是让它先写一个能复现这个 bug 的失败测试，再让测试通过。

Change one thing at a time. If it loops on the same wrong idea after two tries, stop, start a fresh session and give it what you learned.

一次只改一件事。如果它在同一个错误想法上试了两次还在打转，就停下来，开一个新会话，把你学到的告诉它。

Bug: the shares add up to 2 cents too much when 3 people split a 50.35 bill. Reproduce: node split.js (node runs a JavaScript file) (prints 5037, expected 5035) Do not change code yet. First list three likely causes, with the file for each. Then write a failing test that shows the bug. Only then fix it.

Sort each request to an agent as good or weak.

把给智能体的每条请求分成“好”或“弱”。

Step 4 · The bug, the test, the fix第 4 步 · bug、测试、修复

Learn先学

Here is what the debug prompt above produces. The bill is 5035 cents shared by 3 people. The code rounds every share up, so the shares add up to 5037. After listing the causes, the agent's next move is a test that fails for the right reason (a test is a small check that fails while the bug is there, so writing it first proves it catches the bug). The code boxes here are JavaScript, a language you do not need to know: read the comments. The test checks one rule: the shares must add up to the bill.

上面那份调试提示会得到这样的结果。账单是 5035 分，3 个人分摊。代码把每份都向上取整，所以几份加起来是 5037。列出原因之后，智能体的下一步是写一个因为正确原因而失败的测试（测试就是一个小检查：bug 还在时它会失败，所以先写它，就证明它真能抓住这个 bug）。这里的代码是 JavaScript，你不需要会它，看注释就行。这个测试只检查一条规则：几份加起来必须等于账单。

function split(cents, people) { // Array(3).fill(x) makes a list of three x; Math.ceil rounds up return Array(people).fill(Math.ceil(cents / people)); } const assert = require('node:assert'); // assert stops with an error when a check is false const parts = split(5035, 3); // reduce adds the list up; strictEqual stops with an error if the two values differ assert.strictEqual(parts.reduce((a, b) => a + b, 0), 5035, 'shares must add up to the bill'); // AssertionError: shares must add up to the bill (5037 !== 5035)
Learn先学

Only now the fix: give everyone the rounded-down share, then hand the leftover cents to the first few people. The same test now passes, and you only have to review a four-line change.

到这时才修：每人先拿向下取整的份额，剩下的几分钱分给前几个人。同一个测试现在通过，而你只需审阅四行改动。

function split(cents, people) { const base = Math.floor(cents / people), extra = cents % people; // % is the remainder: 5035 % 3 is 1 // Array.from builds a list; (_, i) => ... is a small function, _ is an unused value and i the position; // `i < extra ? 1 : 0` means 1 if i is below extra, otherwise 0: the first few people get one more cent return Array.from({ length: people }, (_, i) => base + (i < extra ? 1 : 0)); } // split(5035, 3) gives [1679, 1678, 1678], which adds up to 5035

Now make it yours现在把它变成你的

Takeaways要点回顾

• Explore, plan, build small, test, commit, pull request.
• Share AGENTS.md, commands and skills so the team agrees.
• You own the review; keep diffs small.
• Debug with evidence: error, steps, expectation. Causes first, then a failing test.

• 探索、计划、小步构建、测试、提交、拉取请求。
• 共享 AGENTS.md、命令和技能，让团队保持一致。
• 审阅归你；改动要小。
• 用证据调试：报错、步骤、期望。先找原因，再写失败测试。
