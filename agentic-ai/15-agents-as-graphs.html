Side case支线案例

You are helping Auntie Lan, who runs the counter at a busy kopitiam in Ipoh. Orders come in all morning. Every order goes on one order pad that everybody can read. Food goes to the kitchen stall, drinks go to the drinks station, and the slip always comes back to the counter to check nothing is missing. This kitchen is a graph. In this lesson you rebuild it in code with LangGraph: plain functions that read and write a shared pad, joined by arrows. This is Auntie Lan's counter in Ipoh: the same pattern as Kopi Corner's order pad.

你在帮 兰姨，她在怡保一家热闹的咖啡店管柜台。整个早上订单不断。每张订单都记在一块大家都看得到的订单板上：吃的送去厨房档口，喝的送去饮料站，单子做完一定会回到柜台，检查有没有漏。这间厨房就是一张图。这节课你用 LangGraph 把它写成代码：一堆读写同一块板子的普通函数，用箭头连起来。这是怡保兰姨的柜台：和 Kopi Corner 的订单板是同一个套路。

Step 0 · The layer under the graph第 0 步 · 图底下的那一层

Learn先学

Before arrows, you need the parts they connect. LangChain's lowest layer is a thin wrapper around a model provider: one chat-model object, messages, tools and structured output. Think of it as the stoves and pans. You can cook with them, but you light each fire yourself. With a tool, the model only asks for it. At this layer you write the loop that runs the tool and calls the model again. Graphs remove exactly that boilerplate.

画箭头之前，先认识箭头要连起来的零件。LangChain 最底层只是对模型服务商的一层薄封装：一个聊天模型对象、消息、工具和结构化输出。可以把它想成炉灶和锅：能煮，但每把火都得自己点。用工具时，模型只是提出请求；在这一层，运行工具再重新调用模型的循环要你自己写。图要去掉的正是这些重复代码。

# pip install langchain langchain-openai langgraph langgraph-checkpoint-sqlite python-dotenv from langchain_openai import ChatOpenAI from langchain_core.tools import tool from pydantic import BaseModel, Field llm = ChatOpenAI(model="gpt-5.4-mini") # reads OPENAI_API_KEY print(llm.invoke("One sentence: what is a kopitiam?").content) @tool def menu_price(item: str) -> float: """Price in RM of a drink or dish on today's menu.""" return {"kopi o": 1.6, "roti canai": 1.5, "nasi lemak": 4.0}.get(item.lower(), 0.0) class Order(BaseModel): item: str = Field(description="What the customer wants") qty: int = Field(description="How many") parser = llm.with_structured_output(Order) print(parser.invoke("Boss, bagi tiga roti canai")) # Order(item='roti canai', qty=3)

Step 1 · State and reducers: the order pad第 1 步 · 状态与 reducer：订单板

Learn先学

A graph starts with one question: what does everybody get to read? That is the state, the order pad. Auntie Lan never wipes it. New lines are added under the old ones, and the rule for how old and new combine is called a reducer. A field with the add_messages reducer is appended to. A plain field with no reducer is simply replaced by the latest write.

图的第一个问题是：大家都能读到什么？这就是状态（state），也就是订单板。兰姨从不擦掉它，新的内容是加在旧内容下面的，而“旧的和新的怎么合并”的规则叫 reducer。带 add_messages 的字段会追加；没有 reducer 的普通字段，则直接被最新一次写入覆盖。

from typing import Annotated from typing_extensions import TypedDict from langgraph.graph.message import add_messages class Pad(TypedDict): messages: Annotated[list, add_messages] # reducer: append, never overwrite malay: str # no reducer: last write wins

Step 2 · Nodes and edges: the smallest graph第 2 步 · 节点与边：最小的图

Learn先学

The recipe never changes: define the state, make a builder, add nodes, add edges, compile. A node is a plain function. It reads the pad and returns only the keys it changes. An edge is an arrow saying who goes next. START and END are the door in and the door out. This first graph has no model at all, which is the point: a graph is just functions.

做法永远是这五步：定义状态、创建构建器、加节点、加边、编译。节点是一个普通函数，读订单板，并且只返回它改动的键。边是说下一个轮到谁的箭头。START 和 END 是进门和出门。这第一张图里完全没有模型，这正是重点：图只是一堆函数。

import random from langgraph.graph import StateGraph, START, END def auntie(state: Pad) -> dict: shout = random.choice(["Kopi siap!", "Roti dah habis!", "Tunggu sekejap!"]) return {"messages": [{"role": "assistant", "content": shout}]} g = StateGraph(Pad) # builder g.add_node("auntie", auntie) # node g.add_edge(START, "auntie") # edges g.add_edge("auntie", END) app = g.compile() # compile out = app.invoke({"messages": [{"role": "user", "content": "order"}]}) print(out["messages"][-1].content)

Step 3 · A fork and a loop: conditional edges第 3 步 · 分叉与回环：条件边

Learn先学

Real kitchens choose. If the model asked for a tool, the slip goes to the tools station. If not, it moves on. That choice is a conditional edge. Two ready-made pieces do the work: ToolNode runs whatever tools the model asked for, and tools_condition answers "tools" or END. The edge from tools back to the counter is the loop. Here we also add a translate node that fills malay.

真正的厨房要做选择。如果模型请求了工具，单子就送去工具档口；没有的话就往下走。这个选择就是条件边。两个现成的零件负责干活：ToolNode 运行模型请求的所有工具，tools_condition 回答 "tools" 或 END。从工具档口回到柜台的那条边就是回环。这里还加了一个 translate 节点，用来填 malay。

from langgraph.prebuilt import ToolNode, tools_condition tools = [menu_price] llm_t = llm.bind_tools(tools) def counter(state: Pad) -> dict: return {"messages": [llm_t.invoke(state["messages"])]} def translate(state: Pad) -> dict: text = state["messages"][-1].content prompt = f"Translate to Bahasa Melayu, reply with only the translation:\n{text}" return {"malay": llm.invoke(prompt).content} g = StateGraph(Pad) g.add_node("counter", counter) g.add_node("tools", ToolNode(tools)) g.add_node("translate", translate) g.add_edge(START, "counter") g.add_conditional_edges("counter", tools_condition, {"tools": "tools", END: "translate"}) g.add_edge("tools", "counter") # the loop: back to the counter g.add_edge("translate", END) app = g.compile() # app.get_graph().draw_mermaid_png() draws it, to check the arrows

Step 4 · Memory across runs: checkpoints第 4 步 · 跨次运行的记忆：检查点

Learn先学

The reducer only works inside one run. Call invoke twice and the second call starts with a blank pad. To remember between calls, compile with a checkpointer and pass a thread_id. It is like giving every table its own order pad. A checkpoint is saved at every step, so you can even look back and resume from an earlier moment.

reducer 只在一次运行内部起作用。调用两次 invoke，第二次又从一块空白的板子开始。想在多次调用之间记住东西，就要在编译时加上检查点（checkpointer），并传入 thread_id。就像给每张桌子一块自己的订单板。每一步都会存一个检查点，所以你还能回头看，甚至从更早的时刻重新开始。

from langgraph.checkpoint.memory import MemorySaver from langgraph.checkpoint.sqlite import SqliteSaver app = g.compile(checkpointer=MemorySaver()) table5 = {"configurable": {"thread_id": "table-5"}} app.invoke({"messages": [{"role": "user", "content": "I am Mei Ling, I always take kopi kosong"}]}, table5) print(app.invoke({"messages": [{"role": "user", "content": "My usual, please?"}]}, table5)["messages"][-1].content) # survives restarts: a file instead of memory, used inside its with-block with SqliteSaver.from_conn_string("pads.db") as saver: durable = g.compile(checkpointer=saver) # time travel: every step was saved history = list(app.get_state_history(table5)) # newest first old = history[len(history) // 2] cfg = {"configurable": {"thread_id": "table-5", "checkpoint_id": old.config["configurable"]["checkpoint_id"]}} app.invoke(None, cfg) # resume from that earlier moment
What I got wrong我搞错的地方I thought: “the state has messages, so why does it forget?” The reducer only combines updates inside one run. Remembering across runs is the checkpointer's job, keyed by thread_id. Another time malay was never set: I had forgotten the mapping on the conditional edge, so “no tools” went straight to END.我当时的想法是：“状态里明明有 messages，为什么还会忘？”其实 reducer 只在一次运行内部合并更新，跨次运行的记忆是检查点的工作，靠 thread_id 区分。还有一次 malay 一直没被设置：我忘了给条件边写映射，“不用工具”直接去了 END。

Takeaways要点回顾

• A graph is just functions on a shared pad, joined by arrows.
• State is the pad. A reducer decides how old and new combine: add_messages appends, a plain field is replaced.
• A node returns only the keys it changes. An edge says who goes next.
• A conditional edge chooses the next node. An edge back to an earlier node makes a loop.
• tools_condition answers "tools" or END. Pass a mapping to send “no tools” elsewhere.
• The reducer works inside one run. A checkpointer plus thread_id remembers across runs.
• MemorySaver vanishes on restart. SqliteSaver keeps a file.

• 图只是读写同一块板子的函数，用箭头连起来。
• 状态就是订单板。reducer 决定新旧内容怎么合并：add_messages 追加，普通字段被覆盖。
• 节点只返回它改动的键。边说明下一个轮到谁。
• 条件边选择下一个节点。指回前面节点的边就形成回环。
• tools_condition 回答 "tools" 或 END。想把“不用工具”送去别处，就要传映射。
• reducer 只在一次运行内部有效。检查点加 thread_id 才能跨次记住。
• MemorySaver 重启就没了，SqliteSaver 会存成文件。
