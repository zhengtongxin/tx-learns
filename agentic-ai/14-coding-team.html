Multi-agent teams · Project多智能体团队 · 项目

Coding team编程团队

Four agents design, build, put a screen on and test a small app, running their own code inside a safe box · ~35 min · hands-on四个智能体设计、编写、加上界面并测试一个小应用，还在安全的盒子里运行自己写的代码 · 约 35 分钟 · 动手实践

Key point要点

A coding team splits one job into roles (lead, backend, frontend, tester) and lets each agent run its code in a throwaway Docker box, so it reads real results instead of guessing. Our example: a tab system for a mamak stall.

编程团队把一个任务拆成角色（负责人、后端、前端、测试员），并让每个智能体在用完即弃的 Docker 盒子里运行自己的代码，读真实结果而不是靠猜。示例：mamak 档口的赊账系统。

Step 1 · A safe box where code can run第 1 步 · 一个能安全运行代码的盒子

Learn先学
  • Model-written code should not run loose on your laptop. Run it in Docker, a throwaway container that sees only one sandbox folder.
  • Two tools are enough: save_file writes a file, run_python runs it and returns what it printed.
  • Return the error output too, or a crash looks like silence. Docker Desktop must be running.
  • 模型写的代码不该在你的电脑上随便跑。放进 Docker 里运行：一个用完即弃的容器，只能看到一个 sandbox 文件夹。
  • 两个工具就够了：save_file 写文件，run_python 运行并返回打印的内容。
  • 错误输出也要返回，否则崩溃就像一片寂静。Docker Desktop 必须在运行。
import subprocess from pathlib import Path from crewai.tools import tool BOX = Path(__file__).resolve().parents[1] / "sandbox" BOX.mkdir(exist_ok=True) @tool("Save File") def save_file(filename: str, content: str) -> str: """Write a text file into the sandbox folder, replacing it if it exists.""" (BOX / filename).write_text(content) return f"saved {filename}" @tool("Run Python") def run_python(filename: str) -> str: """Run a .py file from the sandbox in a fresh container and return what it printed.""" out = subprocess.run( ["docker", "run", "--rm", "-v", f"{BOX}:/work", "-w", "/work", "python:3.12-slim", "python", filename], capture_output=True, text=True, timeout=60, ) return out.stdout + out.stderr # errors too, so a crash is visible box_tools = [save_file, run_python]
Try one coder first先试一个程序员

Give a single coder agent box_tools and ask: “How many 20-cent coins pay for 1,000 cups of kopi at S$1.80?” It writes a script, runs it and reports the printed number (9,000), not a guess.

给单个 coder 智能体 box_tools，问：“付 1,000 杯 kopi（每杯 S$1.80）需要多少个 20 分硬币？”它会写脚本、运行，并报告打印出的数字（9,000），而不是猜。

from tools.box import box_tools # a one-off agent just for this test: give it a "coder" entry in agents.yaml (role, goal, backstory). # Step 2 replaces it with the four real roles. It is a method of your crew class. @agent def coder(self) -> Agent: return Agent(config=self.agents_config["coder"], tools=box_tools, verbose=True)

Step 2 · Split the work into four roles第 2 步 · 把工作分给四个角色

Learn先学
  • agents.yaml has four entries. Only the lead gets the stronger model (llm:), because a good design pays off down the chain.
  • tasks.yaml chains roles with context: design feeds code, code feeds both the screen (Gradio, a Python library for simple web pages) and the tests.
  • agents.yaml 有四项。只有负责人用更强的模型（llm:），因为好的设计会在整条链上带来回报。
  • tasks.yaml 用 context 串起角色：设计供代码使用，代码同时供界面（Gradio，做简单网页的 Python 库）和测试使用。
# config/agents.yaml lead: role: Engineering lead for a {module_name} module goal: > Turn these requirements into a detailed design for one Python module with one main class: {requirements} backstory: You write clear designs that a junior dev can follow. llm: openai/gpt-4o backend_dev: role: Python developer goal: Implement the design exactly, as {module_name}.py, and save it to the sandbox. backstory: Careful, writes clean self-contained code. llm: openai/gpt-4o-mini # frontend_dev and tester look similar (both gpt-4o-mini)
# config/tasks.yaml design_task: description: Write the design for {module_name}. Markdown only, no code. expected_output: A design with class name, methods and signatures. agent: lead code_task: description: Implement the design and save it as {module_name}.py. expected_output: Confirmation the file was saved and runs. agent: backend_dev context: [design_task] ui_task: description: Build app.py, a minimal Gradio screen that imports {module_name}. expected_output: app.py saved in the sandbox. agent: frontend_dev context: [code_task] test_task: description: Write a test file for {module_name}, run it and summarise pass or fail. expected_output: A short test report. agent: tester context: [code_task]
@CrewBase class TabTeam: agents_config = "config/agents.yaml" tasks_config = "config/tasks.yaml" # one @agent method per role, one @task method per task. # backend_dev, frontend_dev and tester get tools=box_tools; the lead only writes the design @crew def crew(self) -> Crew: return Crew(agents=self.agents, tasks=self.tasks, process=Process.sequential)

Which role does each job? Sort them.

每项工作该由哪个角色来做？请分类。

Step 3 · One kickoff, live docs, a working app第 3 步 · 一次启动、实时文档、一个能用的应用

Learn先学
  • Pass the requirements as plain text plus a module name. Fixed test prices give the tester something to check.
  • Afterwards the sandbox holds the design, module, screen, tests and a report. Run pip install gradio and python app.py in that sandbox folder on your own laptop (not in Docker), so the screen opens in your browser.
  • A model may know an old version of a library. MCP plugs in outside tools; mcps= gives only the frontend dev a live-docs server.
  • 需求以普通文字加模块名传入。固定的测试价格让测试员有依据可查。
  • 运行后沙盒里有设计、模块、界面、测试和报告。在你自己电脑上的这个 sandbox 文件夹里（不是在 Docker 里）运行 pip install gradio 和 python app.py，界面就会在浏览器里打开。
  • 模型可能只认识库的旧版本。MCP 用来接入外部工具；mcps= 只给前端开发一个实时文档服务。
REQS = """ A tab system for regular customers at a drinks stall. Open a tab, top up cash, record orders (item, qty) using get_price(item), with fixed test prices: teh_tarik 2.00, kopi_o 1.60, roti_canai 1.50 (S$). Block orders that would make the balance negative. Report balance, items ordered, and a full history. """ def run(): TabTeam().crew().kickoff(inputs={"requirements": REQS, "module_name": "tabs"}) # in crew.py, only the frontend dev gets live library docs @agent def frontend_dev(self) -> Agent: return Agent(config=self.agents_config["frontend_dev"], tools=box_tools, mcps=["https://mcp.context7.com/mcp"])
What I got wrong我犯过的错I did not clear the sandbox, so the tester tested yesterday's file. And with Docker stopped, the agent happily said “the code ran fine”.我没有清空沙盒，测试员测的是昨天的文件。Docker 没启动时，智能体还高兴地说“代码运行正常”。

Takeaways要点回顾

• A coding agent should run its code and read the result, not guess.
• Run model-written code in a throwaway Docker container that sees one folder.
• Return error output too, so crashes are visible.
• Split roles; give the stronger model to the design role.
• mcps= plugs live docs into only the roles that need them.

• 写代码的智能体应该运行代码并读结果，而不是靠猜。
• 模型写的代码放在只能看到一个文件夹的用完即弃 Docker 容器里运行。
• 也要返回错误输出，崩溃才看得见。
• 拆分角色；更强的模型给设计角色。
• mcps= 只给需要的角色接入实时文档。
