Project: a team that writes code项目：会写代码的团队

Four agents design, build, put a screen on and test a small app, running their own code inside a safe box · ~35 min · hands-on四个智能体设计、编写、加上界面并测试一个小应用，还在安全的盒子里运行自己写的代码 · 约 35 分钟 · 动手实践

The story故事

A small mamak (a 24-hour curry and tea stall) wants a simple tab system. Uncle Raju drinks teh tarik every morning and settles up on Friday. The owner needs to open a tab, add a cash top-up, record each order against the menu price, refuse an order that would push the balance below zero, and show what is owed and a history of every entry. Rather than write it alone, the owner builds a crew the way a small dev shop would split the work: a lead designs, a backend dev writes the module, a frontend dev builds the screen and a tester checks it.

一家小 mamak（24 小时营业的咖喱和茶档）想要一个简单的赊账本系统。Raju 大叔每天早上喝拉茶，星期五结账。老板需要：开一个账户、加现金充值、按菜单价格记录每份订单、拒绝会让余额变成负数的订单，并显示欠款和每一笔记录。老板没有自己动手，而是像一家小型开发公司那样分工，搭了一个团队：负责人做设计，后端开发写模块，前端开发做界面，测试员来检查。

Step 1 · A safe box where code can run第 1 步 · 一个能安全运行代码的盒子

Learn先学

A coding agent should not only write code. It should run it and read what happens, the way you do. But code written by a model should not run loose on your laptop. So the tools run it inside Docker, a program that starts a throwaway container, like a fresh empty room that is thrown away afterwards. The container only sees one sandbox folder.

Two tools are enough: save_file writes a file into the sandbox, and run_python runs it in a new container and returns what it printed. Return the error output too, not only the normal output, or a crash looks like silence. You need Docker Desktop installed and running.

写代码的智能体不该只是写代码，还应该像你一样运行它，并读结果。但模型写的代码不该在你的电脑上随便跑。所以工具把代码放进 Docker 里运行。Docker 会启动一个用完即弃的容器，像一间全新的空房间，用完就扔。容器只能看到一个 sandbox（沙盒）文件夹。

两个工具就够了：save_file 把文件写进沙盒，run_python 在新容器里运行它并返回打印的内容。除了正常输出，也要把错误输出一起返回，否则程序崩溃在智能体看来就像一片寂静。你需要安装并启动 Docker Desktop。

# tools/box.py import subprocess from pathlib import Path from crewai.tools import tool BOX = Path(__file__).resolve().parents[3] / "sandbox" BOX.mkdir(exist_ok=True) @tool("Save File") def save_file(filename: str, content: str) -> str: """Write a text file into the sandbox folder, replacing it if it exists.""" (BOX / filename).write_text(content) return f"saved {filename}" @tool("Run Python") def run_python(filename: str) -> str: """Run a .py file from the sandbox in a fresh container and return what it printed.""" out = subprocess.run( ["docker", "run", "--rm", "-v", f"{BOX}:/work", "-w", "/work", "python:3.12-slim", "python", filename], capture_output=True, text=True, timeout=60, ) return out.stdout + out.stderr # errors too, so a crash is visible box_tools = [save_file, run_python]

Step 2 · Warm up with one coder第 2 步 · 先用一个程序员热身

Learn先学

Before four roles, try one. A single coder agent gets the two box tools. The warm-up job: “Print how many 30-sen coins you need to pay for 1,000 cups of kopi at RM1.80 each, and run it.”

The point is not the sum. It is that the agent writes the script, runs it, reads the printed number and puts that in its answer, instead of guessing. (The right answer is 6,000 coins.)

四个角色之前，先试一个。单个 coder 智能体拿到这两个盒子工具。热身任务：“打印付 1,000 杯 kopi（每杯 RM1.80）需要多少个 30 sen 的硬币，并运行它。”

重点不在这道算术，而在于智能体会写脚本、运行、读到打印出的数字，并把那个数字放进答案，而不是靠猜。（正确答案是 6,000 个硬币。）

from tools.box import box_tools @agent def coder(self) -> Agent: return Agent(config=self.agents_config["coder"], tools=box_tools, verbose=True)

Step 3 · Split the work into four roles第 3 步 · 把工作分给四个角色

Learn先学

agents.yaml now has four entries. Only the lead gets the stronger, pricier model, because a good design pays off all the way down the chain. The others use the cheaper one.

tasks.yaml chains the roles with context from the last lesson, so each role sees only the earlier work it needs. The design feeds the code. The code feeds both the screen and the tests. (Gradio, in the screen task, is a Python library that turns a few lines into a simple web page.)

agents.yaml 现在有四项。只有负责人用更强也更贵的模型，因为好的设计会在整条链上带来回报，其余角色用便宜的模型。

tasks.yaml 用上一课的 context 把角色串起来，每个角色只看到它需要的前面成果。设计供代码使用，代码同时供界面和测试使用。（界面任务里的 Gradio 是一个 Python 库，几行代码就能做出简单的网页。）

# config/agents.yaml lead: role: Engineering lead for a {module_name} module goal: > Turn these requirements into a detailed design for one Python module with one main class: {requirements} backstory: You write clear designs that a junior dev can follow. llm: openai/gpt-4o backend_dev: role: Python developer goal: Implement the design exactly, as {module_name}.py, and save it to the sandbox. backstory: Careful, writes clean self-contained code. llm: openai/gpt-4o-mini # frontend_dev and tester look similar # config/tasks.yaml design_task: description: Write the design for {module_name}. Markdown only, no code. expected_output: A design with class name, methods and signatures. agent: lead output_file: sandbox/design.md code_task: description: Implement the design and save it as {module_name}.py. expected_output: Confirmation the file was saved and runs. agent: backend_dev context: [design_task] ui_task: description: Build app.py, a minimal Gradio screen that imports {module_name}. expected_output: app.py saved in the sandbox. agent: frontend_dev context: [code_task] test_task: description: Write a test file for {module_name}, run it and summarise pass or fail. expected_output: A short test report. agent: tester context: [code_task] output_file: sandbox/test_report.md

Which role does each job? Sort them.

每项工作该由哪个角色来做？请分类。

Step 4 · One kickoff, a working app第 4 步 · 一次启动，得到一个能用的应用

Learn先学

The requirements go in as one block of plain text, with the module name next to it. The test prices are fixed (teh_tarik, kopi_o, roti_canai) so the tester has something to check against. get_price(item) is just a small price lookup that the backend dev is asked to write into the module.

After a run the sandbox holds the design, the module, the screen, the tests and the test report. Run uv run app.py inside the sandbox for a working little screen. That is the payoff: four roles, one kickoff.

需求作为一整段普通文字传入，旁边再放模块名。测试价格是固定的（teh_tarik、kopi_o、roti_canai），这样测试员才有依据去检查。get_price(item) 只是一个简单的查价函数，需求要求后端开发把它写进模块里。

运行结束后，沙盒里有设计、模块、界面、测试和测试报告。在沙盒里运行 uv run app.py，就能得到一个能用的小界面。这就是回报：四个角色，一次启动。

# main.py REQS = """ A tab system for regular customers at a drinks stall. Open a tab, top up cash, record orders (item, qty) using get_price(item), with fixed test prices: teh_tarik 2.00, kopi_o 1.60, roti_canai 1.50 (RM). Block orders that would make the balance negative. Report balance, items ordered, and a full history. """ def run(): TabTeam().crew().kickoff(inputs={ "requirements": REQS, "module_name": "tabs", })

Step 5 · Give two roles live docs through MCP第 5 步 · 通过 MCP 给两个角色实时文档

Learn先学

A model learnt a library at some point in the past, so the frontend dev may write screen code for an old version of Gradio. MCP is a standard plug for outside tools (it gets its own topic later). In recent CrewAI versions, you hand an agent a list of MCP server addresses with mcps=. This one serves up-to-date library docs.

Give it only to the roles that need it, such as the frontend dev below (the lead can get it the same way). The backend dev writes plain Python and does not.

模型是在过去某个时间学到一个库的，所以前端开发可能会按旧版 Gradio 写界面代码。MCP 是连接外部工具的标准插头（后面有专门的主题）。在较新的 CrewAI 版本里，你用 mcps= 给智能体一份 MCP 服务地址列表。这个服务提供最新的库文档。

只给需要的角色，比如下面的前端开发（负责人也可以用同样的方式拿到）。后端开发写的是普通 Python，不需要。

@agent def frontend_dev(self) -> Agent: return Agent( config=self.agents_config["frontend_dev"], tools=box_tools, mcps=["https://mcp.context7.com/mcp"], # up-to-date library docs )
What I got wrong我犯过的错Docker was not running. The run tool came back empty and the agent happily said “the code ran fine”. The first run also has to download the image, so it is slow once. I returned only normal output. A crash then looked like silence, so I added the error output and the agent could finally read its own tracebacks and fix them. An MCP bug. In the pinned version, tools from an HTTPS MCP server whose names contain a hyphen could not be called, because the cleaned-up name was sent back to the server. A small patch fixed it, and I must check it again after any upgrade. Lesson: when a tool “exists” but always fails, look at the exact name being sent. I did not clear the sandbox. The tester tested yesterday's file.Docker 没有启动。运行工具返回了空内容，智能体还高兴地说“代码运行正常”。第一次运行还要下载镜像，所以只有第一次很慢。我只返回了正常输出。程序崩溃就像一片寂静，加上错误输出以后，智能体终于能读到自己的报错并修好它。一个 MCP 的 bug。在锁定的版本里，名字带连字符的 HTTPS MCP 工具没法调用，因为清理过的名字被送回了服务器。一个小补丁解决了问题，每次升级后都要再检查一遍。教训：工具“存在”却总是失败时，去看实际发送出去的名字。我没有清空沙盒。测试员测的是昨天的文件。
Check before you trust it相信之前先核对Passing tests only means the code matches what the tester thought to check. Before the mamak uses it with real money, the owner tries a few tabs by hand.测试通过只说明代码符合测试员想到要检查的内容。在 mamak 用它处理真钱之前，老板要亲手试几个账户。

Now make it yours现在把它变成你的

Back at the kopitiam回到 kopitiamUncle Raju's Friday tab at the mamak is a tiny program: open a tab, add an order, settle up. A coding team of agents writes it the way Kopi Corner would: one writes, one tests, and one reads the result before it goes live.Raju 叔叔在 mamak 档的周五结账，其实就是一个小程序：开单、加单、结账。一组编程智能体写它的方式，就像 Kopi Corner 做事：一个写，一个测，一个在上线前读一遍结果。

Takeaways要点回顾

• A coding agent should run its code and read the result, not guess.
• Run model-written code in a throwaway Docker container that sees one folder.
• Return the error output as well as the normal output, so crashes are visible.
• Split the job into roles: design, backend, frontend, tests. Give the stronger model to the design role.
• context lets each role see only the earlier work it needs.
• mcps= plugs live library docs into only the roles that need them.
• Clear the sandbox between runs, and when a tool always fails, check the exact name it is called by.

• 写代码的智能体应该运行自己的代码并读结果，而不是靠猜。
• 模型写的代码要放在只能看到一个文件夹的用完即弃 Docker 容器里运行。
• 除了正常输出，也要返回错误输出，崩溃才看得见。
• 把工作分成角色：设计、后端、前端、测试。更强的模型给设计角色。
• context 让每个角色只看到它需要的前面成果。
• mcps= 只给需要的角色接入实时库文档。
• 每次运行之间清空沙盒；工具总是失败时，检查它被调用时的确切名字。
