Where we left off上回讲到

Last time the Kopi Corner assistant could be rebuilt in several frameworks and compared. Today it fails when Aina needs to see exactly why it did something, because a framework hides the loop. We fix it by writing the loop ourselves: one coordinator agent that starts workers, watches a board and finishes on its own.

上回 Kopi Corner 助手已经能用好几种框架重建并比较。今天的问题是：Aina 想看清它为什么这样做，框架却把循环藏了起来。我们自己写这个循环：一个总协调智能体，负责启动工人、盯着任务板，并自己收工。

Side case支线案例

Your school is holding a fair, and Lina wants a small website: one page for each of five booths (pancakes, a ring toss, face painting, a book swap, a plant sale), each with a tiny interactive widget. Five pages, five builders working at once, plus one coordinator. Think of the person running the fair on the day: sets the look first (same colours, same fonts), gives each booth one job, watches the sign-up board while everyone works, checks each booth before opening, sends back anything wrong (once only) and writes the programme at the end. The five builders are the single-framework workers from the last lesson. The coordinator is itself an agent, not a Python for loop. Aina's counter works the same way: Auntie Suria is the coordinator, and Ah Seng and Kak Ros are two builders working from one board.

学校要办义卖会，Lina 想做一个小网站：五个摊位（煎饼、套圈、脸部彩绘、换书、卖植物）各一页，每页一个小小的互动组件。五个页面、五个同时开工的建造者，再加一个总协调。想想当天负责义卖会的人：先定好外观（同样的颜色和字体），给每个摊位派一份活，大家干活时盯着报名板，开门前逐个检查摊位，有问题就退回去（只退一次），最后写节目单。五个建造者就是上一课里各框架的工人，总协调本身是一个智能体，不是 Python 的 for 循环。Aina 的柜台也是这样：Suria 阿姨是总协调，Ah Seng 和 Kak Ros 是两位按同一块板干活的建造者。

Step 1 · The agent decides, the tools do the mechanics第 1 步 · 智能体做决定，工具做机械活

Learn先学

Each worker already has its own inner loop (read the board, plan, do, tick off). Your new code is the outer loop: an agent with a handful of tools. The rule that makes it work: anything brittle and exact (starting processes, timeouts, checking files) goes into a tool. Anything that is a choice (what each builder makes, whether a page is good enough, who to send back) is left to the model.

每个工人已经有自己的内层循环（读任务板、规划、执行、打勾）。你要写的新代码是外层循环：一个带几个工具的智能体。让它跑得通的规则是：脆弱又精确的事（启动进程、超时、检查文件）放进工具；属于判断的事（每个建造者做什么、页面够不够好、退回谁）留给模型。

Step 2 · Four tools and one coordinator第 2 步 · 四个工具，一个总协调

Learn先学

Build the tools first, then the agent that uses them. The code below is a sketch, so do not run it yet: team (starts and watches the builders), board (the shared task board) and judge (the page inspector from step 4) are helpers you set up first; the code starts with tiny stand-ins so you can read it on its own. Starting a builder returns at once, so all five run in parallel. Waiting is a separate tool, so the coordinator decides when to wait. Cap the whole loop with max_llm_calls so it cannot run forever.

先做工具，再做用它们的智能体。下面的代码只是草图，先别运行：team（启动并监看建造者）、board（共享任务板）和 judge（第 4 步的页面检查员）都是要先搭好的帮手；代码开头放了几个小小的替身，方便单独阅读。启动建造者会立刻返回，所以五个可以并行。等待是单独的工具，由总协调决定什么时候等。用 max_llm_calls 给整个循环设上限，它就不会无限运行。

from google.adk.agents import LlmAgent from google.adk.agents.run_config import RunConfig from google.adk.runners import InMemoryRunner # stand-ins, so the sketch reads on its own (the real ones do the work): class Board: def add_goal(self, text): ... # writes one goal row, returns its id class Team: pending = [] # worker processes still running def slug(self, framework): ... # folder name for a framework def start(self, framework, goal): ... # subprocess.Popen, output to DEVNULL async def wait_all(self, timeout): ... # until all exit, or the timeout def status(self): ... # who finished, who did not def fix_once(self, framework, problem): ... board, team = Board(), Team() def make_tools(team): def start_builder(framework: str, booth: str) -> str: """Start one framework's worker on one booth page. Returns immediately.""" goal = board.add_goal(f"Build the {booth} page in site/{team.slug(framework)}/") team.start(framework, goal) # subprocess.Popen, output sent to DEVNULL return f"{framework} is building {booth}" async def wait_for_builders() -> str: """Block until every started worker exits or times out. Returns the status.""" await team.wait_all(timeout=300) return team.status() async def inspect_page(slug: str) -> str: """Open one finished page in a real browser and report whether it works.""" return str(await judge(slug)) # judge() is built in Step 4 def send_back(framework: str, problem: str) -> str: """Give one worker a single fix task that describes the problem.""" return team.fix_once(framework, problem) return [start_builder, wait_for_builders, inspect_page, send_back] coordinator = LlmAgent(name="fair_coordinator", model="gemini-2.5-flash", instruction="Build the fair site with your team: start every builder, wait, inspect each page, " "send back at most one fix per page, then finish.", tools=make_tools(team)) # run_async(..., run_config=RunConfig(max_llm_calls=80)) caps the outer loop

Step 3 · The board is the only channel第 3 步 · 任务板是唯一的通道

Learn先学

The coordinator never talks to a builder directly. It starts them and the shared board does the rest: each builder claims its goal, writes its own steps under it and ticks them off. That also gives you a live view. The same worker file runs in two modes, chosen by two lines at the top. The loop at the bottom is the coordinator's side and is only the display: it redraws the live view until every builder has exited.

总协调从不直接和建造者说话。它负责启动，其余交给共享任务板：每个建造者领自己的目标，在下面写自己的步骤并打勾。这也让你有了实时视图。同一个工人文件有两种运行方式，由顶部两行决定。底部的循环是总协调那一侧，只负责显示：它不停刷新实时视图，直到所有建造者都退出。

import sys TASK_ID = int(sys.argv[1]) if len(sys.argv) > 2 else None BOARD = sys.argv[2] if len(sys.argv) > 2 else "board.db" # no args -> seed my own demo goal and run alone # with args -> claim TASK_ID on the shared board, build that page, exit import asyncio from rich.live import Live # render_board() draws the board as a table; team.pending is the list of running workers (stand-ins from Step 2) with Live(render_board(), refresh_per_second=4) as live: while any(p.poll() is None for p in team.pending): live.update(render_board()) # five coloured goals filling in together await asyncio.sleep(0.25)

Step 4 · A fresh inspector for every page第 4 步 · 每个页面一个全新的检查员

Learn先学

To check a page, start a new, short-lived agent with a real browser (the Playwright MCP server) and one report tool that records the verdict. A fresh agent per page keeps each browser session small, so one confusing page cannot eat the whole budget. If nobody reports, the answer is “no verdict”, which counts as failing.

检查页面时，启动一个全新、短命的智能体，给它真正的浏览器（Playwright MCP 服务）和一个记录结论的 report 工具。每个页面用一个新智能体，浏览器会话就小，一个让人困惑的页面也吃不掉整个预算。如果没人汇报，结果就是“没有结论”，算作不通过。

from google.adk.tools.mcp_tool import McpToolset, StdioConnectionParams from mcp import StdioServerParameters from google.genai import types async def run_once(agent, max_llm_calls): """Run one agent to the end, with a cap on model calls.""" runner = InMemoryRunner(agent=agent, app_name="inspect") session = await runner.session_service.create_session(app_name="inspect", user_id="coord") msg = types.Content(role="user", parts=[types.Part(text="Begin.")]) async for _ in runner.run_async(user_id="coord", session_id=session.id, new_message=msg, run_config=RunConfig(max_llm_calls=max_llm_calls)): pass async def judge(uri: str) -> dict: verdict = {} def report(works: bool, note: str) -> dict: """Record whether the page loads and the widget works, with one short note.""" verdict.update(works=works, note=note) return {"ok": True} browser = McpToolset(connection_params=StdioConnectionParams( server_params=StdioServerParameters(command="npx", args=["-y", "@playwright/mcp@latest", "--browser", "chrome", "--isolated"]), timeout=30.0)) # the first browser call starts slowly inspector = LlmAgent(name="inspector", model="gemini-2.5-flash", instruction=f"Open {uri}, try the widget, check the console, then call report.", tools=[browser, report]) try: await run_once(inspector, max_llm_calls=25) finally: await browser.close() return verdict or {"works": False, "note": "no verdict"}

Step 5 · Guardrails that make it finish第 5 步 · 让它能收工的护栏

Learn先学

A team of agents can burn money and time forever. Put a limit on everything, and decide in advance what happens when something fails. Sort these safeguards by the problem they solve. One more safeguard: a plain fallback template, written when a model call for a page fails, so there is always a front page.

一队智能体可能永远烧钱烧时间。给每件事都设上限，并提前决定出问题时怎么办。把这些保护措施按它们解决的问题分类。还有一道保护：某个页面的模型调用失败时，写入一份朴素的备用模板，保证总有首页。

What I got wrong我踩过的坑“Event loop is closed” on exit. Python runs every async job on one scheduler called the event loop. asyncio has its own way of starting other programs (called subprocess transports), and mixing that with a long-running agent loop left things to clean up after the loop had already shut down. Plain subprocess.Popen for workers, plus closing the MCP toolset inside the loop (the finally in Step 4), fixed it. Output tearing the live view. Framework banners printed by workers broke the rich display. Sending their output to DEVNULL (a hole that swallows the text) is fine because they report through the board anyway. Cost. Five workers plus inspectors add up fast, so I keep the two model names (coordinator and workers) in one config read from environment variables, and drop to cheaper models while experimenting. Also, the default 5-second MCP timeout was too short for the first browser call, so I raised it to 30.退出时出现“Event loop is closed”。Python 把所有异步任务都交给一个叫事件循环（event loop）的调度器。把 asyncio 自己启动程序的方式（子进程传输）和长时间运行的智能体循环混用，循环关闭后还留着没清理的东西。工人改用普通的 subprocess.Popen，并在循环里面关闭 MCP 工具集（第 4 步的 finally），就解决了。输出撕裂实时视图。工人打印的框架横幅会弄乱 rich 的显示。把它们的输出丢到 DEVNULL（一个吞掉文字的“黑洞”）就行，反正它们是通过任务板汇报的。成本。五个工人加检查员，花费涨得很快，所以我把两个模型名（总协调和工人）放在一个由环境变量读取的配置里，实验时换成便宜的模型。另外，MCP 默认 5 秒超时对第一次打开浏览器太短，我调到了 30 秒。

Common errors常见错误

• google.genai.errors.ClientError: 429 RESOURCE_EXHAUSTED: Five workers called the model at once and hit the rate limit. Fix: start them a few seconds apart or cap them with max_llm_calls.
• sqlite3.OperationalError: database is locked: Workers write to the board at the same time. Fix: use a short timeout and retry, or write one row per step.
• A worker never finishes (no error): Nothing stops it. Fix: team.wait_all(timeout=300) then kill what is left.

• google.genai.errors.ClientError: 429 RESOURCE_EXHAUSTED：五个工人同时调用模型，触到了频率限制。解决：错开几秒启动，或用 max_llm_calls 限制次数。
• sqlite3.OperationalError: database is locked：几个工人同时写任务板。解决：设置较短的超时再重试，或每一步只写一行。
• A worker never finishes (no error)：没有东西让它停下。解决：用 team.wait_all(timeout=300)，到时把剩下的进程结束掉。

Takeaways要点回顾

• The outer loop is an agent with a few tools. The agent chooses, the tools do the exact mechanics.
• Start workers without waiting, so they run together. Waiting is its own tool.
• The shared board is the only channel between coordinator and workers.
• Use a fresh, short-lived inspector with a real browser for each page.
• Bound everything: LLM calls, worker time, inspection time and one fix per page.
• Kill the whole process tree on timeout, and keep a plain fallback so there is always a front page.
• Keep model names in one config so experiments stay cheap.

• 外层循环是一个带几个工具的智能体：智能体做选择，工具做精确的机械活。
• 启动工人时不要等，这样它们能同时跑。等待是单独的工具。
• 共享任务板是总协调和工人之间唯一的通道。
• 每个页面用一个全新、短命、带真实浏览器的检查员。
• 给一切设上限：模型调用次数、工人时间、检查时间，以及每个页面只修一次。
• 超时要杀掉整个进程树，并准备朴素的备用页面，保证总有首页。
• 把模型名放在一个配置里，实验才不贵。
