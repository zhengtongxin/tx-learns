Roles, tasks and crews角色、任务与团队

Split one job between workers who each have a role, with CrewAI · ~25 min · hands-on用 CrewAI 把一件事分给各有角色的工人 · 约 25 分钟 · 动手实践

Where we left off上回讲到

Last time the assistant could research suppliers on the web, but one script did every role. Today it fails when Uncle Lim wants both sides of an idea and gets one mixed-up answer. We fix it by giving each worker a role and each job a task, like Ah Seng on drinks and Kak Ros on noodles.

上回助手能上网查供应商，但所有角色都由一个脚本包办。今天的问题是：Lim 叔叔想听一个点子的正反两面，得到的却是一份混在一起的答案。我们的办法是给每个工人一个角色，给每件活一个任务，就像 Ah Seng 管饮料、Kak Ros 管面。

Side case支线案例

Wira runs a small stall at a night market and keeps wondering: should durian cendol go on the menu? Friends argue both ways, and Wira never hears the arguments side by side. So Wira builds a tiny crew: one worker argues for, the same worker argues against, and a picky regular customer reads both and picks the winner. Along the way you learn the three words that run through every multi-agent team: agent, task and crew. Wira's durian cendol crew has the same shape as the morning crew at Kopi Corner.

Wira 在夜市开了一个小摊，总在想：菜单上该不该加榴莲 cendol？朋友们各说各的，Wira 从没把两边的理由放在一起听过。于是 Wira 搭了一个小团队：一个工人陈述赞成的理由，同一个工人再陈述反对的理由，最后由一位挑剔的熟客读完两份，选出赢家。过程中你会学到每个多智能体团队都离不开的三个词：智能体、任务和团队。Wira 的榴莲 cendol 团队和 Kopi Corner 的早班是同一个结构。

Step 1 · Start a crew from the scaffold第 1 步 · 用脚手架创建一个团队

Learn先学

Before any code, a picture. Think of a kopitiam at 7am. Ah Seng only makes drinks. Kak Ros only cooks noodles. The towkay (the boss) cooks nothing: he takes orders and decides who does what. Nobody's job overlaps, and everyone knows what “done” looks like.

CrewAI is a Python library built on exactly this picture. An agent is a worker with a role, a goal and a backstory. A task is one order slip. A crew is the shop: the workers plus the slips. The command crewai create crew builds the shop for you. Pin the version, because the library changes fast and a newer one can break the generated project.

先看一幅画面。想象早上 7 点的 kopitiam（街坊咖啡店）。Ah Seng 只做饮料，Kak Ros 只煮面。towkay（老板）什么都不煮：他接单，并决定谁做什么。每个人的工作互不重叠，也都知道“做完”是什么样子。

CrewAI 是一个完全按这幅画面设计的 Python 库。智能体是有角色、目标和背景故事的工人。任务是一张订单。团队（crew）就是整间店：工人加订单。命令 crewai create crew 会替你搭好这间店。要锁定版本，因为这个库更新很快，新版本可能弄坏生成的项目。

# pin the version, then check it uv tool install crewai==1.14.4 uv tool list # build a project called menu_argument, then run it crewai create crew menu_argument cd menu_argument crewai run # what you get (the parts we touch): # src/menu_argument/config/agents.yaml who the workers are # src/menu_argument/config/tasks.yaml the order slips # src/menu_argument/crew.py wires them into a crew # src/menu_argument/main.py the start button

Expected output (your wording will differ)预期输出（你的措辞会有所不同）

$ uv tool list crewai v1.14.4 - crewai $ crewai create crew menu_argument Crew menu_argument created successfully!

Step 2 · Describe the workers in agents.yaml第 2 步 · 在 agents.yaml 里描述工人

Learn先学

Our practice crew settles an argument for Wira, who wonders if durian cendol belongs on the menu. One agent argues the case, and a picky regular customer decides who argued better.

Each worker gets a role (the job title), a goal (what it is trying to do) and a backstory (a line of character). Anything in {curly braces} is a blank that gets filled in when you start the crew. The llm line picks a model per agent, written as provider/model. The prompts live in YAML, so you can reword them without touching Python.

我们的练习团队要替 Wira 解决一个争论：菜单上要不要加榴莲 cendol（一种冰甜品）。一个智能体负责陈述理由，一位挑剔的熟客来判断谁说得更好。

每个工人有角色（职位名称）、目标（它要做什么）和背景故事（一句人物设定）。{花括号} 里的内容是空格，启动团队时才填入。llm 这一行给每个智能体选模型，写成 提供商/模型。提示词放在 YAML 里，改措辞不用动 Python。

# config/agents.yaml arguer: role: > Stall owner who loves a good pitch goal: > Make one short, convincing case about this menu idea: {idea} backstory: > You have sold food at night markets for years and know what people pay for. llm: openai/gpt-4o-mini regular: role: > Picky regular customer goal: > Read both cases about {idea} and pick the stronger one. Judge only the arguments. backstory: > You eat here every morning and you are hard to impress. llm: openai/gpt-4o-mini

Step 3 · Write the order slips in tasks.yaml第 3 步 · 在 tasks.yaml 里写订单

Learn先学

A task says what to do and what done looks like. The description is the order. The expected_output is the finish line, like “one teh tarik, less sweet, in a glass”. The agent line says who takes the slip.

One worker can take many slips. Here arguer takes two: the case for and the case against. output_file saves each result to disk.

任务说明做什么和做成什么样才算完成。description 是订单内容，expected_output 是终点线，就像“一杯少甜的拉茶，装在玻璃杯里”。agent 这一行说明谁来接这张单。

一个工人可以接多张单。这里 arguer 接了两张：赞成的理由和反对的理由。output_file 把每个结果存到磁盘。

# config/tasks.yaml argue_for: description: > Argue in favour of: {idea}. Keep it tight. expected_output: > A short, punchy argument for the idea. agent: arguer output_file: output/for.md argue_against: description: > Argue against: {idea}. expected_output: > A short, punchy argument against the idea. agent: arguer output_file: output/against.md verdict: description: > Read both arguments, decide which side wins and say why. expected_output: > The winning side plus two or three reasons. agent: regular output_file: output/verdict.md

Step 4 · Wire it up in crew.py and start it第 4 步 · 在 crew.py 里接线并启动

Learn先学

crew.py turns the YAML into real objects. The @agent and @task decorators collect every method they mark into self.agents and self.tasks, in the order the methods are written. In a sequential crew, that order is the running order, and each task automatically sees the results of the tasks before it. That is how verdict can read both arguments without you passing anything by hand.

kickoff(inputs=...) is the start button. Its dictionary fills the {curly} blanks, so every blank in both YAML files needs a key.

crew.py 把 YAML 变成真正的对象。@agent 和 @task 这两个装饰器会把它们标记的方法收集进 self.agents 和 self.tasks，顺序就是方法的书写顺序。在顺序式（sequential）团队里，这个顺序就是执行顺序，而且每个任务会自动看到前面任务的结果。所以 verdict 不用你手动传递，就能读到两份论点。

kickoff(inputs=...) 是启动键。它的字典用来填 {花括号} 里的空格，所以两个 YAML 文件里的每个空格都要有对应的键。

# crew.py from crewai import Agent, Crew, Process, Task from crewai.project import CrewBase, agent, crew, task @CrewBase class MenuArgument(): @agent def arguer(self) -> Agent: return Agent(config=self.agents_config["arguer"], verbose=True) @agent def regular(self) -> Agent: return Agent(config=self.agents_config["regular"], verbose=True) @task # the order here is the running order def argue_for(self) -> Task: return Task(config=self.tasks_config["argue_for"]) @task def argue_against(self) -> Task: return Task(config=self.tasks_config["argue_against"]) @task def verdict(self) -> Task: return Task(config=self.tasks_config["verdict"]) @crew def crew(self) -> Crew: return Crew(agents=self.agents, tasks=self.tasks, process=Process.sequential, # slips handled top to bottom verbose=True)
# main.py def run(): idea = input("Menu idea to argue about: ") result = MenuArgument().crew().kickoff(inputs={"idea": idea}) print(result.raw)

Expected output (your wording will differ)预期输出（你的措辞会有所不同）

Menu idea to argue about: durian cendol ... (the arguer, the regular and the verdict print their turns here) Verdict: try it as a weekend special first; the smell is the risk.

Sort each piece into the part of the shop it belongs to.

把每一项归到它所属的部分。

Step 5 · Sequential or hierarchical?第 5 步 · 顺序式还是层级式？

Learn先学

Sequential is the default: the slips run in the listed order and each result flows forward. It is predictable and cheap.

Hierarchical adds a manager, like the towkay. The manager decides which worker takes which task and can send work back. It is more flexible, but it uses more tokens and is less predictable. Pick it only when the order truly cannot be fixed in advance.

One more trick: placeholders also work inside a role. A second practice crew had a researcher whose role was “{topic} Senior Researcher”, so the same YAML works for any topic you pass in.

顺序式是默认做法：订单按列出的顺序执行，每个结果往下传。结果可预期，也便宜。

层级式加了一位主管，就像 towkay。主管决定哪个工人接哪个任务，还能把活打回去重做。它更灵活，但更耗 token，也更难预料。只有当顺序真的没法事先定好时才选它。

还有一个小技巧：占位符也能放进角色里。我的第二个练习团队里，研究员的角色写成“{topic} 高级研究员”，同一份 YAML 就能用于你传入的任何主题。

Crew( agents=self.agents, tasks=self.tasks, process=Process.hierarchical, manager_llm="openai/gpt-4o", # a manager model hands out the slips )
What I got wrong我犯过的错Task order is method order. I once wrote the verdict method first, and the regular “judged” before any argument existed. Placeholders need keys. My YAML used {idea} but I started the crew with {"topic": ...}, and it failed the moment the blanks were filled in. I forgot to pin the version. A newer CrewAI broke the generated project, so now I run uv tool list first and uv tool uninstall crewai if an old one is hanging around.任务顺序就是方法顺序。我曾把 verdict 方法写在最前面，结果熟客在任何论点出现之前就“裁决”了。占位符需要对应的键。我的 YAML 用的是 {idea}，启动团队时却传了 {"topic": ...}，一填空格就报错。我忘了锁定版本。新版 CrewAI 弄坏了生成的项目，所以现在我先运行 uv tool list，如果还留着旧版本，就用 uv tool uninstall crewai 清掉。

Common errors常见错误

• command not found: crewai: The tool is installed but its folder is not on your PATH. Fix: run uv tool update-shell, then open a new terminal.
• KeyError: 'idea': The task text uses {idea} but kickoff(inputs=...) did not pass it. Fix: pass inputs={"idea": idea}.
• yaml.scanner.ScannerError: mapping values are not allowed here: Bad indentation or a colon inside unquoted text in a YAML file. Fix: use two spaces per level and put > after description: for multi-line text.

• command not found: crewai：工具装了，但它所在的文件夹不在 PATH 里。解决：运行 uv tool update-shell，再打开一个新终端。
• KeyError: 'idea'：任务文字里用了 {idea}，但 kickoff(inputs=...) 没有传。解决：传入 inputs={"idea": idea}。
• yaml.scanner.ScannerError: mapping values are not allowed here：YAML 文件缩进不对，或没加引号的文字里有冒号。解决：每级缩进两个空格，多行文字在 description: 后面加 >。

Takeaways要点回顾

• An agent is a worker with a role, a goal and a backstory.
• A task is one order slip: a description and an expected output.
• A crew holds the workers and the slips and runs them.
• Prompts live in YAML and wiring lives in Python, so you can reword without touching code.
• In a sequential crew, method order is running order, and each task sees what came before.
• Hierarchical adds a manager: more flexible, but costlier and less predictable.
• Pin the version and match every {blank} with an input key.

• 智能体是有角色、目标和背景故事的工人。
• 任务是一张订单：一段描述加一个预期输出。
• 团队装着工人和订单，并负责执行。
• 提示词放 YAML，接线放 Python，改措辞不用动代码。
• 顺序式团队里，方法顺序就是执行顺序，每个任务都能看到前面的结果。
• 层级式加了一位主管：更灵活，但更贵，也更难预料。
• 锁定版本，并让每个 {空格} 都有对应的输入键。
