Project: a claims desk pilot项目：理赔台试点

Build the smallest thing the customer can react to: sample claims, a queue with a hard sign-off rule, and an agent that decides · ~30 min · hands-on做出客户能有反应的最小东西：样本理赔、带硬性签字规则的队列，以及会做决定的智能体 · 约 30 分钟 · 动手实践

The story故事

Mei Ling has the brief and a plan. Now Kaya Travel Cover needs something to react to. In this project she builds a first pilot: a small backend holding 25 sample claims, a dashboard for the handlers, and an agent (a model that reads a claim, is handed the policy wording, and returns a decision). For each claim it must say approve, decline or refer, a payout, and two or three sentences of reasons. Then she runs it on the whole queue and compares with what Aisha and the handlers actually decided.

Mei Ling 有了需求，也有了计划。现在 Kaya Travel Cover 需要一个能让他们有反应的东西。这个项目里她要做第一个试点：一个装着 25 份样本理赔的小后端、一个给理赔员看的看板，以及一个智能体（读理赔、拿到条款与保单资料、给出决定的模型）。对每份理赔，它要给出批准、拒绝或转交，再加赔付金额和两三句理由。最后她把整条队列跑一遍，和 Aisha 与理赔员们真实的决定对比。

Step 1 · Make the sample data, and hide the answer key第 1 步 · 造样本数据，并把答案藏起来

Learn先学

You cannot test on real customers, so you invent 25 claims, their policies, their customers and a plain policy wording. Also write down what the handlers decided for each. That list is the answer key, and it must live in a folder the agent never reads. Like a teacher who keeps the marking sheet out of the exam hall.

不能拿真实客户来测试，所以你自己编 25 份理赔、对应的保单、客户，还有一份朴素的保单条款。同时把理赔员对每份的决定也写下来。这份清单就是答案，必须放在智能体永远读不到的文件夹里。就像老师把评分表留在考场外面。

pilot/ data/ # the agent may read this claims.json # 25 invented claims policies.json # policy id -> cover and limits policy_wording.txt # the plain wording of the cover answer_key/ # the agent must NEVER read this handler_decisions.json # what the handlers decided # one claim in claims.json {"id": "C007", "policy_id": "P003", "customer": "Mr Tan", "story": "My flight was cancelled and I paid for a hotel.", "amount": 420}

Step 2 · The backend queue第 2 步 · 后端的队列

Learn先学

Every claim needs a state, so everyone knows where it is. Four are enough: waiting, in progress, waiting for sign-off and decided. In the code they are the words waiting, in_progress, waiting_signoff and decided. It works like the queue-number ticket machine at the shophouse door: a claim is always in exactly one place.

每份理赔都要有一个状态，让大家知道它在哪。四个就够：等待中、处理中、等待签字、已决定。代码里它们分别写作 waiting、in_progress、waiting_signoff 和 decided。就像店屋门口的取号机：一份理赔在任何时刻都只在一个地方。

queue = {} # claim id -> its record def add_claim(claim): queue[claim["id"]] = {"claim": claim, "state": "waiting", "decision": None} def start(claim_id): queue[claim_id]["state"] = "in_progress"

Step 3 · A dashboard to look at第 3 步 · 一个能看的看板

Learn先学

The handlers will not read JSON. They need to see the queue, each claim in full, the agent’s reasons, and what the agent is doing step by step. A real page can come later. For the pilot, even a printout of the queue is something Aisha can react to, and that is the point.

理赔员不会去读 JSON。他们要看到队列、每份理赔的全部内容、智能体给的理由，以及智能体一步步在做什么。真正的网页可以以后再做。试点阶段，哪怕只是把队列打印出来，Aisha 也能有反应，而这正是目的。

def show_queue(): for claim_id, item in queue.items(): decision = item["decision"] line = f"{claim_id} {item['state']:16}" if decision: line += f"{decision['action']:8} S${decision['payout']} {decision['reason']}" print(line)

Step 4 · A hard rule in the backend第 4 步 · 后端里的硬性规则

Learn先学

Any payout over the sign-off limit (here S$800) must wait for a handler, even if the agent tries to pay. A rule in the prompt is a request the model may ignore. A rule in the code is a locked door. So put it in the backend, in the one function every decision passes through. A refer also goes to a handler.

任何超过签字上限（这里是 S$800）的赔付都必须等理赔员，哪怕智能体想直接赔。提示词里的规矩只是请求，模型可能不听；代码里的规矩是一扇锁住的门。所以把它放进后端，放在每个决定都必经的那个函数里。转交（refer）也交给理赔员。

SIGNOFF_LIMIT = 800 def record_decision(claim_id, decision): item = queue[claim_id] item["decision"] = decision too_big = decision["action"] == "approve" and decision["payout"] > SIGNOFF_LIMIT needs_human = too_big or decision["action"] == "refer" item["state"] = "waiting_signoff" if needs_human else "decided" def sign_off(claim_id, handler): queue[claim_id]["state"] = "decided" queue[claim_id]["signed_by"] = handler

Step 5 · The agent that reads one claim第 5 步 · 读一份理赔的智能体

Learn先学

Now the part everyone came to see. The agent gets one claim, with its policy and the wording pasted into the prompt, and returns a decision as JSON: action, payout and reason. It never touches the queue itself. It only returns an answer, and record_decision from Step 4 decides what happens to it. This first agent has no tools: it is one model call, and the code gives it everything it needs. Install with pip install openai and set your OPENAI_API_KEY.

现在是大家最想看的部分。智能体拿到一份理赔，保单和条款已经贴在提示词里，然后以 JSON 返回决定：action、payout、reason。它自己不碰队列，只返回答案，怎么处理由第 4 步的 record_decision 决定。这第一个智能体没有工具：它就是一次模型调用，代码把它需要的一切都给了它。用 pip install openai 安装，并设置好 OPENAI_API_KEY。

import json from openai import OpenAI client = OpenAI() POLICIES = json.load(open("data/policies.json")) WORDING = open("data/policy_wording.txt").read() def decide(claim): policy = POLICIES[claim["policy_id"]] prompt = f"""You help a travel insurer's claims desk. Policy wording: {WORDING} This customer's policy: {json.dumps(policy)} The claim: {json.dumps(claim)} Reply with JSON only: {{"action": "approve" or "decline" or "refer", "payout": a number in S$, "reason": two or three short sentences}}""" reply = client.chat.completions.create( model="gpt-5.4-mini", messages=[{"role": "user", "content": prompt}], response_format={"type": "json_object"}) return json.loads(reply.choices[0].message.content)

Step 6 · Run it on the queue and compare第 6 步 · 跑整条队列并对比

Learn先学

Load the claims, run each through the agent and the backend, then show the queue. Scoring is a separate step that runs once the queue is built, and it is the only place that opens the answer key. A pilot like this usually agrees with the handlers on most claims. It struggles on the ones that need the claims manual or the customer’s history. That gap is the plan for everything that follows.

加载理赔，逐份交给智能体和后端，然后显示队列。打分是队列跑完之后的另一步，也是唯一会打开答案的地方。这样的试点通常在大多数理赔上和理赔员一致，难的是那些需要理赔手册或客户历史才能判断的。这个差距，就是后面所有内容的计划。

# run_pilot.py (uses add_claim, start, record_decision, show_queue and decide from above) for claim in json.load(open("data/claims.json")): add_claim(claim) for claim_id in list(queue): start(claim_id) record_decision(claim_id, decide(queue[claim_id]["claim"])) show_queue() # score.py: add this to the end of run_pilot.py, so it can see queue. # It is the ONLY code that opens the answer key. key = json.load(open("answer_key/handler_decisions.json")) # {claim id: handler's action}, e.g. {"C007": "approve"} agree = sum(1 for cid, item in queue.items() if item["decision"]["action"] == key[cid]) print(f"agrees with handlers on {agree} of {len(key)} claims")

Takeaways要点回顾

• Build the smallest thing the customer can react to.
• Invent your own sample claims, and keep the answer key where the agent cannot read it.
• Give every claim one clear state: waiting, in progress, waiting for sign-off, decided.
• Enforce the sign-off rule in the backend, not in the prompt.
• The agent only returns an answer. The backend decides what happens to it.
• A score from an agent that saw the answers means nothing.
• The gap where the pilot fails is the plan for what comes next.

• 做出客户能有反应的最小东西。
• 样本理赔自己编，答案放在智能体读不到的地方。
• 每份理赔只有一个明确的状态：等待、处理中、等待签字、已决定。
• 签字规则放在后端执行，而不是写在提示词里。
• 智能体只返回答案，怎么处理由后端决定。
• 见过答案的智能体，分数毫无意义。
• 试点出错的地方，就是接下来要做的事。
