An agent on a managed runtime托管运行时上的智能体

Run the same agent where someone else keeps the servers, and write its long jobs so they survive session limits · ~30 min · concept with one runnable idea让同一个智能体跑在别人维护服务器的地方，并把长任务写得能熬过会话的时限 · 约 30 分钟 · 概念课，带一段能跑的代码

The story故事

The agent works on Mei Ling’s laptop, and Kumar does not want to look after one more server. He wants a place where the agent runs, scales and restarts without him. A managed agent runtime is that: you hand it your agent as an app, and it starts a fresh, isolated copy for each piece of work. Mei Ling’s job is to make the agent fit. You need Flask and requests (pip install flask requests). The agent itself stays a stand-in, so everything runs on its own.

智能体在 Mei Ling 的笔记本上跑得好好的，而 Kumar 不想再多管一台服务器。他想要一个地方，让智能体自己运行、伸缩、重启，不用他操心。托管的智能体运行时就是这样的地方：你把智能体当成一个应用交给它，它为每一件工作启动一份全新的、相互隔离的副本。Mei Ling 要做的，是让智能体适应它。你需要 Flask 和 requests（pip install flask requests）。智能体本身仍用替身，所以一切都能独立运行。

Step 1 · Turn the agent into an app with two doors第 1 步 · 把智能体做成有两扇门的应用

Learn先学

A runtime does not know what is inside your agent. It only needs two doors. One endpoint takes work (here /invocations). One endpoint answers a health ping (/ping): “are you alive?”. Like the queue ticket machine and the counter bell: one gives out numbers, the other tells the street the shop is open. Many runtimes use these two names on port 8080. Check yours.

运行时不知道你的智能体里面是什么。它只需要两扇门。一个接口接收工作（这里是 /invocations）。一个接口回应健康探测（/ping）：“你还活着吗？”。就像取号机和柜台的铃：一个发号码，一个告诉街上的人店开着。很多运行时用这两个名字，端口 8080。要核对你用的那个。

# agent_app.py from flask import Flask, jsonify, request app = Flask(__name__) def decide_claim(claim): """Stand-in for the real agent. Swap the real one in later.""" return {"action": "approve", "payout": float(claim["amount"])} @app.get("/ping") def ping(): return jsonify(status="Healthy") @app.post("/invocations") def invocations(): body = request.get_json(silent=True) or {} claim = body.get("claim") if not claim: return jsonify(error="send a claim"), 400 return jsonify(decision=decide_claim(claim)) if __name__ == "__main__": app.run(host="0.0.0.0", port=8080)

Step 2 · Test it on your own computer first第 2 步 · 先在自己电脑上测试

Learn先学

Deploying is slow and costs money, so find the mistakes at home. The same app runs on your laptop and on the runtime. Only the address changes. Flask’s test client calls the app without starting a server. To run it for real, use python agent_app.py and call http://127.0.0.1:8080.

部署又慢又花钱，所以错误要在家里先找出来。同一个应用在笔记本和运行时上跑的是同一份代码，只有地址不同。Flask 的测试客户端不用启动服务器就能调用应用。想真跑一遍，就用 python agent_app.py，然后调用 http://127.0.0.1:8080。

# test_local.py from agent_app import app client = app.test_client() print(client.get("/ping").json) # {'status': 'Healthy'} print(client.post("/invocations", json={"claim": {"id": "C-2001", "amount": 450}}).json) print(client.post("/invocations", json={}).status_code) # 400: no claim sent

Step 3 · Deploy, then watch cold and warm starts第 3 步 · 部署，然后观察冷启动和热启动

Learn先学

Package the app (usually as a container image) and deploy it with your runtime’s own command. Those commands differ, so follow its guide. The agent code does not change. Then time it. A cold start is the first call, when the runtime must start a fresh copy. A warm call reaches a copy that is already running, and it is much faster. Like the shophouse in the morning: the first customer waits while the ceiling fans spin up.

把应用打包（通常是一个容器镜像），用运行时自己的命令部署。这些命令各家不同，照它的指南来。智能体的代码不用变。然后给它计时。冷启动是第一次调用，运行时得先启动一份新的副本。热调用则打到已经在跑的副本上，快得多。就像早上的店屋：第一位客人要等吊扇转起来。

# timing.py: set AGENT_URL to the deployed address, or leave it for your laptop import os, time, requests URL = os.environ.get("AGENT_URL", "http://127.0.0.1:8080") CLAIM = {"claim": {"id": "C-2001", "amount": 450}} def timed(): start = time.perf_counter() reply = requests.post(URL + "/invocations", json=CLAIM, timeout=60) # add your runtime’s sign-in headers if it needs them return reply.status_code, round(time.perf_counter() - start, 2) print("first call:", timed()) print("second call:", timed())

Step 4 · Every run gets its own session, and sessions end第 4 步 · 每次运行有自己的会话，会话会结束

Learn先学

The runtime gives each dispatch and each evaluation its own session: a separate little computer with its own memory. Two claims never share variables. A session ends when it has been idle for about a minute, meaning no request is in flight. It ends even if a background thread of yours is still going, because the runtime cannot see inside. Anything kept in the session’s memory or disk goes with it. Only things stored outside survive. Your runtime tells you the session id in a request header. The name differs, so check it.

运行时给每一次派发、每一次评测一个自己的会话：一台独立的小电脑，有自己的内存。两份理赔永远不共用变量。会话在空闲大约一分钟后结束，空闲的意思是没有任何请求在处理。哪怕你有后台线程还在跑，它也照样结束，因为运行时看不到里面。会话内存或磁盘里放的东西，会随它一起消失。只有存在外面的才活得下来。运行时会在请求头里告诉你会话编号，名字各家不同，要去核对。

# agent_app.py, changed SESSIONS = {} # lives in this session’s memory only def session_id(): return request.headers.get("X-Session-Id", "local") # header name differs per runtime @app.post("/invocations") def invocations(): body = request.get_json(silent=True) or {} claim = body.get("claim") if not claim: return jsonify(error="send a claim"), 400 seen = SESSIONS.setdefault(session_id(), []) seen.append(claim["id"]) return jsonify(decision=decide_claim(claim), seen_in_this_session=seen)

What survives when a session ends? Sort them.

会话结束后，什么还在？来分一分。

Step 5 · Keep long work visibly alive第 5 步 · 让长任务清清楚楚地“活着”

Learn先学

A long job, such as reading a thick claim file, may run for minutes in a background thread. To the runtime, nothing is happening, so it ends the session mid-job. The fix is to show the work. Count the jobs that are running, and let /ping say “busy” while the count is above zero. Also record each step, so a person can see progress. Keep the flag honest: set it only while real work runs. A stuck flag keeps a session, and your bill, alive. The word for “busy” varies, so use your runtime’s.

长任务，比如读一份很厚的理赔文件，可能在后台线程里跑几分钟。对运行时来说，什么都没发生，于是它在任务中途结束了会话。解法是把工作亮出来。数一数正在跑的任务，只要数字大于零，就让 /ping 回答“忙”。再把每一步记下来，让人看得到进度。标志要诚实：只在真有工作时才设置。标志卡住不放，会话和你的账单就一直活着。“忙”这个词各家不同，用你的运行时规定的。

# agent_app.py, added (import threading, time and from contextlib import contextmanager at the top) BUSY, LOCK, JOBS = 0, threading.Lock(), {} @contextmanager def busy(): global BUSY with LOCK: BUSY += 1 try: yield finally: with LOCK: BUSY -= 1 def long_job(claim_id): with busy(): for step in ("read the file", "decide", "write the record"): JOBS[claim_id] = {"step": step, "at": time.time()} # progress anyone can read time.sleep(20) # stands in for slow model and tool calls JOBS[claim_id] = {"step": "done", "at": time.time()} @app.post("/jobs/<claim_id>") def start_job(claim_id): threading.Thread(target=long_job, args=(claim_id,), daemon=True).start() return jsonify(started=claim_id), 202 @app.get("/jobs/<claim_id>") def job(claim_id): return jsonify(JOBS.get(claim_id, {"step": "unknown"})) # and ping becomes: @app.get("/ping") def ping(): return jsonify(status="HealthyBusy" if BUSY else "Healthy")

Step 6 · Pause in one session, resume in another第 6 步 · 在一个会话里暂停，在另一个会话里继续

Learn先学

A payout over S$800 waits for a handler, maybe for hours. The session that started it will be gone by then. So park the waiting claim outside the session, in a database, under its claim id. Whichever new session gets the handler’s answer takes it out and carries on. This is the pause idea from the earlier lesson, in a smaller form. Here it is a local SQLite file so the code runs at home. On the runtime, point it at a hosted database, because the session’s disk disappears too.

超过 S$800 的赔付要等理赔员，可能一等就是几个小时。到那时，发起它的会话早已不在了。所以要把等待中的理赔放在会话外面，放进数据库，用理赔编号做标签。无论哪个新会话收到理赔员的答复，都把它取出来接着干。这是前面那一课“暂停”的想法，做成了更小的版本。这里用的是本地 SQLite 文件，方便在家里运行。到了运行时上，要换成托管数据库，因为会话的磁盘也会消失。

# agent_app.py, added (import json, os and sqlite3 at the top) SIGNOFF_LIMIT = 800 db = sqlite3.connect(os.environ.get("STATE_DB", "state.db"), check_same_thread=False) db.execute("CREATE TABLE IF NOT EXISTS parked (claim_id TEXT PRIMARY KEY, claim TEXT, decision TEXT)") def park(claim, decision): db.execute("INSERT OR REPLACE INTO parked VALUES (?, ?, ?)", (claim["id"], json.dumps(claim), json.dumps(decision))) db.commit() def take(claim_id): row = db.execute("SELECT claim, decision FROM parked WHERE claim_id = ?", (claim_id,)).fetchone() if row is None: return None db.execute("DELETE FROM parked WHERE claim_id = ?", (claim_id,)) db.commit() return json.loads(row[0]), json.loads(row[1]) def settle(claim, decision): if decision["payout"] > SIGNOFF_LIMIT: park(claim, decision) return jsonify(waiting=True, payout=decision["payout"]) return jsonify(paid=decision["payout"]) # stand-in for the real payment call # in invocations(): a resume carries no new claim, so handle it right after "body = ...", before the 400 check resume = body.get("resume") # e.g. {"claim_id": "C-2002", "ok": True} if resume: found = take(resume.get("claim_id")) if found is None: return jsonify(error="nothing is waiting for that claim"), 404 claim, decision = found return jsonify(paid=decision["payout"] if resume.get("ok") else False) # and the last line of invocations() becomes: return settle(claim, decide_claim(claim))

Step 7 · Send it back, not only sign it off第 7 步 · 能退回，不只是签字

Learn先学

A handler can do more than yes or no. A senior handler can send back a large approval with a note, “the receipt is for a smaller bag”, and the agent decides again in a new session, with the note as extra input. A plain sign-off carries no reason. A send-back does. The stand-in agent here just obeys the note by capping the payout. A real agent reads the note in its prompt and may decide something else.

理赔员能做的不只是“行”或“不行”。资深理赔员可以把一笔大额批准退回，附上一句话，比如“收据上的箱子小一些”，智能体就在新会话里重新判定，把这句话当作额外的输入。单纯的签字不带理由，退回带着理由。这里的替身智能体只是照字面执行，把赔付封顶。真正的智能体会在提示词里读这句话，可能做出别的决定。

# agent_app.py, changed def decide_claim(claim, note=""): payout = float(claim["amount"]) if note: # stand-in: a real agent reads the note in its prompt payout = min(payout, SIGNOFF_LIMIT) return {"action": "approve", "payout": payout} # in the resume branch of invocations(), after "claim, decision = found": if resume.get("send_back"): return settle(claim, decide_claim(claim, note=resume["send_back"])) # try_it.py # client = app.test_client() # claim = {"id": "C-2002", "amount": 1200} # print(client.post("/invocations", json={"claim": claim}).json) # waiting: True # back = {"resume": {"claim_id": "C-2002", "send_back": "receipt shows a smaller bag"}} # print(client.post("/invocations", json=back).json) # paid: 800.0
What I got wrong我当时想错了A long job simply stopped halfway. Nothing in my logs said why. The runtime had decided the session was idle, because the job ran in a background thread and nothing was reporting. I first blamed my code. The fix was to report progress while it works: the busy ping and a step the job writes down at each stage. Keeping long work alive and visible is the harness’s job, not the runtime’s.一个长任务在半路就停了。我的日志里什么原因都没写。运行时认定这个会话空闲了，因为任务跑在后台线程里，没有任何东西在汇报。我一开始怪自己的代码。解决办法是边干边汇报：忙碌的 ping，加上任务在每个阶段写下的一步记录。让长任务活着、看得见，是 harness 的工作，不是运行时的工作。

Now make it yours现在把它变成你的

Back at the shophouse回到店屋Kumar likes the idea of a runtime the way he likes the building’s landlord: someone else mends the roof. But a landlord does not know a claim is half done. When Aisha leaves a big claim with the red stamp note clipped to it, the folder goes back in the cabinet, and whoever is at the counter next picks it up. If she writes “smaller bag” on the note instead of stamping, the clerk does the sum again. Nobody has to remember anything. It is all in the folder.Kumar 喜欢运行时，就像喜欢大楼的房东：屋顶有别人来修。可房东不知道一份理赔办到了一半。Aisha 把一份大额理赔夹上“待盖章”的便条，文件夹就放回柜子里，下一个站在柜台的人拿起来接着办。如果她在便条上写的不是盖章，而是“箱子小一些”，柜员就把账重新算一遍。没有谁需要记着什么，一切都在文件夹里。

Takeaways要点回顾

• The same agent runs on a laptop or a runtime. The app needs one door for work and one for a health ping.
• Test at home first. Then deploy and time the cold and the warm start.
• Each dispatch or evaluation gets its own session, and nothing in a session’s memory or disk outlives it.
• A session ends after about a minute idle, even with a background thread running.
• Keep long work visibly alive: a busy ping, and a progress step at every stage.
• Park waiting work in a database under its claim id, so any later session can resume it.
• Sending back with a note is as important as signing off.

• 同一个智能体，在笔记本上或运行时上都能跑。应用需要一扇接收工作的门，一扇健康探测的门。
• 先在家里测试。再部署，给冷启动和热启动计时。
• 每次派发或评测都有自己的会话，会话内存和磁盘里的东西，活不过会话。
• 空闲约一分钟后会话就结束，即使后台线程还在跑。
• 让长任务清清楚楚地活着：忙碌的 ping，加上每个阶段的进度记录。
• 把等待中的工作按理赔编号放进数据库，之后任何会话都能接着干。
• 带着理由退回，和签字批准一样重要。
