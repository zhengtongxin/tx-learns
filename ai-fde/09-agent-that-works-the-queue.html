Project: an agent that works the queue项目：自己处理队列的智能体

Turn the pilot into one run that works the whole queue, with a to-do list to watch and failures that fix themselves · ~30 min · hands-on把试点变成一次运行就处理整条队列，有张能看的待办清单，失败也能自己修好 · 约 30 分钟 · 动手实践

The story故事

Mei Ling now knows the idea of a harness. At Kaya Travel Cover she turns it into a working run. One command should start it. The agent picks the order itself and ends with a short summary for the handlers. While it runs, the queue page shows a to-do list. Each claim goes to a fresh helper, the manual is read by section, and a failure never leaves a claim stuck. She builds it in six steps on top of the pilot (queue, add_claim, record_decision, start, decide, POLICIES and client from the claims desk project).

Mei Ling 现在懂了 harness 的思路。在 Kaya Travel Cover，她要把它变成能跑的东西。一条命令就能启动；智能体自己挑顺序，最后给理赔员一段简短总结。运行时，队列页面显示一张待办清单。每份理赔交给一个新帮手，手册按章节读取，失败也不会让理赔卡住。她分六步，在试点的基础上搭起来（用到理赔台项目里的 queue、add_claim、record_decision、start、decide、POLICIES 和 client）。

Step 1 · One command, the agent picks the order第 1 步 · 一条命令，顺序由智能体挑

Learn先学

The pilot walked the queue in the order it was stored. A handler would start with the big or urgent ones. So ask the model to order the claims first, then work through them, then write a short summary. Always check the model’s order: drop ids it invented and add any it forgot. Each client.chat.completions.create(...) call sends the model a list of messages and gets one reply back.

试点是按存放的顺序走队列的。理赔员会先处理金额大或紧急的。所以先让模型给理赔排序，再逐份处理，最后写一段简短总结。模型给的顺序一定要检查：去掉它编出来的 id，补上它漏掉的。每次 client.chat.completions.create(...) 调用，都是把一组消息发给模型，再拿回一条回复。

import json def pick_order(ids): brief = [{"id": i, "amount": queue[i]["claim"]["amount"]} for i in ids] reply = client.chat.completions.create( model="gpt-5.4-mini", messages=[{"role": "user", "content": "Order these insurance claims the way a careful handler would tackle them. " 'Reply with JSON only: {"order": [claim ids]}\n' + json.dumps(brief)}], response_format={"type": "json_object"}) order = json.loads(reply.choices[0].message.content)["order"] return [i for i in order if i in ids] + [i for i in ids if i not in order] def summarise(lines): reply = client.chat.completions.create( model="gpt-5.4-mini", messages=[{"role": "user", "content": "Write three short sentences for the claims handlers about this run:\n" + "\n".join(lines)}]) return reply.choices[0].message.content def run(ids): lines = [] for claim_id in pick_order(ids): start(claim_id) decision = decide(queue[claim_id]["claim"]) record_decision(claim_id, decision) lines.append(f"{claim_id}: {decision['action']} S${decision['payout']}") print(summarise(lines))

Step 2 · Options: cap the run, or run one claim第 2 步 · 选项：限制数量，或只跑一份

Learn先学

While you are building, you do not want to pay for 25 claims every trial. Add a cap that runs only the first five. Also add a way to run one named claim, which is how you debug a single odd case. Both options are plain command-line flags.

搭建的时候，不想每次试跑都为 25 份理赔付钱。加一个上限，只跑前五份。再加一个只跑指定理赔的方式，用来调试某个古怪的个案。两个选项都是普通的命令行参数。

import argparse, json if __name__ == "__main__": parser = argparse.ArgumentParser() parser.add_argument("--limit", type=int, help="run only the first N claims") parser.add_argument("--claim", help="run one named claim, e.g. C007") args = parser.parse_args() for claim in json.load(open("data/claims.json")): add_claim(claim) ids = list(queue) if args.claim: ids = [args.claim] elif args.limit: ids = ids[:args.limit] run(ids) # python run_queue.py --limit 5 (put this code at the end of the file with run)

Step 3 · A to-do list on the queue page第 3 步 · 队列页面上的待办清单

Learn先学

Handlers should see the run as it happens. Keep a to-do list with four states: to do, in progress, done and for handler. Save it to a file every time something changes. The queue page just reads that file, like the board behind Auntie Siew’s counter.

理赔员应该能看到运行过程。维护一张有四种状态的待办清单：待办、处理中、已完成、留给理赔员。每次有变化就存进文件。队列页面只要读这个文件，就像 Auntie Siew 柜台后面的那块板。

TODO_FILE = "todo.json" todo = {} # claim id -> {"state", "tries", "line", "read"} def save_todo(): json.dump(todo, open(TODO_FILE, "w"), indent=1) def plan(ids): for claim_id in ids: todo[claim_id] = {"state": "to_do", "tries": 0, "line": "", "read": []} save_todo() def show_todo(): for state in ["to_do", "in_progress", "done", "for_handler"]: names = [i for i, item in todo.items() if item["state"] == state] print(f"{state:12} {', '.join(names)}") # in run(ids): call plan(ids) first, then inside the loop # todo[claim_id]["state"] = "in_progress"; save_todo() # ...after record_decision: todo[claim_id]["state"] = "done"; save_todo()

Step 4 · A fresh helper for every claim第 4 步 · 每份理赔一个新帮手

Learn先学

A helper is a fresh model call that sees only one claim. The main run never reads its working. It receives one line: the decision and payout, or what went wrong. Nothing piles up between claims, so the 25th claim costs about the same as the first.

帮手就是一次只看一份理赔的全新模型调用。主流程从不读它的思考过程，只收到一行话：决定和赔付金额，或者哪里出了问题。理赔之间什么都不会堆积，所以第 25 份的成本和第 1 份差不多。

def run_helper(claim_id): """A fresh call: it sees this claim and nothing else.""" decision = decide(queue[claim_id]["claim"]) record_decision(claim_id, decision) return f"{claim_id}: {decision['action']} S${decision['payout']}" # in run(): the loop body becomes # todo[claim_id]["state"] = "in_progress"; save_todo() # todo[claim_id]["line"] = run_helper(claim_id) # todo[claim_id]["state"] = "done"; save_todo()

Step 5 · Read the manual by section, and show what was read第 5 步 · 按章节读手册，并显示读了什么

Learn先学

Give the helper the list of section titles and one tool that reads a section. It looks up only what it needs and calls the tool as many times as it likes, up to a limit. Log every title it reads. The claim page then shows what the decision was based on, which is what Aisha asks first. The model cannot run code itself. When it wants a section, its reply says to call read_manual with a title. Our loop runs that function, sends the text back as a tool message, and asks again, until the model answers without asking for more. This version of run_helper replaces the one in Step 4. Put the claims manual and the wording into data/manual.json, one entry per section.

给帮手一张章节标题清单和一个读取某一节的工具。它只查需要的，想调用几次都行，但有上限。把它读过的每个标题都记下来。理赔页面就能显示决定依据了什么，这正是 Aisha 最先会问的。模型自己不能运行代码。它想看某一节时，回复里会写明要用 read_manual 读哪个标题。我们的循环运行这个函数，把读到的文字作为 tool 消息送回去，再问一次，直到模型不再要求读取、直接给出答案。这一版 run_helper 会取代第 4 步的那一版。把理赔手册和条款放进 data/manual.json，每个章节一条。

SECTIONS = json.load(open("data/manual.json")) # section title -> text TOOLS = [{"type": "function", "function": { "name": "read_manual", "description": "Read one section of the claims manual or policy wording by its exact title.", "parameters": {"type": "object", "properties": {"title": {"type": "string"}}, "required": ["title"]}}}] def decide_with_manual(claim, read_log): policy = POLICIES[claim["policy_id"]] messages = [{"role": "user", "content": f"You help a travel insurer's claims desk. Section titles: {list(SECTIONS)}\n" f"Read only what you need with read_manual. Policy: {json.dumps(policy)}\n" f"Claim: {json.dumps(claim)}\n" 'Then reply with JSON only, no code fences: {"action": "approve" or "decline" or "refer", ' '"payout": a number in S$, "reason": two or three short sentences}'}] for _ in range(6): message = client.chat.completions.create( model="gpt-5.4-mini", messages=messages, tools=TOOLS).choices[0].message if not message.tool_calls: return json.loads(message.content) messages.append(message) for call in message.tool_calls: title = json.loads(call.function.arguments)["title"] read_log.append(title) messages.append({"role": "tool", "tool_call_id": call.id, "content": SECTIONS.get(title, "No such section.")}) raise RuntimeError("helper read too many sections without answering") def run_helper(claim_id): read_log = [] decision = decide_with_manual(queue[claim_id]["claim"], read_log) todo[claim_id]["read"] = read_log record_decision(claim_id, decision) return f"{claim_id}: {decision['action']} S${decision['payout']}"

Step 6 · Failures that fix themselves第 6 步 · 会自己修好的失败

Learn先学

Four rules, all in code. A claim that fails before it is decided goes back to the queue. If it fails twice, it is left for a handler. And no claim is ever decided twice, so before any work the code checks whether a decision already exists. The fourth closes the gap from a killed run: on start, anything still “in progress” goes back to “to do”.

四条规矩，全在代码里。还没决定就失败的理赔，回到队列。失败两次，就留给理赔员。任何理赔都不会被决定两次，所以动手之前，代码先检查是否已经有决定。第四条，补上运行被杀掉留下的漏洞：启动时，任何还停在“处理中”的理赔，都回到“待办”。

MAX_TRIES = 2 def recover(): """After a killed run, nothing may stay in_progress.""" for item in todo.values(): if item["state"] == "in_progress": item["state"] = "to_do" save_todo() def work_one(claim_id): item = todo[claim_id] if item["state"] != "to_do": return if queue[claim_id]["decision"] is not None: # never decide twice item["state"] = "done" save_todo() return item["state"] = "in_progress" item["tries"] += 1 save_todo() try: item["line"] = run_helper(claim_id) item["state"] = "done" except Exception as err: if item["tries"] < MAX_TRIES: item["state"] = "to_do" else: item["state"] = "for_handler" item["line"] = f"{claim_id}: failed twice ({type(err).__name__})" save_todo() # run(): call recover(), plan(ids), then for each id in pick_order(ids) call work_one(id) until # no claim is "to_do". Then print the summary of todo[...]["line"] for every claim.

Put it together: run() now does four things in order. It calls recover(), then plan(ids), then work_one for each id in pick_order(ids) until no claim is still to do, and finally it prints each claim’s line. Each earlier step only replaced part of the loop, so this is the final version.

整合起来：run() 现在按顺序做四件事。先调用 recover()，再调用 plan(ids)，然后对 pick_order(ids) 里的每个 id 调用 work_one，直到没有理赔还是待办，最后打印每份理赔的那一行。前面每一步只是替换了循环的一部分，所以这就是最终版本。

What I got wrong我当时想错了A claim failed partway and stayed “in progress” for ever. Worse, it silently blocked a later run, because the new run thought someone was still working on it. The fix was one rule: every claim must always end in a clear state. That is the recover() step and the two-tries rule.有一份理赔做到一半失败，从此一直停在“处理中”。更糟的是，它悄悄挡住了之后的运行，因为新的运行以为还有人在处理它。解决办法就一条规矩：每份理赔最后都必须处于明确的状态。这就是 recover() 和“两次机会”的规则。

Takeaways要点回顾

• Let the agent organise its own work: order the queue and write the summary.
• Add a cap and a one-claim option so trials cost little.
• Show a visible to-do list: to do, in progress, done, for handler.
• Use one fresh helper per claim, and take back only one line.
• Look things up by section, and record what was read.
• Retry once, then leave it for a human, and never decide twice.
• Every item must always end in a clear state.

• 让智能体自己组织工作：给队列排序，写出总结。
• 加上数量上限和单份理赔选项，试跑就花不了多少钱。
• 显示一张看得见的待办清单：待办、处理中、已完成、留给理赔员。
• 每份理赔一个新帮手，只收回一行话。
• 按章节查资料，并记录读了什么。
• 重试一次，再不行就留给人，而且绝不决定两次。
• 每个事项最终都必须处于明确的状态。
