Pausing and working in parallel · Lesson 2暂停与并行 · 第 2 课

Swarms of agents in parallel多个智能体并行

Work many claims at once with a dispatcher, a cap on how many agents run together, and retries · ~25 min · concept with one runnable idea用调度器、并行上限和重试，同时处理很多份理赔 · 约 25 分钟 · 概念课，附一个可动手的做法

The story故事

After a long weekend, Kaya Travel Cover has 25 claims waiting. The agent takes about 30 seconds on each, so one after another that is over twelve minutes, and Auntie Siew’s phone keeps ringing. Mei Ling wants them all worked at the same time. But she also remembers the last time she sent too much at once, so she builds a small dispatcher that is careful about how many agents it lets loose.

长周末过后，Kaya Travel Cover 积压了 25 份理赔。智能体处理一份大约要 30 秒，一份接一份做下来要十几分钟，Siew 阿姨的电话响个不停。Mei Ling 想让它们同时处理。但她也记得上次一下子发太多出去的教训，所以她做了一个小调度器，对放出多少个智能体很谨慎。

Step 1 · A dispatcher made of plain code第 1 步 · 用普通代码做调度器

Learn先学

A dispatcher is the person at the front desk who hands each claim to a free handler. It does not need to be clever, so it uses no model at all. It lists the claims and starts one piece of work for each. Plain code is free, instant and does the same thing every time. In Python, asyncio lets many waits (like “waiting for the model”) overlap instead of queueing.

调度器就像前台那位把每份理赔交给空闲理赔员的人。它不需要聪明，所以完全不用模型。它列出理赔，给每一份开一个任务。普通代码免费、即时，而且每次做的事都一样。在 Python 里，asyncio 能让很多次等待（比如“等模型回答”）重叠进行，而不是排队。

import asyncio async def dispatch(claims, agent): # start one piece of work per claim, then wait for all of them results = await asyncio.gather(*(agent(c) for c in claims)) return dict(zip([c["id"] for c in claims], results))

Step 2 · Test it with stand-in agents first第 2 步 · 先用替身智能体测试

Learn先学

Do not test a dispatcher with the real agent: it is slow, it costs money and it can fail in ways that hide your own bugs. Use a stand-in that just sleeps for a moment and returns a fixed answer. Like a fire drill, where nobody is really on fire. When the dispatcher behaves with stand-ins, swap in the real agent.

不要用真智能体来测调度器：它又慢又花钱，还可能出错，把你自己代码里的毛病盖住。用一个替身，只睡一小会儿，再返回固定的答案。就像消防演习，没人真的着火。调度器用替身跑得正常了，再换上真的智能体。

import random async def stand_in(claim): await asyncio.sleep(random.uniform(0.5, 1.5)) # pretend to think return {"action": "approve", "payout": claim["amount"]} claims = [{"id": f"C-{i}", "amount": 100 * i} for i in range(1, 26)] print(asyncio.run(dispatch(claims, stand_in)))

Step 3 · Keep the dispatcher’s state第 3 步 · 记住调度器的状态

Learn先学

While 25 things run, you need to see which claims are running, which are done and which failed. So the dispatcher reports each change to a small record. It also catches an error inside each claim, so one bad claim becomes a “failed” line instead of crashing the whole batch. Like the queue board on the wall, which shows every ticket’s status at a glance.

25 件事同时在跑时，你得看得出哪些在跑、哪些做完了、哪些失败了。所以调度器把每次变化报给一份小记录。它还在每份理赔内部接住错误，让一份有问题的理赔变成一行“失败”，而不是把整批搞崩。就像墙上的叫号板，每张号码的状态一眼就能看到。

async def run_one(claim, agent, on_change): on_change(claim["id"], "running") try: result = await agent(claim) except Exception: on_change(claim["id"], "failed") # one bad claim stays one bad claim return None on_change(claim["id"], "done") return result async def dispatch(claims, agent, on_change): results = await asyncio.gather(*(run_one(c, agent, on_change) for c in claims)) return dict(zip([c["id"] for c in claims], results)) state = {} def on_change(claim_id, status): state[claim_id] = status

Step 4 · Put a cap on the swarm第 4 步 · 给智能体群设个上限

Learn先学

Starting all 25 at once is how you meet the model provider’s rate limit, a ceiling on how many requests you may send per minute. A cap says “at most N agents at the same time”; the rest wait their turn. Python’s asyncio.Semaphore is exactly that: N tickets at the door. Keep N between 1 and 25.

一次放出 25 个，正是撞上模型供应商速率限制的办法：它规定你每分钟最多能发多少个请求。上限的意思是“同一时间最多 N 个智能体”，其余的排队等。Python 的 asyncio.Semaphore 就是这个：门口只有 N 张入场券。N 取 1 到 25 之间。

async def run_one(claim, agent, on_change, gate): async with gate: # wait here until a ticket is free on_change(claim["id"], "running") try: result = await agent(claim) except Exception: on_change(claim["id"], "failed") return None on_change(claim["id"], "done") return result async def dispatch(claims, agent, on_change, cap=3): cap = max(1, min(25, cap)) gate = asyncio.Semaphore(cap) for c in claims: on_change(c["id"], "waiting") results = await asyncio.gather(*(run_one(c, agent, on_change, gate) for c in claims)) return dict(zip([c["id"] for c in claims], results))

Step 5 · Retries: wait or go back第 5 步 · 重试：等一等，还是退回去

Learn先学

Not every error means the same. A rate limit or a timeout only means “not now”: wait a little and ask again, and it is still the same attempt, not a strike against the claim. Any other failure is a real problem, so the claim goes back once. If it fails a second time, leave it for a handler and move on. Like a queue ticket: if the counter is busy you wait, but a torn form is sent back once, then to a person.

不是所有错误都是一回事。速率限制或超时只是说“现在不行”：等一会儿再问，这仍是同一次尝试，不算这份理赔的一次失败。其他任何失败都是真问题，所以这份理赔退回去一次。第二次还失败，就留给理赔员，继续往下做。就像排号：柜台忙你就等，但撕破的表格会退回一次，再不行就交给人。

class RateLimited(Exception): pass # map your provider's rate-limit error to this class TimedOut(Exception): pass # and its timeout error to this WAIT_SECONDS = 2 async def attempt(claim, agent): failures = 0 while True: try: return await agent(claim) except (RateLimited, TimedOut): await asyncio.sleep(WAIT_SECONDS) # same attempt, just later except Exception: failures += 1 if failures == 2: # second real failure: give up raise # in run_one, one line changes: result = await attempt(claim, agent) # A "failed" claim is left for a handler. The rest carry on.

Which way should each error go? Sort them.

每种错误该走哪条路？来分一分。

Step 6 · Measure the time, and read the result from records第 6 步 · 量一量时间，结果从记录里读

Learn先学

Run the same 25 claims with a cap of 3, then 10, then 25, and time each run. In order, the queue took over ten minutes; with the whole queue in parallel it takes about as long as the slowest single claim. The cost per claim does not change: you pay for the same work, only sooner. The summary is a count over state, with no model writing it, so it can never disagree with what happened.

把同样的 25 份理赔，分别用上限 3、10、25 各跑一遍，并计时。按顺序做要十分钟以上；整队并行时，用时差不多等于最慢的那一份理赔。每份理赔的成本不变：做的是同样的活，只是更早做完。总结就是对 state 的一次计数，不用模型来写，所以它绝不会和实际发生的事不一致。

import time from collections import Counter for cap in (3, 10, 25): state.clear() start = time.perf_counter() asyncio.run(dispatch(claims, stand_in, on_change, cap)) print(cap, "agents:", round(time.perf_counter() - start, 1), "seconds", dict(Counter(state.values())))
What I got wrong我当时想错了I fanned out all 25 at once and hit the provider’s rate limit straight away. Half the claims failed, and it was not my code’s fault. A cap and a wait-and-retry rule fixed it.我一口气把 25 个全放出去，立刻撞上了供应商的速率限制。一半的理赔失败了，而这不是我代码的错。加上上限和“等一等再试”的规则就好了。

Now make it yours现在把它变成你的

Back at the shophouse回到店屋On Monday morning the queue-number machine spits out tickets faster than anyone can read them. Auntie Siew used to hand them out one by one; now three handlers’ worth of agents work at once, and the board on the wall fills with green. One claim stays red. “That one is for Aisha,” says Mei Ling, and the rest of the morning goes on without it.星期一早上，取号机吐号码的速度比谁都读得快。Siew 阿姨以前是一张一张地派；现在三个理赔员份量的智能体同时在干，墙上的叫号板一片绿。只有一份还是红的。“那份留给 Aisha。”Mei Ling 说，其余的上午照常进行。

Takeaways要点回顾

• Use plain code for dispatch: it is free, quick and predictable.
• Test the dispatcher with stand-in agents before the real one.
• Keep the dispatcher’s state so you can see who is waiting, running, done or failed.
• Cap concurrency; the first limit you hit is the provider’s rate limit, not your code.
• A retry after a rate limit or timeout is the same attempt; another failure goes back once, then to a handler.
• One bad claim never stops the rest.
• Going parallel cuts the time a lot and leaves the cost per claim unchanged.

• 调度用普通代码：免费、快、可预测。
• 先用替身智能体测调度器，再换真的。
• 记住调度器的状态，这样看得出谁在等、在跑、已完成或已失败。
• 给并行设上限；最先撞上的是供应商的速率限制，不是你的代码。
• 速率限制或超时之后的重试是同一次尝试；其他失败退回一次，再不行就交给理赔员。
• 一份有问题的理赔绝不拖住其余的。
• 并行能大幅缩短时间，每份理赔的成本不变。
