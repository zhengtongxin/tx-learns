Step 1 · The retriever: search, then take the top few第 1 步 · 检索器：搜索，取最前面几条

Learn先学

The store already knows how to find close chunks. A retriever is just a thin wrapper that hands back the top few for a question. You call it with .invoke(). The model object you meet next has the same .invoke(). LangChain mostly gives every piece one common shape, so pieces snap together.

向量库本来就会找相近的块。检索器只是薄薄的一层包装，针对一个问题返回最靠前的几块。你用 .invoke() 来调用它。下一步见到的模型对象也有同样的 .invoke()。LangChain 大多让每个零件都有统一的形状，所以零件很好拼。

from langchain_chroma import Chroma from langchain_huggingface import HuggingFaceEmbeddings embedder = HuggingFaceEmbeddings(model_name="sentence-transformers/all-MiniLM-L6-v2") # same one as when building store = Chroma(persist_directory="council_db", embedding_function=embedder) retriever = store.as_retriever(search_kwargs={"k": 4}) # top 4 similar chunks found = retriever.invoke("Who fixes a stuck lift?") for chunk in found: print(chunk.metadata["source"])

Step 2 · The prompt with one rule, and temperature 0第 2 步 · 只有一条规则的提示词，和 temperature 0

Learn先学

The prompt has two jobs. It holds a slot for the found chunks. And it carries the rule: answer from this context, and say "I don't know" if it is not there. Without that rule the model falls back on guessing. Temperature is how adventurous the next-word pick is: at 0 the model always picks the most likely word. For answering facts, set it to 0.

提示词有两个任务。一是留一个位置放找到的块。二是带上规则：照这些内容回答，不在里面就说“我不知道”。没有这条规则，模型就会退回去瞎猜。temperature 是选下一个词时有多“大胆”：设成 0，模型每次都选最可能的那个词。回答事实时，把它设成 0。

from langchain_openai import ChatOpenAI TEMPLATE = """You help residents with questions about the town council. Answer using only the context below. If the answer is not in the context, say you do not know. Context: {context}""" llm = ChatOpenAI(model="gpt-4.1-mini", temperature=0)

Step 3 · The whole chain in a handful of lines第 3 步 · 整条链只要几行

Learn先学

Now join the parts. Retrieve for the question, paste the chunks into the template, add the chat history and the new question, and invoke the model. That is "search, paste, answer". Hand the function to a Gradio chat page and you have a council chatbot. The history is passed whole, so the model can still read earlier turns.

现在把几个零件接起来。针对问题检索，把块贴进模板，加上聊天记录和新问题，然后调用模型。这就是“搜索、粘贴、回答”。把这个函数交给 Gradio 的聊天页面，一个理事会聊天机器人就有了。聊天记录是整段传进去的，所以模型还能读到前面的对话。

# pip install gradio: a small library that makes a chat page; open the link it prints import gradio as gr def answer(question, history): chunks = retriever.invoke(question) context = "\n\n".join(c.page_content for c in chunks) messages = [("system", TEMPLATE.format(context=context))] messages += [(m["role"], m["content"]) for m in history] messages.append(("user", question)) return llm.invoke(messages).content gr.ChatInterface(answer, type="messages").launch()

Step 4 · Where it still breaks: follow-up questions第 4 步 · 它还会坏在哪：追问

Learn先学

Retrieval only sees the latest question. Ask "Who is the lift officer?" and it works. Then ask "And what about his manager?". The word "his" means nothing to the store, so it fetches nothing useful. The history helps the model but not the search. The fix, rewriting the question before searching, comes in the project lesson.

检索只看最新的那个问题。问“电梯负责人是谁？”没问题。接着问“那他的上司呢？”，“他”对向量库毫无意义，所以什么有用的也检索不到。聊天记录能帮到模型，却帮不到搜索。解法是在搜索之前改写问题，会在项目那一课里做。

answer("Who is the lift officer?", []) # good: finds his page answer("And what about his manager?", history) # search text is just "And what about his manager?" # -> chunks about managers in general, or none that fit
What I got wrong我搞错的地方I believed RAG needed a big framework. The framework only saves a few lines. The idea is "search, paste, answer", and I could write it with no framework at all.我以为 RAG 需要一个很大的框架。其实框架只省几行代码。真正的想法是“搜索、粘贴、回答”，不用框架我也能写出来。

Common errors常见报错

• chromadb ... Embedding dimension 1536 does not match collection dimensionality 384. You embedded with a different model than the one that built the store. Use the same embedder for both, or delete the store folder and rebuild.
• The chat says "I do not know" for a question the files answer. Retrieval found the wrong chunks. Print the chunks first and raise k or fix the chunking.
• OSError: Cannot find empty port in range: 7860-7860. An older screen is still running. Stop the old cell (or restart the kernel), or pass server_port=7861.

• Embedding dimension 1536 does not match collection dimensionality 384：建库和查询用了不同的嵌入模型。两边用同一个，或者删掉库文件夹重建。
• 文件里明明有答案，聊天却说“不知道”：检索拿错了片段。先打印片段，再调大 k 或改切块。
• OSError: Cannot find empty port in range: 7860-7860：上一个界面还在运行。停掉旧单元格（或重启内核），或者传入 server_port=7861。

Takeaways要点回顾

• A retrieval chain is a retriever, a prompt and a model.
• Retrievers and models both use .invoke(), so they snap together.
• The prompt must say: answer from the context, otherwise say you do not know.
• Use temperature 0 when answering facts.
• Follow-up questions are the weak spot, because search sees only the latest question.
• The idea is search, paste, answer. A framework only saves lines.

• 检索链就是检索器、提示词和模型。
• 检索器和模型都用 .invoke()，所以很好拼接。
• 提示词必须写明：照内容回答，没有就说不知道。
• 回答事实时用 temperature 0。
• 追问是弱点，因为搜索只看最新的问题。
• 核心是搜索、粘贴、回答。框架只是省几行代码。

Recap小结

1. Retrieve the closest chunks, put them in the prompt, and let the model answer from them.
2. Show the sources, so a resident can check the answer.
3. When an answer is wrong, look at the retrieved chunks before changing the prompt.

1. 取出最近的块，放进提示里，让模型照着回答。
2. 把来源显示出来，居民就能自己核对。
3. 答案不对时，先看取回的块，再去改提示。
