# TX Learns: rules for Claude

Bilingual (EN/中文) interactive learning site. Static HTML/CSS/JS, no build step. Deployed on Vercel.

## Layout

- **Three parts.** `index.html` is a plain landing page with two parallel choices: "Pick a track" (`tracks.html`) and "Study your own material" (`study/index.html`); it has no menu or About/How it works links, and each choice is a compact card with a preview (the track names and levels read from `tracks.js`; three short study steps (hand in, get quizzed, fix weak spots) and a one-line "free, stays on your device, no login"; the whole card is one link). `tracks.html` is the tracks home (what used to be the home page: start/continue button, top bar with About, How it works, Glossary; lessons and track pages link back to it). It has two levels: it first lists the subjects from `DOMAINS` (AI, project management) and a subject with several tracks opens its track list at `tracks.html#<id>` (`drawHub` in `assets/site.js`; a subject with one track links straight to it), and the landing card lists the subjects the same way. The study coach is subject-neutral in its wording: PMP is only one built-in exam outline, never what the tool is about. The study section (`study/`) is its own area with its own top bar ("Study coach", "About this site" = `study/about.html`, "How it works" = `study/how.html`); its pages set `data-area="study"` on `<html>` and the landing sets `data-area="landing"` (`assets/site.js` builds the top bar per area). `tracks.js` lists learning tracks (`window.TRACKS`). The tracks page's no-JavaScript track list (between `<!-- tracks:start -->` markers, each track with its one-line description) is written by `check-pages --fix` in `tracks.js` order.
- `about.html` the About page (who writes the site, how lessons are made, what the site records, where to report a mistake), linked from the top bar (next to "How it works"). If what the site records changes (`assets/site.js`), change that section too.
- `ecosystem.html` the "How it works" page: one system diagram, six layers left to right (input, notes, AI agents, GitHub, Vercel, readers) with the numbered lesson path. Agents are the focus: each has its own colour (`hue` in `AGENTS`), a trigger line (`on`) and live status in its box (yellow pulsing while a run is working, then green/orange/red for passed/flagged/failed; red only for a real failure), with a short purpose sentence and bilingual Runs/Output rows in one solid popup on hover (click pins it, Escape closes it); technical specs and raw run summaries stay out of agent popups, and run details remain in "What changed"; the plumbing stays grey. Telegram is a node in column 06 ("Telegram → me") and each agent box carries a paper plane: filled = it messages TX every run, hollow = only on a problem (`tg`/`tga` in `AGENTS`; keep true to the workflows' Telegram steps). The popup lives on `<body>`, outside the glass panels, so nothing paints over it, and there is only ever one. Agent details are not repeated anywhere else on desktop. The five numbered steps above the diagram light up their boxes and arrows (and dim the rest) on hover, focus or tap (`FS` map in the page script). The "What changed" section (`#changes`) opens with one slim status pill (`#attention-box`, no section of its own at the top of the page; "All clear" or "N items need attention", with a coloured dot) that opens, on click, the list of reports: one compact row per current report (a short badge, title, agent and age; "Needs you" rows start open, the rest open on click) holding the run state, actual problem excerpt, impact, owner, next step, safe source links and a "Fix now" button (opens the improver workflow's Run workflow form on GitHub; `now` input skips the 7-day wait; only people with write access can run it, no token on the site), with no intro paragraph; earlier reports stay in a separate disclosure. "Being handled automatically" needs a matching recheck or verified open repair PR, and "Recovered" needs a later passing check on the same scope; unrelated successes never clear a report. Missing, stale or partially available evidence is labelled unconfirmed, never healthy. Current unresolved reports also get a small hint and a link from the agent's compact popup. The original four sections follow, always fully open (nothing collapsed): 01 the system diagram, 02 "Guardrails": one chip per rule (all of them shown), grouped under four small labels (`GG`: before a merge, what agents may touch, after it goes live, secrets and alerts), one card style, one-line titles, with an icon (`GI` array, same order) and a short plain-language title; the one-line explanation shows in the shared popup on hover, focus or tap (`G` array, entries `[title, zh, number, unit, unit zh, line, line zh]`; the number and unit are not shown, so keep the line true to the workflows). Section 03 "Ideas to learn" shows the AI and engineering concepts used to build the site as title-only chips in four labelled groups (`CG` in the page script; a concept not listed there lands under "More") from `assets/build-concepts.js` (`window.BUILD_CONCEPTS`: `use` is the one-line description shown in the popup on hover, focus or tap, `status` `live` or `soon`; a click or tap on a chip only shows the popup, which holds the link to the concept's first lesson; `lessons` are published lessons whose file and titles `check-pages` verifies). When an agent gains a capability, add or update its card. Section 04 "What changed" (`#changes`) shows the health summary and the five latest agent runs from `api/status`; there is no hand-written site-updates list any more. Agents are always named "... agent". Phones get an ordered list where tapping an agent opens its details in place (one at a time). Keep the agent specs in its `AGENTS` array true to `.github/workflows/`. **Frozen:** in its first weeks this page was changed by more merges than any lesson while almost nobody read the site, so change it only to keep those specs true or to fix something broken; no new sections, restyling or polish unless TX asks for it by name. It reads `api/status` (`api/status.js`, public, no token): known agent state, time, run count, a short plain summary and narrowly validated same-repository GitHub report links. The `attention` response correlates recorded checks with the public quality issue, reader findings and verified repair PRs; no raw logs, branch names, credentials or arbitrary links are exposed. Status reads cache for one minute, supplementary evidence for ten minutes, with bounded requests/timeouts and explicit incomplete/unconfirmed output when evidence is missing.
- **Domains.** `tracks.js` also holds `window.DOMAINS` (id, icon, title, desc); each track names its domain with `domain:'<id>'` (the twenty AI tracks listed below are `ai`; `pmp` is the only track of `pm`, project management; `community` holds tracks the writer makes from learners' notes and shows only once it has one). The tracks page lists tracks grouped by domain (`drawHub` in `assets/site.js`). Inside a domain the tracks are not one numbered line: a track with `entry:{en,zh}` is an entry point ("No code", "Coding with AI", "Leading a team": pick by who you are) and is listed first under "Pick where you start"; the tracks with `bridge:true` (the skills tracks: Python basics to Data basics) are a "Skills toolbox: take what you need, in any order" group, listed second and not numbered; the rest are one path, numbered Step 1, 2, ... under "Then the engineering path, in order" (a domain with no entry points is one numbered path, unless all its tracks are `bridge:true`, as in the skills subject: then they are not numbered). What follows a track is named in `tracks.js`, never taken from the list order: `next:['<id>',...]` (later tracks of the same domain; none or `[]` where the path ends, as on a track the writer makes from a learner's notes) and an optional `go:{href,title}` link (PMP points at the study coach); the count check fails on a `next` that names no later track of the same domain. `tracks-index.js` (`window.TRACK_INDEX`: each track's topic count, published lesson files and titles) is written by `check-pages --fix` from every `lessons.js`, so the tracks page, the "What next" card and the study coach read one generated file instead of one request per track; it is a generated file like `sitemap.xml` (listed as such in `scripts/areas.json`, `review-triage.mjs`, `sync-branch.mjs`, `writer-batch.mjs`, `agent-context.mjs` and `daily-scan.mjs`). A new domain = one entry in `DOMAINS` plus its tracks after the existing ones; the level order check (`scripts/check-counts.mjs`) runs per domain. The no-JavaScript track list stays flat. The Topics menu (`byDomain`, `group` and `wire` in `assets/site.js`) lists subjects too, never every track in one flat list: a subject with several tracks is one row that opens to its tracks (folded on pages outside a track; open on a track's pages when it holds that track, with one box per track inside), and a subject with one track (PMP) is that track's own row at the same level; what was opened or folded is remembered (`learn-nav`).
- `study/` the study section: `study/index.html` the study coach tool, `study/how.html` "How it works", built like `ecosystem.html` (same styles, six numbered steps (the sixth, "Turn it into a track", has its own boxes: track notes, GitHub, new track) that light up the diagram, one system diagram of the six in-browser agents with hover/click popups and a phone list, Guardrails and Ideas chips; the agents' triggers and outputs in its `A` array must stay true to `coach/coach.js`; no live status, nothing collapsed) and `study/about.html` (purpose, privacy, limits, corrections), reached from the landing page. The tool lives in `coach/`. It runs entirely in the reader's browser: `coach/coach.js` (UI, reading PDF/PPTX/text, IndexedDB records, export/import, an "I guessed" mark (a lucky right answer counts as a miss) and "Change my answer", a wrong-question book (missed and guessed questions, redone shuffled, printable in full), and one flow: a step bar (`#flow`: Material, Goal, Model, then Practise, Progress, Track) shows one panel at a time (`go`/`applyView` in `coach/coach.js`, sections carry `data-v`), each step ends with a Continue button, and the first round starts by itself once the model has loaded; the coach card on Practise opens with a day ring (today's questions out of the daily goal), the streak of days in a row (`L.streak`, an empty today keeps yesterday's streak alive) and a 7-day strip (`L.week`), then names the gaps (`gapInfo`: weak, not tested, due, the passages missed most), `Fix my gaps` runs a gap round (`gapSlots`: missed passages first, slots carry a `chunk`) and a round ends with a coach's word (`coachNote`: how the round went by its score, and how many questions are left to today's goal), its gaps, a redo button and the next review; the wrong-question book sits inside Progress; and a "Turn it into a track" panel: the model writes the key ideas of up to 30 passages spread over all the material in its own words (stoppable, kept as it goes), the learner adds a topic and optional own words, ticks that they are their own words and become public, and a "Send to GitHub" button (the Track step of the bar, once there is material) opens GitHub's new-file page for `inbox/<topic>-<date>-<id>/notes.md` on the `notes` branch with the substance of what was studied, built in the browser (`Lg.digest`: the exam areas, the first line of each passage (cut to 80 characters) as its heading, the most frequent terms; the key ideas the model writes in its own words (heading "Key ideas from my material"), refused by `Lg.copied` if they repeat 8 words of the source; lines that name a link, a copyright or a course are dropped by `Lg.scrubLine`), the learner's own notes and two header lines filled in (never the uploaded files or their names, and no passage beyond its first line; the file name is not the default topic; the learner sees the whole text in a preview first, and one that is too long for a prefilled link is copied to the clipboard and pasted into the empty editor): `Track: new` (default; with `Subject: community`) or `Track: <id>` (one more lesson in an existing track, chosen from `tracks.js`); the owner presses Commit and the push starts the writer, anyone else gets a forked pull request, and no token or server is involved. No `TRACK` file is needed for these notes. Questions, options and explanations are generated in the language of the page (`pageLang()`, `Lg.prompt`'s `lang`; a cross-language excerpt is translated, and `Lg.inLang` rejects an answer in the wrong language), not the language of the material. On a first visit it opens on Material; with material loaded, on Practise. Such a pull request targets the data-only `notes` branch, not main, so auto-merge never touches it and the owner reads it before merging; merging it is what starts the writer, so treat the text as untrusted until then, and add the `TRACK` file when merging), `coach/logic.js` (chunking, matching passages to exam areas, plan and weak-spot maths, question parsing; no page, runs in node too). Rules of its logic, each covered by `scripts/test-coach.mjs`: an area is only ever asked from its own passages (an area no passage matches is marked "no material" and gets no questions; a passage that matches no area is practised under "Other", a tenth of a drill and never in a mini exam); a typed area's id comes from its name, not its line number, so its history stays with it; a question with an "all/none of the above" option is refused (one key only); with an exam goal about one question in five is a "choose two" question (`slot.multi`, only on the first try of a slot): the model writes `answers:[i,j]`, `parseQuestion(raw, true)` refuses anything but exactly two distinct keys or a stem that asks for "the one" answer, the item carries `m` (both keys, `L.keys`/`L.right`) and the reader taps two options and presses "Check my two" (all or nothing); a failed choose-two output falls back to a normal one-key question on the next try, and its second opinion (`parseVerifyMulti`) drops it only when the model clearly names a different pair; a question that repeats an earlier one from the same passage (this round or the last 30 in the bank; `L.similar`, 70% shared words (中文: character pairs) in the stem or the stem with its options) is dropped before the second opinion; every question gets a second opinion before it is shown (the model answers it from the passage without the key, and a clear disagreement drops the question: one more model call per question); an area is due for review after 1, 3, 7, 14, then 30 days as right answers in a row add up (`L.interval`); taking an answer back undoes exactly what it did to the passage's miss count; and a weak area of a ready-made outline lists this site's lessons on it (`lessons:{track,files}` in `coach/exams.js`, titles from `tracks-index.js`; the count check verifies the files are published), `coach/exams.js` (ready-made exam outlines, presets only: PMP, current weights People 33 / Process 41 / Business Environment 26 from July 2026, and the earlier 42 / 50 / 8; add an exam or outline version there). The tool itself is subject-neutral: the default goal is "understand the material" (one area per file), and the "exam" goal defaults to the reader's own exam, whose areas and weights they type (`Lg.parseAreas` in `coach/logic.js`: `Name, 30`, `Name 30%` or `Name | keywords | 30`); a ready-made outline is chosen from the same list and the tool page names none until then, `coach/worker.js` (runs the model off the main thread) and `coach/vendor/` (web-llm, pdf.js with cmaps, JSZip, copied unmodified; the version is in each file name, so they are cached for a year; see its `README.txt`). The model is an open one (Qwen3, Apache 2.0) downloaded from the model host only when the reader clicks the download button, so `connect-src` in `CSP` (`scripts/check-pages.mjs`) lists that host. No paid API, no server model, no login, no analytics: files, answers and records never leave the device and are not part of the reader signals above. Nothing loads the model until that click, so the agents' checks never download it. `scripts/test-coach.mjs <dir with t.pptx and t.pdf>` is its behaviour test (fake model, needs Playwright); run it after changing `coach/`. Area `study-coach` in `scripts/areas.json`.
- `glossary.html` the AI glossary and concept map; its terms live in `glossary.js` (`window.GLOSSARY` terms, `window.GLOSSARY_THEMES` themes). ### More about four agents

- The **Efficiency engineer agent** runs every six hours from `.github/workflows/optimizer.yml`. It measures the repository with `scripts/efficiency-report.mjs`, makes at most one focused source improvement per run, records before/after measurements, and opens one pull request. It never changes the merge guardrails, agent runners, lesson prose or project reference code; the existing copy check, backend review, UI check, auto-merge and live rollback still apply. Its status id is `optimizer`. **Code review (continuous):** `scripts/code-queue.mjs plan` (no AI) hands each run a batch of the site's own code it has not read yet: `api/`, `assets/` scripts and styles, `coach/` (not `vendor/`), `scripts/*.mjs` and the pages with their own logic (`PAGES` in the script); not lesson pages or their widget scripts, not `.github/`, not the five protected scripts. The first pass covers every file, one area (`scripts/areas.json`) and about 120 KB per run; after that a file comes back only when it changed since it was read (`signals/code-review.json` on `agent-status` keeps each file's hash at reading time and after the agent's own edit, ignoring `?v=` hashes). While files wait, the run is a code review of that batch (real defects only, each with the input that went wrong, a test case where a test exists; nothing found means no change). When none wait, Claude does not run (the status says so), except on the first run of Monday (UTC) and on a manual run, when it is the usual efficiency run (`mode` output of the `queue` step: `review`, `efficiency` or `idle`). `code-queue.mjs done` remembers the batch after Claude finishes; a change that fails the guard counts a try and after two the batch is let go; a run where Claude could not run remembers nothing. To have everything read again, delete `signals/code-review.json` on `agent-status`; to add a file or folder to the scope, edit `DIRS` or `PAGES` in the script. `node scripts/code-queue.mjs list` prints the scope. **Logic check (daily):** a code review asks whether one file does what it says; the logic check asks whether the parts of the site agree with each other and whether the rules still fit what really happens. The 12:23 UTC run of every day (and a manual run with the `logic` input: `today` or a flow name) is that check, whatever code waits (the next run reads it): `scripts/logic-brief.mjs` (no AI) picks one flow in rotation (`FLOWS`: `path` the learning path, `coach` the study coach, `signals` the agents' rule numbers against their own data on `agent-status`, `claims` what the site's pages say about its behaviour against the code) and writes the question, the files to read in full and the facts it gathered (the track graph with what a script noticed, the rule numbers, the intern's score spread, what the improvement agent tried, the daily scan's reader and rework lines, the agents' calls of the last 7 days). Claude walks the flow as one concrete case, and a finding counts only as "this part does X, that part does Y, so this case comes out wrong"; it fixes at most one, at the root, with a test case where the flow has a test, under the same guard as every run (six source files, no protected file, the four checks). It never changes a rule number because the data moved a little, never undoes a decision this file records as TX's, and never edits `ecosystem.html`; what needs `.github/`, this file or TX's decision goes under "Needs TX" in its summary, and the first lines of that reach TX through the status line and the daily digest. Finding nothing is a normal result and opens no pull request. The `mode` output is then `logic` and the pull request title starts with "Logic:". A new flow = a new entry in `FLOWS` (`node scripts/logic-brief.mjs list` prints them; `--flow <id> --offline` builds a brief without the network).

- The **Improvement engineer agent** (`.github/workflows/improver.yml`, status id `improver`) closes the loop on what other agents found. Four times a day `scripts/signals.mjs brief` (no AI) picks ONE item: a page named in the open `Quality check` issue, else the lesson the intern scored lowest below 7 (`signals/reader.json` on `agent-status`, written by the reader workflow; the intern's scores bunch at 6 to 7, so only "could not follow a step" is worth a fix). Only then Claude (Sonnet, at most 30 turns) fixes just that in just the files it was given (a guard step fails the run if it touched any other file) and opens one `improver/` PR; at most one is open at a time and the same item waits 7 days (`signals/improver.json`); a lesson the intern flagged gets ONE fix and then rests for 30 days, whatever the intern scores it afterwards: the second opinion is real readers' "Was this lesson clear?" (a `readers` idea), never re-scoring a lesson until it passes. Nothing to fix means no AI run. **Scouting (every role looks for improvements itself):** when neither a quality problem nor a low score exists, `scripts/scout.mjs plan` (no AI) picks the role that scouted longest ago (content creator, backend engineer, frontend engineer, cybersecurity engineer, product engineer, translator, interface translator (`assets/site.js` only: its {en, zh} pairs against a fixed term list in its `ask`; change the list there when a term changes), intern; their lenses live in `ROLES`; the translator compares a lesson's 中文 with its English for meaning and glossary terms) and ONE file of its area that is new or changed since it was last scouted (or older than 45 days); Haiku (read-only, 10 turns) suggests at most 2 ideas, and `scout.mjs add` stores them in `signals/ideas.json` on `agent-status` (deduped against pending and done ideas, at most 12 pending, expire after 30 days). `signals.mjs pick` takes the best idea when nothing more urgent exists (an idea with role `readers`, left by the daily scan for a lesson real readers marked "not quite clear", has priority 1), so ideas go through the same one-PR path and checks. No scout runs while a reported problem comes first, while 5 or more ideas wait, or when every file is unchanged; shared site scripts are never scouted. A new role = a new entry in `ROLES`. Same checks as every PR, including the scope guard. It never edits workflows, scripts, rules or project code.

- The **Industry consultant agent** (`.github/workflows/news.yml`, status id `news`) keeps lessons current. Daily `scripts/news.mjs plan` (no AI) reads the first-party feeds in `scripts/news-sources.json` (official blogs and release notes; add or drop a feed there), keeps items from the last 3 days it has not seen (`signals/news.json` on `agent-status`), and matches each to the lessons that mention the topic with the local search; an item that names a model id the lessons use in code (`modelsInLessons` in `scripts/lib.mjs`) is always matched to those lessons, so a retired model is caught the day it is announced. Only when something matches does Haiku run (no tools, 2 turns, at most 10 items) and judge whether a fact a lesson teaches is now out of date; `news.mjs add` keeps at most 3 ideas (role `news`, with a `source` link; the file must be one of the matched lessons) in `signals/ideas.json`, so the improvement engineer agent handles them like any other idea (one small PR, scope guard, auto-merge). It changes no site file itself, never proposes new lessons or tracks (those come from TX's notes) and sends Telegram only on failure. It does nothing while 8 or more ideas wait.
- **Areas and the scope guard.** `scripts/areas.json` is the map of the site's independent parts: one area per learning track (read from `tracks.js`, packages included), plus `site-shell`, `ecosystem`, `glossary`, `agents` and `rules`; generated files (sitemap, `vercel.json`, search index) belong to every area. Keep a change inside one area where you can, and one pull request does one thing. `scripts/scope-guard.mjs` + `scope-guard.yml` (the **Change control agent**, status id `scope-guard`) reads each PR's diff without the request, says what it does, then compares that with the PR title and description; path rules come first (a `writer/` or `reader/` branch may change one track only (a `writer/` branch that creates a new track may also edit `tracks.js`), `optimizer/` two areas, `improver/` one). A mismatch sets `Scope guard` and the required `Reviewer` status red with a plain reason, so auto-merge waits and tells TX once; no change to auto-merge was needed. It labels the PR `area:<id>`. Label `scope-ok` lets one through. So write a PR description that says everything the PR does, in plain words.

Actions in every workflow are pinned to a full commit SHA with the version as a comment (`uses: actions/checkout@<sha> # v4`), never a bare tag.

Telegram: one digest a day at 8 PM. Instant messages only for failures, a quality-check problem, a rollback, a stuck PR (from auto-merge), and the weekly review.
Pushes and PRs made with the workflow token start no workflows, so an agent that pushes starts `copy-check.yml` on that branch itself (`gh workflow run`), the reader starts the reviewer, and the writer hands notes over with `gh workflow run writer.yml --ref main`. The writer, improvement and efficiency agents open their pull request with `MERGE_TOKEN` when it is set (the workflow token falls back otherwise), because the checks of a pull request opened by a bot with the workflow token wait for someone to approve the run, and the required `copy-check` never turns green; with `MERGE_TOKEN` the pull request starts its own checks and the by-hand starts are skipped. `review.yml` ignores the opening of a `writer/` pull request: there the reader starts it, after its own fixes.

Claude auth: the writer, reviewer, reader, UI check and recall agents use TX's Claude subscription through the `CLAUDE_CODE_OAUTH_TOKEN` secret (made with `claude setup-token`). `ANTHROPIC_API_KEY` is only a fallback when that secret is missing. Subscription runs share TX's plan usage limits. Models are pinned to keep usage low: the writer and reviewer use `sonnet`, the reader, UI check and recall use `haiku` (`--model` on each `claude -p`). Interactive Claude sessions use the same plan. Prompt caching is automatic in `claude -p` (system prompt, tools and the growing conversation are cached within a run); every `claude -p` also passes `--exclude-dynamic-system-prompt-sections` so the cached start is the same between runs. The reader reads at most 6 lessons per run.

## Typography

Type is Apple-style: the system sans (-apple-system / SF Pro on Apple devices, self-hosted Inter in `assets/fonts/` elsewhere, PingFang SC for 中文), no serif and no italics. Headings get contrast from weight, size and tight tracking. An `<em>` inside `h1`/`h2` is upright amber. Rules are at the end of `assets/site.css`. **One size scale on every page**: page titles (`.mega`, `.hero h1`) `clamp(2.3rem,6.5vw,4rem)`, `h2` `clamp(1.6rem,3.4vw,2.2rem)`, `h3` 1.15rem, body 1.04rem, subtitle `.sub` `clamp(1.05rem,2.2vw,1.25rem)`, small text 13.5px. Pages (`about`, `ecosystem`, `glossary`, home) must not set their own `font-size` on titles, headings or body paragraphs; make a page compact with spacing instead. Small UI parts (chips, popups, badges, card titles) may keep a smaller size.

## Rules

0. **One request, one pull request.** Whatever TX asks for in one message (a track of lessons, a fix plus its follow-ups, a pipeline change) lands in ONE pull request, never a pull request per lesson or per step. Parallel pull requests all rewrite the same generated files (sitemap, lesson lists, `?v=` hashes), clash with each other and merge one at a time. Agents and threads that do several things for one request build them in one branch and open one pull request whose description says everything it does. The writer already follows this (`writer.yml`: parallel jobs, one pull request).

1. **Write every lesson to `STYLE.md`.** Lesson titles are short noun phrases (2 to 5 words, about 4 to 10 characters in 中文), never sentences, no colons, no `Project:` prefix. Read it before writing or editing a lesson. Do not wait to be reminded.
2. **Source-neutral, always.** No platform, program, instructor names, no "course"/课程, no week/day numbering, no copied examples. Run `node scripts/check-copy.mjs`, `node scripts/check-counts.mjs` and `node scripts/check-pages.mjs` before every commit; all must pass. Never type a topic or lesson count into a page.
3. **Branches.** Every change is a pull request into `main` (Vercel builds its own preview; that is the test). `main` is the live site. Open it as a draft while you are still pushing to it and mark it ready once: the backend review reads a draft only when it is marked ready, and auto-merge skips drafts. Auto-merge merges it once the copy check and the reviewer agent's ✅ are green (the UI check and live check run after the merge); TX only merges PRs that change auto-merge itself (`auto-merge.yml`, `scripts/auto-merge.mjs`, the ruleset) or that auto-merge reports as stuck. Workflow-changing PRs auto-merge too, through the `MERGE_TOKEN` secret. There is no `test` branch and no release step. If a merge breaks the live site, the live check agent rolls it back.
4. **Agents notify before changing.** An agent never pushes straight to `main`. Every change goes through its one pull request and its required checks; auto-merge merges it when they are green. Agents push directly only to the `agent-status` run log, the `notes` branch (notes only) and, as fixes, to a lesson's own `writer/` draft branch before TX merges it. Agents merge only through auto-merge (all required checks green) and a `Rollback:` pull request that puts main back to the reviewed state before a merge that broke the live site.
5. Keep English and 中文 in step: every `.en` has a matching `.zh`.
6. No build tools or frameworks. Plain files that open from disk.

## Moving or renaming a page

A published URL is never deleted or left to 404. To move or rename a page, a lesson file or a track folder: move the file, add `{"from":"/old/path.html","to":"/new/path.html"}` to `scripts/redirects.json` (point straight at the final page, no chains), update `lessons.js`, then run `node scripts/check-pages.mjs --fix`. That regenerates the permanent redirects in `vercel.json`, the sitemap, canonical links and JSON-LD. The page check compares `sitemap.xml` with main and fails when a URL that was published no longer opens and has no redirect. Renaming only a title (as when the track became "AI Agentic") moves no URL and needs no redirect. Do not link `.md` files: they are not deployed.

## Adding a lesson

Easiest: drop notes in `inbox/<concept>/` on the `notes` branch and let the writer agent draft it (see `inbox/README.md`). Notes for a track other than `agentic-ai` carry a one-line `TRACK` file with the track id. By hand:

1. Copy `agentic-ai/_template.html` to `<track>/NN-slug.html` (next free number in that track).
2. Write it to `STYLE.md`, with the tag `<Topic> · Lesson N`.
2b. Lesson widget code (`TX2.game`, `TX2.predict`, ...) goes in `<track>/js/NN-slug.js`, loaded by a script tag for `js/NN-slug.js` after `assets/teach.js` at the end of the page, never inline; `--fix` adds the `?v=` hash.
3. Add `file:'NN-slug.html'` to its item in `<track>/lessons.js` (or add the item under the right topic), then run `node scripts/check-pages.mjs --fix` (it also stamps the lesson's updated date).
4. Fill in the `<title>`, description and `og:` tags, run `node scripts/check-copy.mjs`, `node scripts/check-counts.mjs` and `node scripts/check-pages.mjs`, then open the page in a browser and click every widget.
