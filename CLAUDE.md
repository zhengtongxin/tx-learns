# TX Learns: rules for Claude

Bilingual (EN/中文) interactive learning site. Static HTML/CSS/JS, no build step. Deployed on Vercel.

## Layout

- `index.html` home page; `tracks.js` lists learning tracks (`window.TRACKS`). The home page's no-JavaScript track list (between `<!-- tracks:start -->` markers, each track with its one-line description) is written by `check-pages --fix` in `tracks.js` order.
- `about.html` the About page (who writes the site, how lessons are made, what the site records, where to report a mistake), linked from the top bar (next to "How it works"). If what the site records changes (`assets/site.js`), change that section too.
- `ecosystem.html` the "How it works" page: one system diagram, six layers left to right (input, notes, AI agents, GitHub, Vercel, readers) with the numbered lesson path. Agents are the focus: each has its own colour (`hue` in `AGENTS`), a trigger line (`on`) and live status in its box (yellow pulsing while a run is working, then green/orange/red for passed/flagged/failed; red only for a real failure), with a short purpose sentence and bilingual Runs/Output rows in one solid popup on hover (click pins it, Escape closes it); technical specs and raw run summaries stay out of agent popups, and run details remain in "What changed"; the plumbing stays grey. Telegram is a node in column 06 ("Telegram → me") and each agent box carries a paper plane: filled = it messages TX every run, hollow = only on a problem (`tg`/`tga` in `AGENTS`; keep true to the workflows' Telegram steps). The popup lives on `<body>`, outside the glass panels, so nothing paints over it, and there is only ever one. Agent details are not repeated anywhere else on desktop. The five numbered steps above the diagram light up their boxes and arrows (and dim the rest) on hover, focus or tap (`FS` map in the page script). The "What changed" section (`#changes`) opens with one slim status pill (`#attention-box`, no section of its own at the top of the page) ("All clear" or "N items need attention", with a coloured dot; the heading is visually hidden) that opens, on click, the list of reports: one compact row per current report (a short badge, title, agent and age; "Needs you" rows start open, the rest open on click) holding the run state, actual problem excerpt, impact, owner, next step and safe source links, with no intro paragraph; earlier reports stay in a separate disclosure. "Being handled automatically" needs a matching recheck or verified open repair PR, and "Recovered" needs a later passing check on the same scope; unrelated successes never clear a report. Missing, stale or partially available evidence is labelled unconfirmed, never healthy. Current unresolved reports also get a small hint and a link from the agent's compact popup. The original four sections follow, always fully open (nothing collapsed): 01 the system diagram, 02 "Guardrails": one chip per rule (all of them shown), grouped under four small labels (`GG`: before a merge, what agents may touch, after it goes live, secrets and alerts), one card style, one-line titles, with an icon (`GI` array, same order) and a short plain-language title; the one-line explanation shows in the shared popup on hover, focus or tap (`G` array, entries `[title, zh, number, unit, unit zh, line, line zh]`; the number and unit are not shown, so keep the line true to the workflows). Section 03 "Ideas to learn" shows the AI and engineering concepts used to build the site as title-only chips in four labelled groups (`CG` in the page script; a concept not listed there lands under "More") from `assets/build-concepts.js` (`window.BUILD_CONCEPTS`: `use` is the one-line description shown in the popup on hover, focus or tap, `status` `live` or `soon`; a click or tap on a chip only shows the popup, which holds the link to the concept's first lesson; `lessons` are published lessons whose file and titles `check-pages` verifies). When an agent gains a capability, add or update its card. Section 04 "What changed" (`#changes`) shows the health summary and the five latest agent runs from `api/status`; there is no hand-written site-updates list any more. Agents are always named "... agent". Phones get an ordered list where tapping an agent opens its details in place (one at a time). Keep the agent specs in its `AGENTS` array true to `.github/workflows/`. It reads `api/status` (`api/status.js`, public, no token): known agent state, time, run count, a short plain summary and narrowly validated same-repository GitHub report links. The `attention` response correlates recorded checks with the public quality issue, reader findings and verified repair PRs; no raw logs, branch names, credentials or arbitrary links are exposed. Status reads cache for one minute, supplementary evidence for ten minutes, with bounded requests/timeouts and explicit incomplete/unconfirmed output when evidence is missing.
- `glossary.html` the AI glossary and concept map; its terms live in `glossary.js` (`window.GLOSSARY` terms, `window.GLOSSARY_THEMES` themes). Within each theme, terms are listed most important first: the concept map shows them in that order in seven boxes of the same size: each box shows its first 10 terms (`TOP` in the page script) and, when it has more, a "Show all" button for the rest, and every box takes the height of the tallest (`--box-h`, set by the script); the A to Z list sorts them itself. Each term names the track and a published lesson file where it is first taught (that file must exist). Linked from the top bar (`assets/site.js`) and the home page buttons.
- The old `changelog.html` page is gone and redirects to the "What changed" section of `ecosystem.html` (`#changes`); the hand-written changelog was removed. A lesson can also show "Last changed: ..." from an optional `changed:{en,zh}` in `<track>/prereqs.js`, rendered by `renderMeta` in `assets/site.js`. The last lesson of each topic and the end of each track page show a "What next" card (`whatNext` in `assets/site.js`), computed from `lessons.js` and `tracks.js` order (the next lesson, or the next track once a track is finished).
- `inbox/` raw notes for the writer agent. New notes go to `inbox/<concept>/` on the data-only `notes` branch (create it from main if it is missing; never merged, never deployed: `vercel.json`); `inbox/` is never deployed from main either (`.vercelignore`).
- `<track>/prereqs.js` and `<track>/projects.js` are the editable source of the optional "Before you start" and project-card data per lesson (`window.PREREQ`, `window.PROJECTS`). Pages never load them: `node scripts/check-pages.mjs --fix` copies each lesson's own entry, plus the file list of its package folder, into a `<script type="application/json" id="lesson-data">` block in that lesson (no extra requests; a stale block fails the page check), and `assets/site.js` renders from it. After editing either file, run `--fix`. the home page has one primary button (start, or continue where you left off, with a "Next up" line), the track list (no "Try one" question: TX removed it): no stats row, no resume panel, no second "browse" button, no recent-lessons list, no export/import/reset buttons and no search box on purpose. Vanity numbers (topic/lesson totals, languages, run counts) are not shown; keep new pages free of them and track pages a before/after note from `tracks.js`. `packages/<track>/<NN-slug>/` holds each project's `README.txt`, dependency file, `env.example`, `starter/` and `final/` code: served from the site (so links work), `*.md` is not deployed, hence `.txt`. Every file a card lists in `pkg.files` must exist (the live check fails on a missing file).
- `ai-leader/`, `agentic-ai/`, `ai-engineer/`, `ai-production/` and `ai-fde/` are tracks (one folder each, listed in `tracks.js`; the folder name is the track id). Lessons are succinct and sleek (see `STYLE.md`): key point first, about 600 to 1,000 words of prose per language, story optional (1 to 3 sentences, Singapore-set, on the point), no required track-wide story or cast; any `STORY.md` is only a list of names to reuse. Scripts and agents read every track from `tracks.js`; numbering (`NN-slug.html`, `Lesson N`) is per track. `lessons.js` (`window.TRACK`) groups lessons into concept topics; a lesson with `file` is published, one without is "coming soon". **Order is easiest first.** Each track in `tracks.js` and each topic in `lessons.js` has `level` 1 (beginner), 2 (intermediate) or 3 (advanced), never decreasing down the list (the count check fails otherwise); the home page numbers the tracks as a path and topics show their level. New topics go where their difficulty fits; the file number `NN` is only the next free one.
- `<track>/js/NN-slug.js` each lesson's own widget script (loaded by `<script src="js/NN-slug.js?v=...">` at the end of the page, same place and timing as before), so it caches and the `?v=` hash and immutable cache header come from `scripts/check-pages.mjs --fix`; write new lesson scripts there, not inline. The `{en,zh}` parity check reads these files too.
- `agentic-ai/NN-slug.html` one lesson per file; `_template.html` is the starting point.
- `assets/site.css|js` shared layout, nav, progress; `assets/teach.css|js` lesson widgets (`TX2.game`, `TX2.predict`, ...). `scripts/test-site.mjs` is the behaviour test for `assets/site.js` (language, theme, progress, feedback, pager, no outside requests, no JavaScript, no storage; needs Playwright): the copy check runs it when `assets/site.js` changes, so add a case when you add behaviour there.
- **Reader data.** The site keeps exactly two anonymous signals, both sent by `assets/site.js` to the site's own function `api/feedback.js`: the yes/no answer to the "Was this lesson clear?" line at the end of every lesson (asked once per device, `learn-fb` in storage) and that a lesson was read to its end. Each is one tiny blob in a private Vercel Blob store connected to the project (`BLOB_READ_WRITE_TOKEN`, set by Vercel, never in the repo) whose name holds the lesson path and `yes`, `no` or `done`: no cookies, no page views, no address, no typed text. Nothing is sent from a local copy, a preview that is not production counts apart (`test/`), and an automated browser sends nothing, so the agents' checks never count. `GET /api/feedback` answers with public counts per lesson for the last 14 days, which `scripts/daily-scan.mjs readers` reads without a token. `package.json` exists only so Vercel installs `@vercel/blob` for that function: the site still has no build step, and pages still open from disk. There is no analytics script; do not add one.
- `scripts/check-copy.mjs` + `banned-words.txt` the copyright scrubber. The repo is public, so `banned-words.txt` holds only generic rules; the names of platforms and instructors are never written in the repo (kept in TX's private project notes; scrub notes before pushing them). An optional `BANNED_WORDS_EXTRA` variable or untracked `banned-words.local.txt` can add them on a machine.
- `scripts/check-counts.mjs` the count check. `lessons.js` is the only source of truth for topic and lesson counts: pages compute them (`assets/site.js`), and the check fails on any count typed by hand, a lesson file missing from or doubled in `lessons.js`, or a tag that does not match its place.
- `scripts/check-pages.mjs` the page check: every page has `<html lang>`, a title, a meta description and `og:` link-preview tags, alt text on images, headings that never skip a level, and as many `.en` as `.zh` (in markup and in `{en,zh}` script strings). It also keeps `sitemap.xml`, the no-JavaScript lesson list on the track page (between `<!-- lessons:start -->` markers) and the `data-start` links in step with `lessons.js`: `--fix` rewrites them, never by hand. Each lesson also carries `<meta name="updated">`, shown as "Updated ...": `--fix` sets it to today when the lesson's text changed since the last commit. Runs in the copy check. The same `--fix` also writes, from `tracks.js` and each `lessons.js`, in every served page except `404.html` and `_template.html`: `<link rel="canonical">`, one JSON-LD block (WebSite on home, `LearningResource` + `BreadcrumbList` on lessons with `dateModified` from the updated meta, `CollectionPage` on track pages, `WebPage` elsewhere; the word "course" is never used and no count is typed), `?v=<content hash>` on `assets/site|teach|build-concepts.js|css`, `tracks.js` and `lessons.js`, and the `headers` and `redirects` of `vercel.json` (other keys stay). The headers start with the security headers on every response (`SECURITY` in the script: nosniff, referrer policy, no framing by other sites, no camera/microphone/location) and a `Content-Security-Policy-Report-Only` on the live host only (`CSP`: everything from the site itself, inline scripts and styles allowed); a page that needs an outside host must be added there, or the live check will see the violation as a console error. HTML and everything unversioned revalidate on every visit; only the `?v=` assets under `assets/` are `immutable` for a year, and the check fails if a page references one without `?v=`. Never edit these by hand; a stale one fails the page check.
- `404.html` (uses `<base href="/">`), `robots.txt`, `favicon.ico`, `assets/icon.svg`, `assets/apple-touch-icon.png`, `assets/og.png` (link previews).
- `scripts/record-status.mjs <agent>` records an agent's last run (`STATE=run` marks it working, `idle` clears that mark; each workflow's `working` job sets it, and cancelled runs record nothing) in `status/all.json` on the data-only `agent-status` branch (never deployed, never merged).
- `scripts/ui-check.mjs` the UI check agent's browser test. Run `node scripts/ui-check.mjs --pages <page.html>` after changing anything people hover, click or open (needs Playwright).
- `scripts/notify-telegram.mjs` sends TX a Telegram message (secrets `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`; without the chat id it only sends a one-time setup tip).
- `scripts/digest.mjs` the daily Telegram digest (what went live, rollbacks, what waits for TX, agent runs). `DRY_RUN=1` prints instead of sending; `GITHUB_API` points it at a test server.
- `scripts/claude-run.mjs <agent> <claude args>` and `scripts/trace.mjs`: tracing and cost log. Every `claude -p` call in the writer, reader, reviewer, UI check and recall workflows goes through the wrapper (fetched from main at run time, so the branch under test cannot change how its run is measured; it falls back to plain `claude` if main has none). It prints the answer like `--output-format text` and appends one JSON line (model, turns, tokens, time, estimated cost at API prices) to `/tmp/out/trace-<agent>.jsonl`; a trusted step then runs `trace.mjs push`, which keeps the last 1500 calls (about two weeks, so the weekly report can compare weeks) in `trace/runs.json` on the `agent-status` branch (numbers and short known words only). The daily digest adds one "Agent use" line. On the subscription nothing is billed per call: the figure shows which agent uses the most of the plan. A new `claude -p` call in a workflow must use `$CC` the same way.
- **Cheaper, faster agent runs.** Deterministic work happens in workflow steps before Claude. `scripts/agent-context.mjs review|writer` (fetched from main at run time) builds a short brief: the diff without generated noise (sitemap, `?v=` hashes) and capped at 60 KB, only the *failing* lines of the copy, count, page, security and code-box checks, the CLAUDE.md lines about changed non-lesson files, and the top 3 related passages from `scripts/rag.mjs` per changed lesson (writer: for the notes' concept). The prompt carries a 1 to 2 KB rule packet instead of the full documents: `scripts/rules/writer.md` and `scripts/rules/reviewer.md` are boiled-down copies of `STYLE.md` and this file, so **change them when those rules change**; the full documents are reference only. `scripts/max-turns.mjs <agent> <ceiling>` sets `--max-turns` from the 95th percentile of the agent's recent successful calls in `trace/runs.json` (plus 25% and 3 turns, never above the old fixed limit, and the limit itself until 15 calls exist). The UI check's visual pass gets one desktop and one phone image per changed page (top of the page, capped in height, at most 4 pages). `claude-run.mjs` also records a `step` (`TRACE_STEP`, e.g. `review`, `review-fix`, `blind`, `compare`), and on Sundays the daily digest adds `node scripts/trace.mjs weekly`: the last 7 days by model and by workflow step against the week before. Playwright and Chromium are cached (`actions/cache`) in the UI check, live check, phone fit and quality workflows; `live-check.mjs` renders and fetches 5 pages at a time (`--concurrency`) and waits for a ready signal, not a fixed pause.
- `schemas/review.schema.json` + `scripts/validate.mjs`: structured output. The reviewer writes its verdict and findings as `review.json` (category, blocker or nit, file, one sentence) next to its comment; the share job checks it with the trusted validator. When it is valid the stricter reading wins (`fix` blocks a comment that says ✅) and it stands in when the comment has no verdict. `scripts/memory.mjs` is the durable authoring memory: `learn` adds each review's blockers (counts per category, latest examples, scrubbed) to `memory/authoring.json` on the `agent-status` branch, `note "<text>"` adds a decision or rule of thumb, `show` prints it. The writer and reviewer read that file from the branch at run time (`/tmp/memory.json`) and check for those mistakes first. To teach the agents a rule, run `GITHUB_TOKEN=... GITHUB_REPOSITORY=... node scripts/memory.mjs note "..."` or ask a thread to.
- `evals/` and `scripts/run-evals.mjs`: golden cases (the evaluation dataset). `evals/checks.json` edits a copy of a real lesson (a banned word, a missing description, an image without alt text, a fake key, a new-tab link without noopener, a hand-typed count) and says what each check must do; clean controls must pass. Free and about a second; `evals.yml` runs it on any PR that touches a check script, `lib.mjs`, `banned-words.txt` or `evals/`. When you add a check rule, add a case. Banned words and key shapes in cases are `@@PLACEHOLDERS@@` that the runner fills in, so the dataset passes its own checks. `evals/triage-cases.json` holds golden diffs for `scripts/review-triage.mjs` (what may skip the AI review). `evals/review-cases.json` holds excerpts with the verdict a careful reviewer must give; `node scripts/run-evals.mjs --llm` (or Run workflow with `llm`) asks Haiku about each, a few cents.
- `scripts/rag.mjs "<question>"` and `scripts/lib-search.mjs`: local, free search over the lessons (English words and 中文 pieces, plus concept groups that connect the two languages; no model, no network). The writer and reviewer agents use it to link back to, not repeat or contradict, what the site already teaches. There is no "Related lessons" card, no "Before you start" box and no "Mark lesson as complete" button (TX removed them as useless); a lesson counts as done when the reader scrolls to its end. Do not add them back. The one thing at the end of a lesson besides the pager and the What next card is the slim "Was this lesson clear?" line (TX asked for it: it is the only signal from real readers). The lesson sub-header (summary · time · tag) is one paragraph with `Updated` and `Last changed` on their own lines (`p.meta` in `assets/site.css`; never a `ch` max-width).
- `scripts/check-security.mjs` the security check (secrets in any tracked file, unsafe links and outside scripts in served pages, untrusted text in workflow `run:` lines, `pull_request_target`). `scripts/check-code.mjs [lessons]` syntax-checks lesson code boxes (Python/JS; a note, not a gate); it skips JSX/TypeScript files, `data-file="diagram"`/`"output"` boxes and anything after a "# in <place>, replace ..." note, and fills `...` elisions before parsing).
- `scripts/sync-branch.mjs` + `.github/workflows/sync-branches.yml` keep lesson PRs mergeable: after every merge into main (and every 30 minutes) each open `writer/` or `improver/` branch with a conflict gets main merged in, main's version of the generated files (sitemap, track page list, `lessons.js` apart from the branch's own `file:` line), then `check-pages --fix`, pushed with `MERGE_TOKEN` so the checks run on it. A lesson page a `writer/` branch did not add, when the branch changed only its `?v=` hashes, is taken from main. Any other clash, or a branch that changes `scripts/` or `.github/`, is left alone; without `MERGE_TOKEN` it does nothing.
- `scripts/writer-batch.mjs pack|apply`: how the writer's parallel jobs land in one PR. `pack` saves a job's hand-written change to tracked files (edited pages as a patch with context, hash/date lines left out; other files such as `<track>/lessons.js` as before/after copies that `apply` merges three ways, so two packs touching different lines never clash) and its new files; generated files (pages' `?v=` hashes, sitemap, `vercel.json`) are never packed because the publish job rebuilds them. `apply` fails with a clear message when two packs pick the same file name.
- `scripts/auto-merge.mjs` merges green PRs (see `auto-merge.yml`); `DRY_RUN=1` only prints.
- `scripts/live-check.mjs --base <url>` the live check agent's script: every live page, lesson, link and file, rendered in a browser, counts against `lessons.js`.
- `scripts/check-a11y.mjs` + `scripts/check-links.mjs` (shared helpers in `scripts/lib-quality.mjs`) the QA engineer agent's scripts. The first opens every page (desktop + phone, EN + 中文) with axe-core (installed by the workflow only, `AXE_DIR`; never a repo dependency) and fails on serious/critical violations, a control Tab cannot reach, a lesson over 1.5 MB or an `<img>` without width and height. The second checks internal links, anchors and `pkg.files` (fail) and external links (warnings only). Run locally with `AXE_DIR=<dir with node_modules/axe-core> node scripts/check-a11y.mjs [--pages a.html]`.
- `scripts/daily-scan.mjs smoke|drift|speed|rework|readers|report` the QA engineer agent's daily scan (see `daily-scan.yml` below). `drift` is the docs check: every workflow and script must be named in this file or `README.md`, every file they name must exist, every track folder must be listed here, and `api/status.js`, the `AGENTS` array in `ecosystem.html` and the digest must know the same agent ids. Run `node scripts/daily-scan.mjs drift` after adding a workflow, a script, a track or an agent.
- `scripts/recall.mjs plan|message` the learning coach agent: lessons due for spaced review (1, 3, 7, 14, 30... days after they went live) and the gaps; `models` lists the AI model names lessons use, for the monthly outdated-model check.
- `scripts/lib.mjs` shared helpers for the digest, live check and recall scripts (GitHub calls, Telegram, `lessons.js`, scrubbing).
- `.github/rulesets/main.json` the branch rules for main (pull request only; `copy-check` and `Reviewer` must pass on the exact commit; the UI check and live check run after the merge). Import it in Settings → Rules → Rulesets.

## Agents (GitHub Actions)

The team, by role (workflow ids, check names and status ids stay as before): content creator = `writer`, intern who is learning AI = `reader`, frontend engineer = `ui-check`, cybersecurity engineer = `copy-check`, backend engineer = `reviewer` (code samples run, facts true), product engineer = `live-check`, plus `recall` = learning coach, `quality` = QA engineer, `scope-guard` = change control, `improver` = improvement engineer, `news` = industry consultant, `optimizer` = efficiency engineer (ids, check names and the `Scope guard` and `Quality check` names stay as they are). Pages, Telegram and comments use the role names.

| Workflow | Runs on | Does |
| --- | --- | --- |
| `copy-check.yml` | PRs into main, or started by an agent after it pushes | Runs the scrubber (source names, and stray build files like `.pyc`), the security check (`scripts/check-security.mjs`: secrets, unsafe links, untrusted text in workflow scripts), the count check and the page check, then the phone fit (`scripts/ui-check.mjs --fit`: only the changed pages, or a small sample when shared layout files change, at 390px; content wider than the screen or a popup off the side fails the check; a page that fails to open is left to the full UI check; skipped with a notice if the browser cannot be installed); fails and tells TX on Telegram |
| `writer.yml` | Pushes to `inbox/**` on the `notes` branch (handed over to main's copy as ONE run for the whole push), or manual (`folder`, space separated) | One parallel job per notes folder: Claude writes the lesson, drops any scratch files it made outside the track folders, `assets/` and `inbox/`, and packs only its own change (`scripts/writer-batch.mjs pack`). One `publish` job then applies every pack to main, rebuilds the generated files once (`check-pages --fix`, search index), runs the copy, count and page checks and opens ONE PR for the whole batch, so lessons never clash with each other. Telegram only on failure |
| `reader.yml` | Every finished Vercel preview deploy, or manual | Claude reads changed lessons as the reader each one is written for and scores clarity: `scripts/reader-brief.mjs` (no AI, fetched from main) tells it each lesson's level from `lessons.js` and what the lesson assumes from `prereqs.js`, so a beginner lesson is judged by a complete newcomer and an intermediate or advanced one by someone who knows the easier levels; anything the lesson itself brings in must still be explained. On a lesson's own PR (`writer/` branch) it adds its fixes as one `Reader:` commit when a lesson scores under 8/10, comments, then starts the reviewer. Elsewhere it only comments; it skips merges of lesson PRs and agents' own fix commits. Telegram only on failure |
| `review.yml` | Started by the reader on a lesson PR; every other PR into main when it opens or gets a commit; or manual | Claude reviews against `STYLE.md` and comments once, and sets the required `Reviewer` status (green only for ✅) on the exact commit it read. Before Claude runs, `scripts/check-code.mjs` syntax-checks the changed lessons' code boxes. On a lesson PR it adds its fixes as one `Reviewer:` commit (marked too). Telegram only when it cannot finish (a ⚠️ reaches TX through auto-merge). `scripts/review-triage.mjs` (no AI, fetched from main) runs first: a PR, or the commits since the last ✅ review, that change only generated files (sitemap, `?v=` hashes, page dates) get a ✅ comment without a Sonnet run. A later hand edit needs a new review. Claude runs read-only; a separate job writes |
| `ui-check.yml` | Every finished Vercel preview deploy, or manual | `scripts/ui-check.mjs` hovers, clicks and Tabs through the pages the PR changed (a small sample when shared layout files change; every page on a manual run; no served page changed means a skipped, green status) in a headless browser (desktop + phone) and flags anything clickable that Tab cannot reach, overlapping, covered (opening behind other content) or see-through popups, content wider than the screen and script errors (locally it serves a full fake `api/status` so popups are full size); Claude looks at screenshots of changed pages. Sets a `UI check` status, one PR comment, Telegram only when it cannot finish. It no longer holds a merge back: it runs on the PR's preview and a red check shows there. The browser and Claude run in a read-only job; a separate share job with trusted scripts from main does the writing |
| `scope-guard.yml` | Every PR into main (and started by the review when an agent opened the PR) | Two Haiku calls with no tools: the first sees only the diff and says what it does, the second compares that with the PR title and description (`schemas/scope*.schema.json`). Path rules (`scripts/areas.json`) apply first. On a mismatch: `Scope guard` and `Reviewer` statuses red, one PR comment with a plain reason. Always: `area:<id>` labels. The AI job is read-only and never checks the branch out; a separate job writes. If the AI is unavailable only the path rules apply, and the status says so. Label `scope-ok` overrides |
| `live-check.yml` | Every push to main, every merge by auto-merge (`merge`/`before` inputs), or manual | Waits up to 15 minutes for Vercel's production deploy of that commit, then `scripts/live-check.mjs` on the live site. If the merge broke a site that was fine before (last live check passed, deploy succeeded), the rollback job opens a `Rollback:` PR that reverts it, sets its `Reviewer` status, merges it as soon as the checks allow (up to 20 minutes, else TX gets the link) and checks the site again. Only real breakage counts: a page that does not open, a missing file, a script error, wrong counts, or `undefined`/`NaN`/`{{` that a script put on the page (more on screen than in the page's own HTML, so lessons may teach those words); each broken page is opened twice. Product notes (中文 not showing, wider than a phone, slow, broken image) are reported, never rolled back. One Telegram message; a cancelled run sends nothing and records nothing. Manual runs without `merge` never roll back. It then starts auto-merge for the next PR |
| `improver.yml` | Four times a day (03:41, 09:41, 15:41, 21:41 UTC), or manual | The improvement engineer agent: one reported problem, low-scored lesson or idea per run, one `improver/` PR (details below) |

### More about four agents

- The **Efficiency engineer agent** runs every six hours from `.github/workflows/optimizer.yml`. It measures the repository with `scripts/efficiency-report.mjs`, makes at most one focused source improvement per run, records before/after measurements, and opens one pull request. It never changes the merge guardrails, agent runners, lesson prose or project reference code; the existing copy check, backend review, UI check, auto-merge and live rollback still apply. Its status id is `optimizer`.

- The **Improvement engineer agent** (`.github/workflows/improver.yml`, status id `improver`) closes the loop on what other agents found. Four times a day `scripts/signals.mjs brief` (no AI) picks ONE item: a page named in the open `Quality check` issue, else the lesson the intern scored lowest below 8 (`signals/reader.json` on `agent-status`, written by the reader workflow). Only then Claude (Sonnet, at most 30 turns) fixes just that in just the files it was given (a guard step fails the run if it touched any other file) and opens one `improver/` PR; at most one is open at a time and the same item waits 7 days (`signals/improver.json`). Nothing to fix means no AI run. **Scouting (every role looks for improvements itself):** when neither a quality problem nor a low score exists, `scripts/scout.mjs plan` (no AI) picks the role that scouted longest ago (content creator, backend engineer, frontend engineer, cybersecurity engineer, product engineer, translator, intern; their lenses live in `ROLES`; the translator compares a lesson's 中文 with its English for meaning and glossary terms) and ONE file of its area that is new or changed since it was last scouted (or older than 45 days); Haiku (read-only, 10 turns) suggests at most 2 ideas, and `scout.mjs add` stores them in `signals/ideas.json` on `agent-status` (deduped against pending and done ideas, at most 12 pending, expire after 30 days). `signals.mjs pick` takes the best idea when nothing more urgent exists (an idea with role `readers`, left by the daily scan for a lesson real readers marked "not quite clear", has priority 1), so ideas go through the same one-PR path and checks. No scout runs while a reported problem comes first, while 5 or more ideas wait, or when every file is unchanged; shared site scripts are never scouted. A new role = a new entry in `ROLES`. Same checks as every PR, including the scope guard. It never edits workflows, scripts, rules or project code.

- The **Industry consultant agent** (`.github/workflows/news.yml`, status id `news`) keeps lessons current. Daily `scripts/news.mjs plan` (no AI) reads the first-party feeds in `scripts/news-sources.json` (official blogs and release notes; add or drop a feed there), keeps items from the last 3 days it has not seen (`signals/news.json` on `agent-status`), and matches each to the lessons that mention the topic with the local search; an item that names a model id the lessons use in code (`modelsInLessons` in `scripts/lib.mjs`) is always matched to those lessons, so a retired model is caught the day it is announced. Only when something matches does Haiku run (no tools, 2 turns, at most 10 items) and judge whether a fact a lesson teaches is now out of date; `news.mjs add` keeps at most 3 ideas (role `news`, with a `source` link; the file must be one of the matched lessons) in `signals/ideas.json`, so the improvement engineer agent handles them like any other idea (one small PR, scope guard, auto-merge). It changes no site file itself, never proposes new lessons or tracks (those come from TX's notes) and sends Telegram only on failure. It does nothing while 8 or more ideas wait.
- **Areas and the scope guard.** `scripts/areas.json` is the map of the site's independent parts: one area per learning track (read from `tracks.js`, packages included), plus `site-shell`, `ecosystem`, `glossary`, `agents` and `rules`; generated files (sitemap, `vercel.json`, search index) belong to every area. Keep a change inside one area where you can, and one pull request does one thing. `scripts/scope-guard.mjs` + `scope-guard.yml` (the **Change control agent**, status id `scope-guard`) reads each PR's diff without the request, says what it does, then compares that with the PR title and description; path rules come first (a `writer/` or `reader/` branch may change one track only, `optimizer/` two areas, `improver/` one). A mismatch sets `Scope guard` and the required `Reviewer` status red with a plain reason, so auto-merge waits and tells TX once; no change to auto-merge was needed. It labels the PR `area:<id>`. Label `scope-ok` lets one through. So write a PR description that says everything the PR does, in plain words.

Actions in every workflow are pinned to a full commit SHA with the version as a comment (`uses: actions/checkout@<sha> # v4`), never a bare tag.

Telegram: one digest a day at 8 PM. Instant messages only for failures, a quality-check problem, a rollback, a stuck PR (from auto-merge), and the weekly review.
Pushes and PRs made with the workflow token start no workflows, so an agent that pushes starts `copy-check.yml` on that branch itself (`gh workflow run`), the reader starts the reviewer, and the writer hands notes over with `gh workflow run writer.yml --ref main`. The writer, improvement and efficiency agents open their pull request with `MERGE_TOKEN` when it is set (the workflow token falls back otherwise), because the checks of a pull request opened by a bot with the workflow token wait for someone to approve the run, and the required `copy-check` never turns green; with `MERGE_TOKEN` the pull request starts its own checks and the by-hand starts are skipped. `review.yml` ignores the opening of a `writer/` pull request: there the reader starts it, after its own fixes.

Claude auth: the writer, reviewer, reader, UI check and recall agents use TX's Claude subscription through the `CLAUDE_CODE_OAUTH_TOKEN` secret (made with `claude setup-token`). `ANTHROPIC_API_KEY` is only a fallback when that secret is missing. Subscription runs share TX's plan usage limits. Models are pinned to keep usage low: the writer and reviewer use `sonnet`, the reader, UI check and recall use `haiku` (`--model` on each `claude -p`). Interactive Claude sessions use the same plan. Prompt caching is automatic in `claude -p` (system prompt, tools and the growing conversation are cached within a run); every `claude -p` also passes `--exclude-dynamic-system-prompt-sections` so the cached start is the same between runs. The reader reads at most 6 lessons per run.

## Typography

Type is Apple-style: the system sans (-apple-system / SF Pro on Apple devices, self-hosted Inter in `assets/fonts/` elsewhere, PingFang SC for 中文), no serif and no italics. Headings get contrast from weight, size and tight tracking. An `<em>` inside `h1`/`h2` is upright amber. Rules are at the end of `assets/site.css`.

## Rules

0. **One request, one pull request.** Whatever TX asks for in one message (a track of lessons, a fix plus its follow-ups, a pipeline change) lands in ONE pull request, never a pull request per lesson or per step. Parallel pull requests all rewrite the same generated files (sitemap, lesson lists, `?v=` hashes), clash with each other and merge one at a time. Agents and threads that do several things for one request build them in one branch and open one pull request whose description says everything it does. The writer already follows this (`writer.yml`: parallel jobs, one pull request).

1. **Write every lesson to `STYLE.md`.** Lesson titles are short noun phrases (2 to 5 words, about 4 to 10 characters in 中文), never sentences, no colons, no `Project:` prefix. Read it before writing or editing a lesson. Do not wait to be reminded.
2. **Source-neutral, always.** No platform, program, instructor names, no "course"/课程, no week/day numbering, no copied examples. Run `node scripts/check-copy.mjs`, `node scripts/check-counts.mjs` and `node scripts/check-pages.mjs` before every commit; all must pass. Never type a topic or lesson count into a page.
3. **Branches.** Every change is a pull request into `main` (Vercel builds its own preview; that is the test). `main` is the live site. Auto-merge merges it once the copy check and the reviewer agent's ✅ are green (the UI check and live check run after the merge); TX only merges PRs that change auto-merge itself (`auto-merge.yml`, `scripts/auto-merge.mjs`, the ruleset) or that auto-merge reports as stuck. Workflow-changing PRs auto-merge too, through the `MERGE_TOKEN` secret. There is no `test` branch and no release step. If a merge breaks the live site, the live check agent rolls it back.
4. **Agents notify before changing.** An agent never pushes straight to `main`. Every change goes through its one pull request and its required checks; auto-merge merges it when they are green. Agents push directly only to the `agent-status` run log, the `notes` branch (notes only) and, as fixes, to a lesson's own `writer/` draft branch before TX merges it. Agents merge only through auto-merge (all required checks green) and a `Rollback:` pull request that puts main back to the reviewed state before a merge that broke the live site.
5. Keep English and 中文 in step: every `.en` has a matching `.zh`.
6. No build tools or frameworks. Plain files that open from disk.

## Moving or renaming a page

A published URL is never deleted or left to 404. To move or rename a page, a lesson file or a track folder: move the file, add `{"from":"/old/path.html","to":"/new/path.html"}` to `scripts/redirects.json` (point straight at the final page, no chains), update `lessons.js`, then run `node scripts/check-pages.mjs --fix`. That regenerates the permanent redirects in `vercel.json`, the sitemap, canonical links and JSON-LD. The page check compares `sitemap.xml` with main and fails when a URL that was published no longer opens and has no redirect. Renaming only a title (as when the track became "AI Agentic") moves no URL and needs no redirect. Do not link `.md` files: they are not deployed.

## Adding a lesson

Easiest: drop notes in `inbox/<concept>/` on the `notes` branch and let the writer agent draft it (see `inbox/README.md`). Notes for a track other than `agentic-ai` carry a one-line `TRACK` file with the track id. By hand:

1. Copy `agentic-ai/_template.html` to `<track>/NN-slug.html` (next free number in that track).
2. Write it to `STYLE.md`, with the tag `<Topic> · Lesson N`.
2b. Lesson widget code (`TX2.game`, `TX2.predict`, ...) goes in `<track>/js/NN-slug.js`, loaded by a script tag for `js/NN-slug.js` after `assets/teach.js` at the end of the page, never inline; `--fix` adds the `?v=` hash.
3. Add `file:'NN-slug.html'` to its item in `<track>/lessons.js` (or add the item under the right topic), then run `node scripts/check-pages.mjs --fix` (it also stamps the lesson's updated date).
4. Fill in the `<title>`, description and `og:` tags, run `node scripts/check-copy.mjs`, `node scripts/check-counts.mjs` and `node scripts/check-pages.mjs`, then open the page in a browser and click every widget.
