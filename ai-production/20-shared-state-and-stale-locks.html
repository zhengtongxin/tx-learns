Shared state and stale locks共享状态与过期的锁

Move Terraform state off your laptop so teammates and robots can share it, and learn what a stale lock is and how to clear one safely · ~30 min · hands-on把 Terraform 的状态从你的笔记本挪走，让队友和机器人都能共用，并弄懂什么是过期的锁、怎样安全地清掉它 · 约 30 分钟 · 动手实践

Where we left off上回讲到

Last time the product could be brought up and down by script, but its state, the logbook of what exists, sat on Mei Ling's laptop. Today it fails when a robot needs that book, or two people deploy at once. We fix it by moving the state to a shared bucket with a lock.

上回，产品已经能用脚本上线和下线，但它的状态，也就是记录现有东西的日志簿，放在 Mei Ling 的笔记本上。今天机器人需要这本簿子，或者两个人同时部署，就会出问题。我们的办法是把状态搬到带锁的共享存储桶里。

The story故事

Kumar wants a robot to deploy the twin, and Mei Ling wants to stay able to deploy it too. There is a catch: the state, the logbook of what exists, sits on her laptop. The robot cannot read it, and if two people deploy at once, they will both write in the book. Mei Ling needs one shared logbook with a "do not disturb" sign.

Kumar 想让一个机器人来部署分身，而 Mei Ling 也想保留自己部署的能力。但有个麻烦：状态，也就是记录“有什么存在”的日志，躺在她的笔记本上。机器人读不到它，而且两个人同时部署的话，会同时往日志里写。Mei Ling 需要一本共用的日志，再加一块“请勿打扰”的牌子。

Step 1 · A state bucket and a lock table, once per account第 1 步 · 状态存储桶和锁表，每个账号建一次

Learn先学

Shared state needs two things. A bucket to hold the state files. Turn on versioning (every write keeps the old copy, so a bad write can be rolled back), encryption and a block on public access. And a small lock table where Terraform writes "I am working" while it runs. You make these once per account, by hand or with a one-off script, because Terraform cannot store its state in a bucket that it has not made yet.

共享状态需要两样东西。一个存放状态文件的存储桶。要打开版本管理（每次写入都保留旧副本，写坏了可以回滚）、加密，并禁止公开访问。还要一张小小的锁表，Terraform 运行时会在里面写下“我正在干活”。这些每个账号建一次，用手工或一次性脚本都行，因为 Terraform 没法把状态存进一个它自己还没建好的存储桶里。

# use your own account id in the bucket name BUCKET=wharf-tf-state-111122223333 REGION=ap-southeast-1 aws s3api create-bucket --bucket $BUCKET --region $REGION \ --create-bucket-configuration LocationConstraint=$REGION aws s3api put-bucket-versioning --bucket $BUCKET --versioning-configuration Status=Enabled aws s3api put-bucket-encryption --bucket $BUCKET \ --server-side-encryption-configuration '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}' aws s3api put-public-access-block --bucket $BUCKET \ --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true aws dynamodb create-table --table-name wharf-tf-locks --region $REGION \ --attribute-definitions AttributeName=LockID,AttributeType=S \ --key-schema AttributeName=LockID,KeyType=HASH --billing-mode PAY_PER_REQUEST

Step 2 · Point the config at it and migrate第 2 步 · 让配置指向它，并迁移过去

Learn先学

A backend is where Terraform keeps its state. Tell it to use the bucket and the lock table. The names go in a small file, backend.hcl, so the same config can run on your laptop and in a robot. Then run init with the migrate flag: Terraform sees the old local state, offers to copy it to the bucket, and (if you have several workspaces) copies them all. Answer yes, then check the objects arrived.

后端（backend）是 Terraform 存放状态的地方。让它用上面的存储桶和锁表。名字放在一个小文件 backend.hcl 里，这样同一份配置既能在你的笔记本上跑，也能在机器人里跑。然后带着迁移参数运行 init：Terraform 发现旧的本地状态，提议把它复制到存储桶里（如果有多个工作区，就全部复制）。回答 yes，然后检查对象是不是到了。

The lock table here is the classic setup. Newer Terraform versions can also keep the lock inside the bucket itself; the idea is the same.

这里用的锁表是经典做法。较新的 Terraform 版本也可以把锁放在存储桶里面；道理是一样的。

# main.tf: the backend goes inside the terraform block you already have terraform { required_providers { aws = { source = "hashicorp/aws", version = "~> 5.0" } } backend "s3" { key = "twin/terraform.tfstate" encrypt = true } } # backend.hcl (the values that differ per account; not secret, but keep it out of the config) bucket = "wharf-tf-state-111122223333" region = "ap-southeast-1" dynamodb_table = "wharf-tf-locks" terraform init -migrate-state -backend-config=backend.hcl # answer yes aws s3 ls s3://wharf-tf-state-111122223333/ --recursive # env:/dev/twin/terraform.tfstate ...

Step 3 · The lock in action第 3 步 · 锁在起作用

Learn先学

While one run is changing the state, Terraform writes a lock row into the table. A second run that tries the same state sees the row and stops, and prints who holds the lock, since when, and a lock ID. That is the "do not disturb" sign, and it is a good thing: two writers at once could damage the logbook. If you would rather wait than fail, add -lock-timeout=2m.

一个运行正在改状态时，Terraform 会往表里写一行锁。第二个想动同一份状态的运行会看到这一行，然后停下来，并打印是谁持有锁、从什么时候开始，以及一个锁 ID。这就是那块“请勿打扰”的牌子，它是好事：两个人同时写，可能把日志写坏。如果你宁愿等也不想失败，就加上 -lock-timeout=2m。

# terminal A: terraform apply -var="environment=dev" (leave it at the yes/no prompt) # terminal B: $ terraform plan -var="environment=dev" Error: Error acquiring the state lock Lock Info: ID: 3f2a9c1e-0000-0000-0000-000000000000 Operation: OperationTypeApply Who: mei@laptop Created: 2026-11-23 09:41:07 UTC terraform plan -var="environment=dev" -lock-timeout=2m # wait up to two minutes instead

Step 4 · A stale lock, and how to clear it第 4 步 · 过期的锁，以及怎么清掉它

Learn先学

If a run is killed (a closed laptop, a cancelled job, a lost connection; a pipeline is the robot's automatic run of these steps, and the next lesson explains it), nobody removes its lock row. It is now a stale lock: the sign says "working" but nobody is. That is normal. The fix is terraform force-unlock with the lock ID. But force-unlocking while the run is still alive lets two writers in, which can corrupt the state. So check first.

如果一个运行被中途杀掉（合上的笔记本、取消的任务、断掉的连接；流水线（pipeline）是机器人自动运行这些步骤的地方，下一课会讲），没人会去删它的锁。这就成了过期的锁：牌子写着“正在干活”，其实没人在干。这很正常。解法是用锁 ID 运行 terraform force-unlock。但如果那个运行其实还活着，强制解锁就等于放第二个写入者进来，可能把状态写坏。所以要先检查。

# the checklist before you unlock # 1. read Lock Info: who, which operation, since when # 2. is that run really dead? look at your terminal, the pipeline's runs, and ask the teammate # 3. only then: terraform force-unlock 3f2a9c1e-0000-0000-0000-000000000000

Step 5 · A destroy script that unlocks and retries第 5 步 · 会解锁并重试的销毁脚本

Learn先学

You can teach the destroy script to spot the lock error, take the lock ID from it and retry. It is handy, and it is dangerous for the same reason as step 4, so the script asks a human first. Never make it unlock silently.

你可以教销毁脚本识别锁的报错，从里面取出锁 ID，然后重试。这很方便，也和第 4 步一样危险，所以脚本要先问一个人。千万别让它悄悄解锁。

# inside destroy.sh, replacing the last line (the plain terraform destroy) if out=$(terraform destroy -auto-approve -lock-timeout=30s -var="environment=$ENV" 2>&1); then echo "$out"; exit 0 fi echo "$out" if echo "$out" | grep -q "Error acquiring the state lock"; then id=$(echo "$out" | awk '/^ *ID:/ {print $2; exit}') read -r -p "Lock $id is held. Is nobody really running Terraform on $ENV? (yes/no) " ok [ "$ok" = "yes" ] || exit 1 terraform force-unlock -force "$id" terraform destroy -auto-approve -var="environment=$ENV" else exit 1 fi
What I got wrong我犯过的错Three slips. I force-unlocked while another run was still alive, which can corrupt state. I lost track of which bucket held which environment's state, so now there is one state bucket and one clear path per environment. And I forgot to turn on versioning, so there was no way back from a bad write.三个失误。我在另一个运行还活着的时候强制解了锁，这可能把状态写坏。我分不清哪个存储桶放着哪个环境的状态，所以现在只有一个状态存储桶，每个环境一条清楚的路径。我还忘了打开版本管理，结果写坏之后没有退路。

Now make it yours现在把它变成你的

What changed这一课之后Now the state lives in a shared bucket behind a lock, so Mei Ling or a robot can deploy but never both at once, and she knows how to clear a stale lock only after checking. The next problem is that a person still has to run the deploy, and Kumar wants a push to do it.现在状态放在带锁的共享存储桶里，Mei Ling 或机器人都能部署，但不会同时进行，她也知道只有在核实之后才能清除过期的锁。下一个问题是部署仍要有人动手，Kumar 想让一次推送就完成。

Takeaways要点回顾

• State on a laptop cannot be shared; a bucket with versioning, encryption and no public access can.
• Create the state bucket and the lock table once per account, before Terraform uses them.
• Point the backend at them, keep the names in backend.hcl, and migrate with init -migrate-state.
• The lock stops two runs from changing the same state at the same time.
• A killed run leaves a stale lock behind. That is normal.
• Before force-unlock, check that nobody is really running; unlocking a live run can corrupt state.
• Let a script retry after unlocking only if it asks a human first.

• 笔记本上的状态没法共享；开了版本管理、加密、禁止公开访问的存储桶可以。
• 状态存储桶和锁表，每个账号建一次，要在 Terraform 用到它们之前建好。
• 把后端指向它们，名字放在 backend.hcl 里，用 init -migrate-state 迁移。
• 锁防止两个运行同时改同一份状态。
• 被杀掉的运行会留下过期的锁。这很正常。
• force-unlock 之前，先确认真的没人在运行；给还活着的运行解锁，可能把状态写坏。
• 只有在先问过人的前提下，才让脚本解锁后重试。
