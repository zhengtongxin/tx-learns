Shared state and locks共享状态与锁

Move Terraform state off your laptop so teammates and robots can share it, and learn what a stale lock is and how to clear one safely · ~30 min · hands-on把 Terraform 的状态从你的笔记本挪走，让队友和机器人都能共用，并弄懂什么是过期的锁、怎样安全地清掉它 · 约 30 分钟 · 动手实践

Step 1 · A state bucket and a lock table第 1 步 · 状态存储桶和锁表

Learn先学

State on a laptop cannot be shared with a robot. Shared state needs a bucket with versioning (a bad write can be rolled back), encryption and no public access, plus a small lock table where Terraform writes "I am working". Create both once per account, by hand: Terraform cannot store state in a bucket it has not made yet.

笔记本上的状态没法和机器人共用。共享状态需要一个开了版本管理（写坏了可以回滚）、加密、禁止公开访问的存储桶，再加一张小小的锁表，Terraform 在里面写下“我正在干活”。每个账号手工建一次：Terraform 没法把状态存进一个它还没建的桶里。

BUCKET=wharf-tf-state-111122223333 # use your own account id REGION=ap-southeast-1 aws s3api create-bucket --bucket $BUCKET --region $REGION \ --create-bucket-configuration LocationConstraint=$REGION aws s3api put-bucket-versioning --bucket $BUCKET --versioning-configuration Status=Enabled aws s3api put-public-access-block --bucket $BUCKET \ --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true aws dynamodb create-table --table-name wharf-tf-locks --region $REGION \ --attribute-definitions AttributeName=LockID,AttributeType=S \ --key-schema AttributeName=LockID,KeyType=HASH --billing-mode PAY_PER_REQUEST # (also turn on default encryption with put-bucket-encryption)

Step 2 · Point the config at it and migrate第 2 步 · 让配置指向它，并迁移过去

Learn先学

A backend is where Terraform keeps its state. Put the account-specific names in backend.hcl, then run init -migrate-state and answer yes: Terraform copies the old local state into the bucket. Newer Terraform versions can also keep the lock in the bucket itself; the idea is the same.

后端（backend）是 Terraform 存放状态的地方。把和账号相关的名字放进 backend.hcl，然后运行 init -migrate-state 并回答 yes：Terraform 会把旧的本地状态复制进存储桶。较新的 Terraform 版本也可以把锁放在桶里；道理一样。

# main.tf, inside the terraform block backend "s3" { key = "twin/terraform.tfstate" encrypt = true } # backend.hcl bucket = "wharf-tf-state-111122223333" region = "ap-southeast-1" dynamodb_table = "wharf-tf-locks" # terminal: terraform init -migrate-state -backend-config=backend.hcl

Step 3 · The lock, and a stale lock第 3 步 · 锁，以及过期的锁

Learn先学

While a run changes the state, Terraform writes a lock row. A second run sees it, stops, and prints who holds the lock and its ID. That is good: two writers could damage the state. Add -lock-timeout=2m to wait instead of failing.

一个运行改状态时，Terraform 会写一行锁。第二个运行看到后会停下，并打印是谁持有锁和锁 ID。这是好事：两个写入者可能把状态写坏。加上 -lock-timeout=2m 可以等待而不是失败。

If a run is killed (closed laptop, cancelled job), its lock stays: a stale lock. Fix it with terraform force-unlock and the lock ID, but only after you confirm the run is really dead. Unlocking a live run lets two writers in and can corrupt the state.

如果一个运行被杀掉（合上的笔记本、取消的任务），它的锁会留下来：这就是过期的锁。用 terraform force-unlock 加锁 ID 来清除，但必须先确认那个运行真的死了。给活着的运行解锁会放进第二个写入者，可能把状态写坏。

$ terraform plan -var="environment=dev" Error: Error acquiring the state lock Lock Info: ID: 3f2a9c1e-0000-0000-0000-000000000000 Who: mei@laptop Created: 2026-11-23 09:41:07 UTC # only after checking who, since when, and that the run is dead: terraform force-unlock 3f2a9c1e-0000-0000-0000-000000000000

Now make it yours现在把它变成你的

Common errors常见错误

• Error acquiring the state lock Fix: Read Lock Info, wait with -lock-timeout, and unlock only when sure nobody runs.
• Backend initialization required Fix: Run terraform init -migrate-state -backend-config=backend.hcl.
• BucketAlreadyOwnedByYou You ran the create command twice. Fix: Move on to the next command.

• Error acquiring the state lock 解决：读 Lock Info，用 -lock-timeout 等待，确认无人在运行才解锁。
• Backend initialization required 解决：运行 terraform init -migrate-state -backend-config=backend.hcl。
• BucketAlreadyOwnedByYou 创建命令运行了两次。 解决：继续下一条命令。

Takeaways要点回顾

• Shared state needs a versioned, encrypted, private bucket plus a lock table, made once per account.
• Point the backend at them and migrate with init -migrate-state.
• The lock stops two runs changing the same state at once.
• A killed run leaves a stale lock; that is normal.
• Check that nobody is running before force-unlock.

• 共享状态需要开了版本管理、加密的私有存储桶，加一张锁表，每个账号建一次。
• 把后端指向它们，用 init -migrate-state 迁移。
• 锁防止两个运行同时改同一份状态。
• 被杀掉的运行会留下过期的锁；这很正常。
• force-unlock 之前先确认没人在运行。
