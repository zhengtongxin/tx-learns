So she picks a size by test instead of by feeling, and then sets up a way to see what the twin does once Auntie Siti and the canteen crowd start chatting with it.

Step 1 · Three sizes, and the model id as a knob第 1 步 · 三种大小，把模型 id 做成一个旋钮

Learn先学

The provider's own model family comes in three sizes. Micro is the fastest and cheapest, good for simple jobs. Lite is balanced. Pro is the best at reasoning, and the slowest and dearest. Make the model id an environment variable (a setting the function reads when it starts) so that switching size needs no code change.

服务商自己的模型家族有三种大小。Micro 最快最便宜，适合简单的活。Lite 比较均衡。Pro 推理最强，也最慢最贵。把模型 id 做成一个环境变量（函数启动时读取的设置），这样换大小就不用改代码。

One catch: the command below replaces the function's whole set of variables, so list every one you still need.

有一个坑：下面这条命令会替换函数的整套变量，所以还需要的变量都要列出来。

import os MODEL_ID = os.environ["MODEL_ID"] # no size is written in the code any more
# example for later: once Step 3 shows micro passes, switch to it without touching the code # (list EVERY variable the function needs): aws lambda update-function-configuration --function-name wharf-twin \ --environment "Variables={MODEL_ID=apac.amazon.nova-micro-v1:0,MEMORY_BUCKET=wharf-twin-memory}"

Step 2 · What a month costs第 2 步 · 一个月要花多少钱

Learn先学

A model is priced per thousand tokens (small pieces of text, roughly three-quarters of a word), with one price for the text going in and a higher one for the text coming out. So a chat costs: input tokens × input price + output tokens × output price. Multiply by how many chats you expect. The prices below are made-up round numbers for practice; always read the provider's current price page.

模型按每一千个 token（文字的小片段，大约四分之三个英文单词）计价，输入的文字一个价，输出的文字一个更高的价。所以一次聊天的费用是：输入 token 数 × 输入单价 + 输出 token 数 × 输出单价，再乘以你预计的聊天次数。下面的价格是练习用的数字，是编的；实际请读服务商当前的价格页。

# example prices in dollars per 1,000 tokens: (input, output) -- not real, check today's page PRICES = {"micro": (0.00004, 0.00016), "lite": (0.00006, 0.00024), "pro": (0.0008, 0.0032)} def cost_per_chat(size, tokens_in=800, tokens_out=200): p_in, p_out = PRICES[size] return tokens_in / 1000 * p_in + tokens_out / 1000 * p_out for size in PRICES: c = cost_per_chat(size) print(size, round(c, 6), "per chat,", round(c * 1000, 3), "per 1,000 chats") # micro 6.4e-05 per chat, 0.064 per 1,000 chats # lite 9.6e-05 per chat, 0.096 per 1,000 chats # pro 0.00128 per chat, 1.28 per 1,000 chats

Step 3 · Same ten questions, three sizes第 3 步 · 同样十道题，三种大小

Learn先学

Do not judge a model on one prompt. Write ten questions the twin must answer well, with a word each good answer must contain, and run all of them on every size. Record what passed, how long it took and how many tokens it used (each reply carries a usage block with inputTokens and outputTokens, the counts you are billed on). A keyword check is crude, but it is repeatable, and you can read the failures yourself.

别拿一个提示就给模型下结论。写十道分身必须答好的题，每题写一个好答案里必须出现的词，然后在每种大小上都跑一遍。记下通过了几道、用了多久、用了多少 token（每个回应里都带一个 usage 块，有 inputTokens 和 outputTokens，这就是计费用的数字）。关键词检查很粗糙，但它可以重复，而且失败的答案你可以自己去读。

The code shows four questions to keep it short; grow the list to ten.

代码里为了简短只放四道题；请把清单扩到十道。

import os import time import boto3 client = boto3.client("bedrock-runtime", region_name=os.environ.get("AWS_REGION", "ap-southeast-1")) SYSTEM = ("You are Mei Ling's twin. Facts: she works in the wharf IT office, " "she studies on weekends, her favourite lunch is Auntie Siti's laksa.") SIZES = {"micro": "apac.amazon.nova-micro-v1:0", "lite": "apac.amazon.nova-lite-v1:0", "pro": "apac.amazon.nova-pro-v1:0"} QUESTIONS = [("What is Mei Ling's favourite lunch?", "laksa"), # grow this list to ten ("Where does Mei Ling work?", "wharf"), ("When does Mei Ling study?", "weekend"), ("Who makes her favourite lunch?", "siti")] def run(size): passed, secs, tin, tout = 0, 0.0, 0, 0 for question, must_have in QUESTIONS: t0 = time.time() r = client.converse(modelId=SIZES[size], system=[{"text": SYSTEM}], messages=[{"role": "user", "content": [{"text": question}]}], inferenceConfig={"maxTokens": 200}) secs += time.time() - t0 text = r["output"]["message"]["content"][0]["text"].lower() passed += must_have in text tin += r["usage"]["inputTokens"] tout += r["usage"]["outputTokens"] return passed, round(secs, 1), tin, tout for size in SIZES: print(size, run(size)) # (passed, seconds, input tokens, output tokens)
(example output) micro (4, 3.1, 520, 96) lite (4, 4.2, 520, 101) pro (4, 9.8, 520, 108)

Step 4 · Watch it once it is live第 4 步 · 上线后盯着它

Learn先学

The test tells you what should happen. The logs tell you what does. The logs service already counts invocations, duration and errors for the function. Add one line per model call with the model, the time and the token counts, so a slow or costly request shows up as a single searchable line (print sends it to the function's logs). Then set an alarm: it messages you when errors go over a limit, so you hear about it before a user complains.

测试告诉你应该发生什么，日志告诉你实际发生了什么。日志服务已经替函数统计了调用次数、时长和错误数。再给每次模型调用加一行，写上模型、耗时和 token 数，这样慢的或贵的请求就成了一行能搜到的记录（print 会把这一行送进函数的日志）。然后设一个警报：错误超过上限时它会通知你，这样用户还没抱怨你就先知道了。

import json import os import time import boto3 client = boto3.client("bedrock-runtime", region_name=os.environ.get("AWS_REGION", "ap-southeast-1")) MODEL_ID = os.environ["MODEL_ID"] def ask_logged(system_prompt: str, messages: list) -> str: t0 = time.time() resp = client.converse(modelId=MODEL_ID, system=[{"text": system_prompt}], messages=messages, inferenceConfig={"maxTokens": 300}) print(json.dumps({"event": "model_call", "model": MODEL_ID, "ms": round((time.time() - t0) * 1000), "in": resp["usage"]["inputTokens"], "out": resp["usage"]["outputTokens"]})) return resp["output"]["message"]["content"][0]["text"]
# first make the alert topic that emails you; the command prints its address (an ARN), and you confirm the email it sends: aws sns create-topic --name wharf-alerts aws sns subscribe --topic-arn arn:aws:sns:ap-southeast-1:111122223333:wharf-alerts --protocol email --notification-endpoint you@example.com # then an alarm on errors (the last line is that topic's address): aws cloudwatch put-metric-alarm --alarm-name twin-errors --namespace AWS/Lambda --metric-name Errors \ --dimensions Name=FunctionName,Value=wharf-twin --statistic Sum --period 300 --evaluation-periods 1 \ --threshold 1 --comparison-operator GreaterThanOrEqualToThreshold \ --alarm-actions arn:aws:sns:ap-southeast-1:111122223333:wharf-alerts

Step 5 · Cost tips that keep working第 5 步 · 一直管用的省钱办法

Learn先学

Most of the bill is tokens, so cut tokens. Keep the system prompt short. Cap the history sent each time, for example the last ten messages. And pick the smallest model that passes your test. When quality ever drops, you can move up one size, because the id is a knob.

账单的大头是 token，所以要减少 token。系统提示写短一点。限制每次发送的历史长度，比如只发最近十条消息。再就是选能通过你测试的最小模型。以后质量真的下降时，往上调一档就行，因为模型 id 是个旋钮。

MAX_TURNS = 10 def trim(messages: list) -> list: """Send only the most recent turns; older ones cost tokens and add little.""" recent = messages[-MAX_TURNS:] while recent and recent[0]["role"] != "user": # a history must start with the user recent = recent[1:] return recent
What I got wrong我犯过的错Three slips. I picked the biggest model "to be safe" and never checked whether the small one passed. I judged quality on one prompt, which told me nothing. And I did not look at the logs until a user complained that the twin was slow.三个失误。我“为了保险”选了最大的模型，却从没检查小模型能不能通过。我只用一个提示判断质量，什么也说明不了。我也没去看日志，直到有用户抱怨分身太慢。

Common errors常见错误

• KeyError: 'MODEL_ID' The function has no MODEL_ID after you replaced the variables. Fix: update-function-configuration replaces the whole set: list every variable again.
• ThrottlingException: Too many requests Your test loop sent calls faster than the limit. Fix: Add time.sleep(1) between calls, or retry after a pause.
• AccessDenied on put-metric-alarm Your user may not create alarms. Fix: Add the monitoring permission to your group, or ask the account owner.

• KeyError: 'MODEL_ID' 替换环境变量后，函数里没有 MODEL_ID 了。 解决：update-function-configuration 会替换整组变量：每个变量都要再列一遍。
• ThrottlingException: Too many requests 测试循环发送请求太快，超过了限额。 解决：在调用之间加 time.sleep(1)，或停一会再重试。
• AccessDenied on put-metric-alarm 你的用户无权创建告警。 解决：给你的用户组加上监控权限，或请账号所有者处理。

Recap小结Pick the smallest model that passes your own questions.
Keep the model name in a setting so changing size needs no code change.
Log time and tokens per call, set an alarm, and trim old turns to hold cost down.选能通过你自己那些问题的最小模型。
把模型名放进设置里，换大小就不用改代码。
记录每次调用的耗时和 token，设置告警，并裁掉旧的对话轮次来控制成本。
Plain words白话词汇Token: a small piece of text the model reads or writes, and the unit you are billed in. Latency: how long one answer takes.token：模型读写的一小段文字，也是计费的单位。延迟（latency）：得到一次回答要多久。

Takeaways要点回顾

• The model family comes in micro, lite and pro: trade speed and price against reasoning.
• Keep the model id in an environment variable so switching size needs no code change.
• A chat costs input tokens × input price + output tokens × output price.
• Run the same ten questions on every size and compare quality, speed and cost.
• Log one line per model call, and read invocations, duration, errors and tokens.
• Set an alarm so you hear about problems before users tell you.
• Shorter prompts, a history cap and the smallest model that passes are the cost levers.

• 模型家族有 micro、lite 和 pro：在速度、价格与推理能力之间取舍。
• 把模型 id 放进环境变量，这样换大小不用改代码。
• 一次聊天的费用 = 输入 token × 输入单价 + 输出 token × 输出单价。
• 每种大小都跑同样的十道题，比较质量、速度和费用。
• 每次模型调用记一行日志，并关注调用次数、时长、错误和 token。
• 设一个警报，让你比用户先知道问题。
• 更短的提示、限制历史长度、选能通过的最小模型，就是省钱的杠杆。
