"Can the brain live inside our own cloud account, under the same gate rules?" Mei Ling says it can. She will swap the brain, and Sergeant Lee will decide who is allowed to use it.

Step 1 · What a managed model service is第 1 步 · 托管模型服务是什么

Learn先学

A vendor API is a model company's own website that you call with their secret key. A managed model service is the cloud provider offering many companies' models through one API, inside your own account (here the cloud is AWS and the service is Amazon Bedrock). You run no servers, you pay per request, your requests stay in the region you pick, and the cloud's identity service (the gate-pass system from the safe-account lesson) decides who may call it. Your function calls it with its own role: an identity with its own permissions, like a staff pass for the program instead of a person.

厂商 API是模型公司自己的网站，你拿着它给的密钥去调用。托管模型服务则是云服务商把许多公司的模型，通过一个 API 放进你自己的账号里（这里的云是 AWS，服务是 Amazon Bedrock）。你不用运行服务器，按请求付费，请求留在你选的区域里，而且由云的身份服务（账号安全那课的“门禁系统”）来决定谁能调用。你的函数用它自己的角色去调用：角色是程序自己的身份和权限，像给程序发的一张工作证，而不是某个人。

vendor API: function ──(vendor key)──► vendor's servers own invoice, own key managed: function ──(its role)────► model service in YOUR account same invoice, same gate rules

Step 2 · Let people in, and switch the models on第 2 步 · 让人进来，并把模型打开

Learn先学

Two separate doors. First, a permission in the identity service: your user group may call the model service and read logs. Second, an access request for each model you want to use, made once per account in the console. A permission is a small JSON policy: Effect says allow or deny, Action lists the calls it covers, and Resource says on what ("*" means anything). The console steps for this one have changed over time, so read what the console says today instead of trusting an old screenshot.

两扇不同的门。第一，是身份服务里的权限：你的用户组可以调用模型服务并查看日志。第二，是对每个想用的模型提出的访问申请，每个账号在控制台里申请一次。权限写成一小段 JSON 策略：Effect 是允许还是拒绝，Action 列出涉及的调用，Resource 说明作用在什么上（"*" 表示任何东西）。这一步的控制台操作改过好几次，所以请读控制台今天的说明，别信旧截图。

{"Version": "2012-10-17", "Statement": [ {"Effect": "Allow", "Action": ["bedrock:InvokeModel", "bedrock:ListFoundationModels"], "Resource": "*"}, {"Effect": "Allow", "Action": ["logs:DescribeLogGroups", "logs:FilterLogEvents", "logs:GetLogEvents"], "Resource": "*"}]}

Step 3 · Change the code: a client, a model id, a new shape第 3 步 · 改代码：客户端、模型 id、新的格式

Learn先学

Three things change in the function. You make a runtime client for one region. You pass a model id that must exist in that region. And the request and response have a different shape from the vendor's: the system prompt travels in its own field, each message holds a list of content blocks, and the answer hides under output → message → content. The code uses boto3 (pip install boto3).

函数里有三处要改。你要为某个区域建一个运行时客户端；要传一个在该区域存在的模型 id；请求和回应的格式也和厂商的不一样：系统提示放在它自己的字段里，每条消息装的是内容块的列表，答案藏在 output → message → content 下面。代码用 boto3（pip install boto3）。

import os import boto3 client = boto3.client("bedrock-runtime", region_name=os.environ.get("AWS_REGION", "ap-southeast-1")) MODEL_ID = os.environ.get("MODEL_ID", "apac.amazon.nova-lite-v1:0") def ask_managed(system_prompt: str, history: list, user_text: str) -> str: messages = history + [{"role": "user", "content": [{"text": user_text}]}] resp = client.converse( modelId=MODEL_ID, system=[{"text": system_prompt}], messages=messages, inferenceConfig={"maxTokens": 300}, ) return resp["output"]["message"]["content"][0]["text"] # the vendor version it replaces, for comparison: # resp = vendor.chat.completions.create(model=..., messages=[system, *history, user]) # return resp.choices[0].message.content
>>> ask_managed("You are Mei Ling's twin.", [], "What do you work on?") 'I keep the gate-pass system running at the wharf.'

Step 4 · Give the function's own role permission第 4 步 · 给函数自己的角色权限

Learn先学

Your user can call models, so a test from your laptop works. But the deployed function runs as its own role, a separate identity with its own permissions. Add a policy to that role, then redeploy and test. Keep it narrow: only the model family you chose. A model id with a regional prefix (like apac.) is an inference profile, so its permission needs the profile address too.

你的用户能调用模型，所以在笔记本上测试没问题。但部署后的函数是以它自己的角色运行的，这是一个单独的身份，有自己的权限。给这个角色加一条策略，然后重新部署并测试。范围要窄：只放你选的那个模型家族。带区域前缀的模型 id（比如 apac.）是推理配置文件（inference profile），所以权限里也要写上这个配置文件的地址。

{"Effect": "Allow", "Action": "bedrock:InvokeModel", "Resource": [ "arn:aws:bedrock:*::foundation-model/amazon.nova-*", "arn:aws:bedrock:*:*:inference-profile/*.amazon.nova-*"]}

Step 5 · Two traps: the id and the messages第 5 步 · 两个陷阱：模型 id 和消息

Learn先学

Model id and region must match. Some models exist only in some regions, or need a regional prefix on the id; otherwise you get "model not found". The code below uses an apac. id with an ap-southeast-1 client. If you use another region, the prefix changes (for example us. for US regions), so check the console's model list for your region. Messages must alternate between user and assistant, and the system prompt must not be a message at all: it goes in the system field. The small helper below rebuilds the history safely. The memory bucket stores each turn as one line like {"role": "user", "text": "Hi, I am Siti"}; to_messages turns those into the shape that ask_managed expects as history, for example ask_managed(prompt, to_messages(saved), "What is my name?").

模型 id 和区域必须对得上。有些模型只在部分区域有，或者 id 前面要加区域前缀，否则会得到“找不到模型”。下面的代码在 ap-southeast-1 的客户端里用了 apac. 开头的 id。换到别的区域，前缀也要跟着变（比如美国区域用 us.），所以要以控制台的模型列表为准。消息必须在用户和助手之间交替，而系统提示根本不能是一条消息：它要放进 system 字段。下面的小函数会安全地重建历史记录。记忆存储桶把每一轮存成这样的一行：{"role": "user", "text": "你好，我是 Siti"}；to_messages 把它们变成 ask_managed 想要的 history 格式，例如 ask_managed(prompt, to_messages(saved), "我叫什么？")。

def to_messages(saved: list) -> list: """saved: [{"role": ..., "text": ...}] read from the memory bucket.""" messages = [] for m in saved: if m["role"] not in ("user", "assistant"): continue # a stray system line would break the call if messages and messages[-1]["role"] == m["role"]: messages[-1]["content"][0]["text"] += "\n" + m["text"] # keep it alternating else: messages.append({"role": m["role"], "content": [{"text": m["text"]}]}) return messages
What I got wrong我犯过的错Three slips. The model id and the region did not match, so I got "model not found" (some models live only in some regions, or need a regional prefix on the id). I gave my user permission but forgot the function's role needs it too. And a stray system message in the history broke the call, because messages must alternate between user and assistant.三个失误。模型 id 和区域对不上，所以报“找不到模型”（有些模型只在部分区域有，或者 id 前面要加区域前缀）。我给了自己的用户权限，却忘了函数的角色也需要。还有历史里混进一条系统消息，把调用弄坏了，因为消息必须在用户和助手之间交替。

Now make it yours现在把它变成你的

What changed这一课之后Now the product's brain runs inside the wharf's own cloud account: one invoice for Mr Ong, and no vendor key in a settings file. The next problem is that Mei Ling picked the biggest model to be safe, and when Mr Ong asks what a month will cost, she has no answer.现在产品的大脑运行在码头自己的云账户里：Ong 先生只收到一张发票，设置文件里也没有厂商密钥了。下一个问题是 Mei Ling 为了保险选了最大的模型，Ong 先生问一个月要花多少钱，她答不上来。

Common errors常见错误

• AccessDeniedException: You don't have access to the model Model access was not requested in this region, or the role lacks bedrock:InvokeModel. Fix: Request the model in the console for the same region, and add the action to the role.
• ValidationException: Invalid model identifier The model id is wrong, or needs the regional prefix such as apac.. Fix: Copy the id from the console list and set it in MODEL_ID.
• ValidationException: A conversation must start with a user message The saved history starts with the assistant or repeats a role. Fix: Run it through to_messages so roles alternate and start with the user.

• AccessDeniedException: You don't have access to the model 没有在这个区域申请模型权限，或角色缺少 bedrock:InvokeModel。 解决：在同一区域的控制台申请该模型，并给角色加上这个操作。
• ValidationException: Invalid model identifier 模型 id 写错，或缺少区域前缀（如 apac.）。 解决：从控制台列表复制 id，设置到 MODEL_ID。
• ValidationException: A conversation must start with a user message 保存的历史以助手开头，或角色重复。 解决：先用 to_messages 处理，使角色交替并以用户开头。

Recap小结A managed model is called with the function role, not a separate vendor key.
The call shape differs (converse), so convert saved history first.
Grant only InvokeModel on the model family you use.托管模型用函数的角色调用，不需要另一把厂商密钥。
调用格式不同（converse），所以先转换已保存的历史。
只授予所用模型系列的 InvokeModel 权限。
Plain words白话词汇Role: an identity that code borrows, with its own list of allowed actions. Region: the city-sized area where your cloud resources live.角色（role）：代码借用的一种身份，带有自己的允许操作清单。区域（region）：云资源所在的、相当于一座城市的范围。

Takeaways要点回顾

• A managed model service gives many vendors' models through one API inside your cloud account.
• You run no servers, pay per request, keep requests in your region and control access with roles.
• Permission to call the service and access to each model are two separate switches.
• The code change is small: a regional client, a model id and a new request and response shape.
• The deployed function needs permission on its own role, not just on your user.
• Model id and region must match; messages must alternate, with the system prompt in its own field.
• Managed means less to run and more to configure: the access setup is where the time goes.

• 托管模型服务通过一个 API，把许多厂商的模型放进你的云账号里。
• 你不用运行服务器，按请求付费，请求留在你的区域，并用角色控制访问。
• 调用服务的权限，和每个模型的访问权，是两个独立的开关。
• 代码改动很小：一个区域客户端、一个模型 id，以及新的请求和回应格式。
• 部署后的函数要在它自己的角色上有权限，光你的用户有还不够。
• 模型 id 和区域必须对得上；消息要交替出现，系统提示放在它自己的字段里。
• 托管意味着要运行的少了、要配置的多了：时间花在访问设置上。
