Step 1 · A fresh start第 1 步 · 从头开始

Learn先学

Begin from nothing, so the pipeline makes everything and the state matches the files exactly. Destroy the environments you built by hand, then delete their workspaces. You cannot delete the workspace you are standing in, so move to default first.

从零开始，这样一切都由流水线创建，状态也和文件完全吻合。先销毁你手工建的那些环境，再删掉它们的工作区。你没法删除自己正站着的工作区，所以先切到 default。

./destroy.sh dev ./destroy.sh test cd infra terraform workspace select default terraform workspace delete dev terraform workspace delete test terraform workspace list # only default is left

Step 2 · The one-time setup第 2 步 · 只做一次的准备

Learn先学

Some things are made once; others happen on every run. The once-only list is: the state bucket and lock table, the OIDC provider and the pipeline role, the repository secrets and variables, and the GitHub environments with a required reviewer on prod. Everything else belongs to the pipeline.

有些东西只做一次；有些在每次运行时发生。只做一次的清单是：状态存储桶和锁表、OIDC 提供者和流水线角色、仓库的密钥和变量，以及 GitHub 环境（prod 上设必需的审批人）。其余的都归流水线。

once, by hand (from the last two lessons): 1. state bucket + lock table (shared state and stale locks) 2. OIDC provider + role "wharf-pipeline" 3. gh secret set AWS_ACCOUNT_ID / STATE_BUCKET ; gh variable set AWS_REGION 4. GitHub environments: dev, test, prod (prod: required reviewer = you) on every run, by the robot: build, plan, apply, upload the site, print the addresses

Step 3 · Push for dev, then run test and prod第 3 步 · 推送得到 dev，再运行 test 和 prod

Learn先学

Commit and push to main: dev deploys by itself. Then start the manual workflow for test, and for prod. The prod run pauses at the approval. Before you approve, open the plan job's log. A fresh environment should show only things to add. If the plan says something is going to be destroyed and you did not expect that, stop.

提交并推送到 main：dev 会自己部署。然后给 test 启动手动工作流，再给 prod 启动。prod 的运行会停在审批那里。批准之前，先打开 plan 任务的日志。一个全新的环境应该只有要新增的东西。如果 plan 说有东西要被销毁，而你没料到，就停下来。

git add . && git commit -m "twin: first pipeline run" && git push origin main gh run watch # dev deploys on its own gh workflow run manual.yml -f environment=test -f action=deploy gh workflow run manual.yml -f environment=prod -f action=deploy gh run list --workflow manual.yml # prod shows "waiting": read the plan, then approve

Step 4 · Test each twin, and beat the cache第 4 步 · 测试每一个分身，并对付缓存

Learn先学

Open each printed address and chat with it twice: does it answer, and does it remember? A green pipeline only means the steps ran. If the site still shows old files, the CDN is serving its cached copies. Tell it to drop them with an invalidation after the upload, and give the pipeline role permission to do that (cloudfront:CreateInvalidation).

打开每个打印出来的地址，各聊两次：它能回答吗？它记得吗？流水线是绿的，只说明步骤跑完了。如果网站仍显示旧文件，是 CDN 在提供它缓存的副本。上传之后用一次失效（invalidation）告诉它丢掉缓存，并给流水线角色这样做的权限（cloudfront:CreateInvalidation）。

# outputs.tf: one more output, next to site_url output "cdn_id" { value = aws_cloudfront_distribution.site.id } # deploy.sh: after the "aws s3 sync" line aws cloudfront create-invalidation --distribution-id "$(terraform output -raw cdn_id)" --paths "/*"

Step 5 · Ship a real change through the pipeline第 5 步 · 让一个真实的改动走一遍流水线

Learn先学

Auntie Siti reports a bug: after she sends a message, the chat box loses focus, so she cannot type the next one. The cause is that the box is disabled while the twin thinks, and nobody gives the cursor back. Fix it in the front end, then ship it exactly as a real change: push, watch dev, check it, run test, then prod.

Siti 阿姨报告了一个 bug：她发完一条消息后，聊天框失去焦点，没法输入下一条。原因是分身思考时输入框被禁用了，而没人把光标还回去。在前端修好它，然后像真实的改动那样发布：推送、看 dev、检查、运行 test，再运行 prod。

const API_URL = "https://abc123.execute-api.ap-southeast-1.amazonaws.com"; // the api address deploy.sh prints const input = document.querySelector("#chat-input"); const log = document.querySelector("#chat-log"); function addBubble(who, text) { const p = document.createElement("p"); p.className = who; p.textContent = text; log.append(p); } async function send() { const text = input.value.trim(); if (!text) return; input.value = ""; input.disabled = true; addBubble("you", text); try { const r = await fetch(API_URL + "/chat", { method: "POST", headers: { "content-type": "application/json" }, body: JSON.stringify({ message: text }), }); const data = await r.json(); addBubble("twin", data.reply); } finally { input.disabled = false; input.focus(); // the fix: give the cursor back } }

Step 6 · Read what the pipeline did第 6 步 · 读一读流水线做了什么

Learn先学

Automation is only trustworthy if you can look back at it. Three places keep the record. The Actions run page shows every step, the plan, and who approved prod. The cloud console shows what exists now: the function and its settings. The logs service shows what the twin did when real visitors chatted.

自动化只有在你能回头查看时才值得信任。有三个地方保存着记录。Actions 运行页面显示每一步、plan，以及谁批准了 prod。云控制台显示现在存在什么：函数和它的设置。日志服务显示真实访客聊天时分身做了什么。

gh run list --limit 5 # the pipeline's own history aws logs tail /aws/lambda/wharf-twin-dev-twin --since 1h # the twin's own log lines

Step 7 · Tear it all down, by pipeline第 7 步 · 用流水线把它们全拆掉

Learn先学

The project is only finished when the teardown is automated too. Run the same manual workflow with the action destroy for each environment, prod included (it waits for approval again). Then check, the way you did before: empty state list, nothing in the command line, nothing in the console. Look at the cost page a day later, since charges appear with a delay.

拆除也自动化了，项目才算完成。对每个环境运行同一个手动工作流，动作选 destroy，prod 也不例外（它会再次等待批准）。然后像之前那样检查：状态清单为空、命令行里什么都没有、控制台里什么都没有。过一天再去看费用页面，因为费用是有延迟才出现的。

gh workflow run manual.yml -f environment=dev -f action=destroy gh workflow run manual.yml -f environment=test -f action=destroy gh workflow run manual.yml -f environment=prod -f action=destroy # waits for approval aws s3 ls | grep wharf-twin # should print nothing aws lambda list-functions --query "Functions[?starts_with(FunctionName, 'wharf-twin')].FunctionName" # []
What I got wrong我犯过的错Three slips. The pipeline passed, but the site still showed old files, because the CDN cache needed clearing. I left prod running over a weekend. And I approved prod without reading the plan in the log first.三个失误。流水线通过了，网站却仍显示旧文件，因为 CDN 缓存需要清除。我把 prod 开着过了一个周末。我还在没读日志里 plan 的情况下就批准了 prod。

Takeaways要点回顾

• Start fresh: destroy hand-made environments and delete old workspaces, so state matches the files.
• Do the one-time setup once: shared state, the pipeline role, secrets and environments.
• A push deploys dev; a manual run gives test and prod, with approval before prod.
• Read the plan in the log before you approve anything.
• A green pipeline is not proof: open each twin, and clear the CDN cache after an upload.
• Ship real changes the same way, through the same door.
• Automation is only done when teardown is automated too.

• 从头开始：销毁手工建的环境，删掉旧工作区，让状态和文件吻合。
• 只做一次的准备只做一次：共享状态、流水线角色、密钥和环境。
• 推送部署 dev；手动运行得到 test 和 prod，prod 之前要批准。
• 批准任何东西之前，先读日志里的 plan。
• 流水线是绿的不算证据：打开每个分身看看，上传之后要清 CDN 缓存。
• 真实的改动也走同一条路、同一扇门。
• 拆除也自动化了，自动化才算完成。
