Dev, test, prod from one push一推三环境

Put it all together: one push deploys dev, a manual run gives test and prod, and teardown is a workflow too · ~60 min · project把所有东西合在一起：一次推送部署 dev，手动运行得到 test 和 prod，拆除也是一个工作流 · 约 60 分钟 · 项目

Step 1 · Start fresh, then do the one-time setup第 1 步 · 从头开始，做一次性准备

Learn先学

The product is a digital twin: a chat site that answers as one person, with a Python backend and a static front end, described as Terraform files in infra/. Each environment (dev, test, prod) is one Terraform workspace, a separate copy of the state. Begin from nothing so the pipeline makes everything and the state matches the files: destroy the hand-made environments, then delete their workspaces (move to default first; you cannot delete the one you stand in). Some things are made once by hand, the rest belong to the pipeline.

这个产品是一个数字分身：一个替某个人回答的聊天网站，有 Python 后端和静态前端，用 infra/ 里的 Terraform 文件描述。每个环境（dev、test、prod）是一个 Terraform 工作区，也就是一份独立的状态。从零开始，让一切都由流水线创建、状态和文件吻合：销毁手工建的环境，再删掉它们的工作区（先切到 default；不能删除自己站着的那个）。有些东西手工做一次，其余归流水线。

cd infra terraform workspace select dev terraform destroy -var="environment=dev" # remove what you made by hand terraform workspace select default # step out of it first terraform workspace delete dev # repeat for test and prod if they exist
once, by hand: 1. state bucket + lock table 2. OIDC provider + role "wharf-pipeline" 3. repository secrets and variables 4. GitHub environments: dev, test, prod (prod: required reviewer = you) on every run, by the robot: build, plan, apply, upload the site, clear the cache of the CDN (copies of the site kept near visitors), print the addresses

Step 2 · Push for dev, run test and prod第 2 步 · 推送得到 dev，运行 test 和 prod

Learn先学

Push to main: dev deploys by itself. Then start the manual workflow for test and prod; prod pauses at the approval. Before you approve, read the plan job's log: a fresh environment should show only things to add. Anything to destroy that you did not expect means stop.

推送到 main：dev 自己部署。然后给 test 和 prod 启动手动工作流；prod 会停在审批处。批准之前先读 plan 任务的日志：全新的环境应该只有要新增的东西。出现你没料到的销毁，就停下来。

git add . && git commit -m "twin: first pipeline run" && git push origin main gh run watch # dev deploys on its own gh workflow run manual.yml -f environment=test gh workflow run manual.yml -f environment=prod gh run list --workflow manual.yml # prod shows "waiting": read the plan, then approve

Step 3 · Test each twin, and beat the cache第 3 步 · 测试每个分身，并对付缓存

Learn先学

A green pipeline only means the steps ran. Open each printed address and chat twice: does it answer, and does it remember? If the site shows old files, the CDN (the service that keeps copies of your files near visitors; on AWS it is CloudFront) is serving cached copies. The deploy script's create-invalidation line after the upload fixes that, and the pipeline role needs cloudfront:CreateInvalidation.

流水线是绿的，只说明步骤跑完了。打开每个打印出的地址，各聊两次：它能回答吗？它记得吗？如果网站显示旧文件，是 CDN 在提供缓存的副本。部署脚本里上传之后的 create-invalidation 那一行能解决它，流水线角色需要 cloudfront:CreateInvalidation 权限。

Step 4 · Tear it all down, by pipeline第 4 步 · 用流水线全部拆掉

Learn先学

The project is done only when teardown is automated too. Never delete by hand in the console: the state would still list the thing as existing, and no log would show who removed it. Run the manual workflow with destroy for each environment (prod waits for approval again), then check: empty state list, nothing in the command line, nothing in the console. Look at the cost page a day later, since charges appear with a delay. The action choice is one more input on the manual workflow, next to environment; the first box shows the two lines to add.

拆除也自动化了，项目才算完成。绝不要在控制台里手工删除：状态里还会写着那样东西存在，也没有日志说明是谁删的。对每个环境用 destroy 运行手动工作流（prod 会再次等待批准），然后检查：状态清单为空、命令行里什么都没有、控制台里什么都没有。过一天再看费用页面，因为费用有延迟。action 是手动工作流上多加的一个输入，和 environment 并列；第一个代码框是要加的两行。

# under inputs, next to environment: action: { type: choice, options: [deploy, destroy], default: deploy } # the last step of the apply job picks the script by name: - run: ./${{ inputs.action }}.sh "${{ inputs.environment }}" # deploy.sh, or destroy.sh (terraform destroy)
gh workflow run manual.yml -f environment=dev -f action=destroy gh workflow run manual.yml -f environment=test -f action=destroy gh workflow run manual.yml -f environment=prod -f action=destroy # waits for approval aws s3 ls | grep wharf-twin # should print nothing

Common errors常见错误

• Workspace "dev" is not empty Fix: Destroy first, then delete the workspace.
• A prod run sits at "waiting" Fix: Open the run, read the plan, then press Approve.
• The page still shows the old site Fix: Keep the create-invalidation line in deploy.sh.

• Workspace "dev" is not empty 解决：先 destroy，再删除工作区。
• A prod run sits at "waiting" 解决：打开这次运行，读完计划，再点批准。
• The page still shows the old site 解决：在 deploy.sh 里保留 create-invalidation 那一行。

Takeaways要点回顾

• Start fresh so the state matches the files; do the one-time setup once.
• A push deploys dev; a manual run gives test and prod, with approval before prod.
• Read the plan in the log before you approve.
• A green pipeline is not proof: open each twin and clear the CDN cache.
• Automation is done only when teardown is automated too.

• 从头开始让状态和文件吻合；一次性准备只做一次。
• 推送部署 dev；手动运行得到 test 和 prod，prod 之前要批准。
• 批准之前先读日志里的 plan。
