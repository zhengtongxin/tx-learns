Push to deploy推送即部署

Make git push the only deploy step: a robot builds, plans and applies for you, signs in without long-lived keys and waits for approval before production · ~40 min · hands-on让 git push 成为唯一的部署步骤：机器人替你构建、做计划、apply，登录时不用长期密钥，生产环境还要等人批准 · 约 40 分钟 · 动手实践

Step 1 · Git, with a careful ignore file第 1 步 · 放进 git，并写好忽略文件

Learn先学

The project here is a small web product (a backend and a front end) whose cloud resources are written down as Terraform files in infra/, with one script, deploy.sh, that builds and deploys it. Terraform keeps a state file listing what it has created; it lives in a storage bucket, and a small lock table stops two runs from changing it at once. A robot can only deploy what is in the repository, so the whole project goes into git. Keep out what is private or rebuildable: state, installed packages, build output, env files and keys. Write .gitignore before the first commit and read git status before you commit.

这里的项目是一个小网页产品（后端加前端），它的云资源写成 infra/ 里的 Terraform 文件，由一个脚本 deploy.sh 负责构建和部署。Terraform 用一份状态文件记下它建过什么；状态放在存储桶里，一张小小的锁表防止两次运行同时改它。机器人只能部署仓库里有的东西，所以整个项目都放进 git。把私密的或可重建的挡在外面：状态、装好的包、构建产物、环境文件和密钥。第一次提交前写好 .gitignore，提交前读一遍 git status。

.terraform/ *.tfstate *.tfstate.* *.tfvars node_modules/ backend/package/ backend/twin.zip frontend/dist/ .env *.pem

Step 2 · A workflow that deploys dev on every push第 2 步 · 每次推送都部署 dev 的工作流

Learn先学

A GitHub Actions workflow is a text file in .github/workflows/: when this happens, run these steps on a fresh machine. This one runs on a push to main and calls your deploy script. Account-specific values (account id, region, state bucket) come from GitHub secrets (hidden in logs) and variables (plain values), never from the files. Set them with printf %s "value" | gh secret set NAME so no stray newline sneaks in. In the file, ${{ ... }} is a placeholder that GitHub fills in with the secret or variable before the step runs, and an ARN (the arn:aws:... text) is the cloud's full name for one thing, here the role the pipeline takes on. Two more lines to know: environment: dev picks a GitHub environment, a named target such as dev or prod that can carry its own rules (Step 4 shows how). The terraform init line tells Terraform where its state lives: the state bucket holds the state file, and the lock table (wharf-tf-locks) holds a short-lived note saying “a run is changing this now”, so two runs cannot change it at once.

GitHub Actions 工作流是 .github/workflows/ 里的文本文件：发生这件事时，在一台全新的机器上运行这些步骤。这个在推送到 main 时运行，并调用你的部署脚本。因账号而异的值（账号 id、区域、状态桶）来自 GitHub 的密钥（日志里隐藏）和变量（普通值），绝不来自文件。用 printf %s "value" | gh secret set NAME 设置，这样不会混进多余的换行。文件里的 ${{ ... }} 是占位符，GitHub 在运行这一步之前把它换成对应的密钥或变量；ARN（arn:aws:... 那串文字）是云上某一样东西的完整名字，这里指流水线要扮演的角色。还有两行要认识：environment: dev 选择一个 GitHub 环境，也就是 dev 或 prod 这样的命名目标，可以有自己的规则（第 4 步会讲）。terraform init 那行告诉 Terraform 它的状态放在哪里：状态桶存放状态文件，锁表（wharf-tf-locks）记一条短暂的“有一次运行正在改它”的标记，这样两次运行就不能同时修改。

name: deploy-dev on: push: branches: [main] permissions: id-token: write # lets the job ask GitHub for a short-lived identity token contents: read jobs: deploy: runs-on: ubuntu-latest environment: dev # a GitHub environment: a named target with its own rules (Step 4) steps: - uses: actions/checkout@v4 - uses: hashicorp/setup-terraform@v3 - uses: aws-actions/configure-aws-credentials@v4 with: role-to-assume: arn:aws:iam::${{ secrets.AWS_ACCOUNT_ID }}:role/wharf-pipeline aws-region: ${{ vars.AWS_REGION }} - working-directory: infra run: terraform init -backend-config="bucket=${{ secrets.STATE_BUCKET }}" -backend-config="region=${{ vars.AWS_REGION }}" -backend-config="dynamodb_table=wharf-tf-locks" - run: ./deploy.sh dev

Step 3 · No keys on disk: a short-lived token第 3 步 · 磁盘上没有密钥：短期令牌

Learn先学

A stored access key is a permanent pass that can leak. Use OIDC instead: each run, GitHub gives the job a short-lived signed token naming its repository and branch or environment. You tell the cloud once to trust GitHub and let this one named repository take the pipeline role; it swaps the token for credentials that expire in about an hour. Reading the policy below: Principal is who may ask (GitHub's token service), Action is what they may do (take on this role), and Condition narrows it. Its sub line must match exactly what your repository sends. The * means “anything here”: fine after environment:, never in place of the repository name, or any repository on GitHub could deploy to your account.

存着的访问密钥是可能泄露的永久通行证。改用 OIDC：每次运行，GitHub 给任务一个短期的签名令牌，写明仓库和分支或环境。你只需对云说一次：信任 GitHub，并允许这一个指名的仓库扮演流水线角色；云会把令牌换成大约一小时就过期的凭证。读下面的策略：Principal 是谁可以来请求（GitHub 的令牌服务），Action 是它能做什么（扮演这个角色），Condition 再把范围收窄。其中 sub 一行必须和你的仓库实际发送的完全匹配。* 表示“这里什么都行”：放在 environment: 后面可以，绝不能代替仓库名，否则 GitHub 上任何仓库都能部署到你的账号。

{"Version": "2012-10-17", "Statement": [{ "Effect": "Allow", "Principal": {"Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com"}, "Action": "sts:AssumeRoleWithWebIdentity", "Condition": { "StringEquals": {"token.actions.githubusercontent.com:aud": "sts.amazonaws.com"}, "StringLike": {"token.actions.githubusercontent.com:sub": [ "repo:wharf-it/twin:environment:*", "repo:wharf-it/twin:ref:refs/heads/main"]}}}]}

Step 4 · Approval before prod第 4 步 · 上 prod 前先批准

Learn先学

A GitHub environment (dev, test, prod) is a named target with its own rules. Add required reviewers to prod in the repository settings: any job using it pauses until a person approves. A manual workflow can split the work in two jobs: plan only shows what would change, then apply uses the chosen environment, so prod waits for approval. The reviewer reads the plan first.

GitHub 环境（dev、test、prod）是有自己规则的命名目标。在仓库设置里给 prod 加上必需的审批人：用到它的任务会暂停，直到有人批准。手动工作流可以拆成两个任务：plan 只显示将会改什么，apply 使用所选环境，所以 prod 要等批准。审批人先读 plan。

name: manual on: workflow_dispatch: inputs: environment: { type: choice, options: [dev, test, prod], required: true } jobs: plan: runs-on: ubuntu-latest steps: # same checkout, Terraform, sign-in and init steps as deploy.yml, then: - run: | cd infra terraform workspace select -or-create "${{ inputs.environment }}" terraform plan -var="environment=${{ inputs.environment }}" apply: needs: plan runs-on: ubuntu-latest environment: ${{ inputs.environment }} # for prod, this line makes the job wait for a person steps: # same setup steps, then: - run: ./deploy.sh "${{ inputs.environment }}"

Now make it yours现在把它变成你的

Common errors常见错误

• Not authorized to perform sts:AssumeRoleWithWebIdentity Fix: Check the trust policy's sub line: repo:OWNER/REPO:ref:refs/heads/main.
• Credentials could not be loaded Fix: Add id-token: write under permissions.
• Backend configuration changed Fix: Pass the -backend-config values as in the workflow step.

• Not authorized to perform sts:AssumeRoleWithWebIdentity 解决：检查信任策略的 sub 行：repo:所有者/仓库:ref:refs/heads/main。
• Credentials could not be loaded 解决：在 permissions 下加上 id-token: write。
• Backend configuration changed 解决：像工作流那一步一样传入 -backend-config 的值。

Takeaways要点回顾

• Put the project in git; keep state, packages, env files and keys out.
• A workflow is a text file: when this happens, run these steps.
• Account-specific values live in repository secrets and variables, never in files.
• OIDC replaces stored keys: GitHub proves who it is, and the cloud lets one named repository assume a role.
• Environments can require approval before prod; the reviewer reads the plan first.

• 把项目放进 git；状态、包、环境文件和密钥留在外面。
• 工作流是文本文件：发生这件事时，运行这些步骤。
• 因账号而异的值放在仓库密钥和变量里，绝不放进文件。
• OIDC 取代存放的密钥：GitHub 证明自己是谁，云只让一个指名的仓库扮演角色。
• 环境可以要求上 prod 前先批准；审批人先读 plan。
