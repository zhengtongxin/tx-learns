Push to deploy with GitHub Actions用 GitHub Actions 一推就部署

Make git push the only deploy step: a robot builds, plans and applies for you, signs in without long-lived keys and waits for approval before production · ~40 min · hands-on让 git push 成为唯一的部署步骤：机器人替你构建、做计划、apply，登录时不用长期密钥，生产环境还要等人批准 · 约 40 分钟 · 动手实践

Where we left off上回讲到

Last time the state became shared, so the product could be deployed from anywhere. Today it fails Kumar's rule that nobody carries boxes by hand, and Sergeant Lee's rule that no permanent key is stored. We fix it with a GitHub Actions workflow that signs in with a short-lived token and waits for Mr Ong before prod.

上回，状态变成共享的，产品可以从任何地方部署。今天它违反了 Kumar 的规矩（不许人手搬箱子）和 Lee 警官的规矩（不许存永久密钥）。我们的办法是用 GitHub Actions 工作流，靠短期令牌登录，并在上生产前等 Ong 先生批准。

The story故事

Kumar has a rule for the conveyor belt: "Nobody carries boxes by hand." The state is now shared, so the twin can be deployed from anywhere. Mei Ling wants the robot to do it: she pushes, the robot builds and applies. Sergeant Lee adds a condition: the robot must not hold a permanent key to the account, and nothing reaches production without a person saying yes.

Kumar 对传送带有一条规矩：“谁也不许徒手搬箱子。”状态现在是共享的，分身可以在任何地方部署。Mei Ling 想让机器人来做：她一推送，机器人就构建并 apply。Lee 警官加了一个条件：机器人不能持有账号的永久密钥，而且没有人点头，什么都不能进生产环境。

Step 1 · Put the project in git, with a careful ignore file第 1 步 · 把项目放进 git，并写一份仔细的忽略文件

Learn先学

A robot can only deploy what is in the repository, so the whole project goes into git. The danger is committing what must stay private or can be rebuilt: state, installed packages, build output, environment files and keys. Write the .gitignore before the first commit, then read the list git status shows you before you commit it.

机器人只能部署仓库里有的东西，所以整个项目都要放进 git。危险在于把该保密、或者可以重新生成的东西也提交了：状态、装好的包、构建产物、环境文件和密钥。第一次提交之前先写好 .gitignore，提交之前再读一遍 git status 给你的清单。

# .gitignore .terraform/ *.tfstate *.tfstate.* *.tfvars node_modules/ backend/package/ backend/twin.zip frontend/dist/ .env *.pem
git init -b main git add . git status # read every line before you commit
On branch main Changes to be committed: new file: deploy.sh new file: infra/main.tf (no .tfstate, no .env)

Step 2 · A workflow that deploys dev on every push第 2 步 · 每次推送都部署 dev 的工作流

Learn先学

A GitHub Actions workflow is a text file in .github/workflows/ that tells GitHub: when this happens, run these steps on a fresh machine. This one runs when something is pushed to main, and it deploys dev with the very script you wrote. The Ubuntu runner already has Python, Node, zip and the AWS command line, so only Terraform needs installing. A second workflow, which lets you deploy or destroy any environment by hand, comes in step 5.

GitHub Actions 工作流是 .github/workflows/ 里的一个文本文件，告诉 GitHub：发生这件事时，在一台全新的机器上运行这些步骤。这个工作流在有东西推送到 main 时运行，用你写好的那个脚本部署 dev。Ubuntu 运行器已经自带 Python、Node、zip 和 AWS 命令行，所以只需要安装 Terraform。第二个工作流（让你手动部署或销毁任意环境）在第 5 步。

# .github/workflows/deploy.yml name: deploy-dev on: push: branches: [main] permissions: id-token: write # lets the job ask GitHub for a short-lived identity token contents: read jobs: deploy: runs-on: ubuntu-latest environment: dev env: STATE_BUCKET: ${{ secrets.STATE_BUCKET }} steps: - uses: actions/checkout@v4 - uses: hashicorp/setup-terraform@v3 - uses: aws-actions/configure-aws-credentials@v4 with: role-to-assume: arn:aws:iam::${{ secrets.AWS_ACCOUNT_ID }}:role/wharf-pipeline aws-region: ${{ vars.AWS_REGION }} - name: Connect to the shared state working-directory: infra run: terraform init -backend-config="bucket=$STATE_BUCKET" -backend-config="region=$AWS_REGION" -backend-config="dynamodb_table=wharf-tf-locks" - run: ./deploy.sh dev

Step 3 · Secrets and variables, not files第 3 步 · 放进密钥和变量，不放进文件

Learn先学

Values that differ per account, such as the account id, the region and the state bucket name, must not be written in the files. GitHub keeps them in two places: secrets (hidden in logs, for anything sensitive) and variables (plain values, fine to show). The workflow reads them as ${{ secrets.NAME }} and ${{ vars.NAME }}. Set a model id the same way if you choose it outside the files. A tip: pipe the value in with printf %s, so no stray space or newline sneaks in.

因账号而异的值，比如账号 id、区域和状态存储桶的名字，不能写在文件里。GitHub 把它们放在两个地方：密钥（secrets）（在日志里会隐藏，放敏感的东西）和变量（variables）（普通的值，显示出来也没关系）。工作流用 ${{ secrets.NAME }} 和 ${{ vars.NAME }} 来读。如果模型 id 是在文件之外选定的，也用同样的办法设置。一个小技巧：用 printf %s 把值管道传进去，这样不会混进多余的空格或换行。

printf %s "111122223333" | gh secret set AWS_ACCOUNT_ID printf %s "wharf-tf-state-111122223333" | gh secret set STATE_BUCKET printf %s "ap-southeast-1" | gh variable set AWS_REGION # in the workflow: ${{ secrets.STATE_BUCKET }} ${{ vars.AWS_REGION }}
✓ Set Actions secret AWS_ACCOUNT_ID for wharf-it/twin ✓ Set Actions secret STATE_BUCKET for wharf-it/twin ✓ Created variable AWS_REGION for wharf-it/twin

Step 4 · No keys on disk: sign in with a short-lived token第 4 步 · 磁盘上没有密钥：用短期令牌登录

Learn先学

A long-lived access key in a secret is a permanent pass that can leak. Instead, use OIDC (OpenID Connect). Each run, GitHub gives the job a short-lived signed token that says who it is: which repository, which branch or environment. You tell the cloud once: "trust tokens from GitHub, and let this one named repository take the pipeline role". The cloud swaps the token for temporary credentials that expire in about an hour.

放在密钥里的长期访问密钥，是一张可能泄露的永久通行证。改用 OIDC（OpenID Connect）。每次运行，GitHub 会给任务一个短期的、带签名的令牌，说明它是谁：哪个仓库、哪个分支或环境。你只需对云说一次：“信任来自 GitHub 的令牌，并允许这一个指名的仓库扮演流水线角色”。云会用令牌换来一份大约一小时就过期的临时凭证。

The token's subject line names the repository and the branch or environment. GitHub has introduced a newer, longer format for it, so while you move across, let the trust policy accept both the old and the new pattern, whatever your repository actually sends.

令牌里的主体（subject）那一行写着仓库和分支或环境。GitHub 推出了更新、更长的格式，所以在过渡期间，让信任策略同时接受新旧两种写法，以你的仓库实际发送的为准。

# once per account aws iam create-open-id-connect-provider --url https://token.actions.githubusercontent.com --client-id-list sts.amazonaws.com # (if your command line asks for a thumbprint, add the provider in the console instead)
# the pipeline role's trust policy {"Version": "2012-10-17", "Statement": [{ "Effect": "Allow", "Principal": {"Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com"}, "Action": "sts:AssumeRoleWithWebIdentity", "Condition": { "StringEquals": {"token.actions.githubusercontent.com:aud": "sts.amazonaws.com"}, "StringLike": {"token.actions.githubusercontent.com:sub": [ "repo:wharf-it/twin:environment:*", "repo:wharf-it/twin:ref:refs/heads/main"]}}}]}

Step 5 · Environments, a manual workflow and approval before prod第 5 步 · 环境、手动工作流和上生产前的批准

Learn先学

A GitHub environment (dev, test, prod) is a named target with its own rules. In the repository settings, add required reviewers to prod: any job that uses that environment pauses until a person approves it. The manual workflow below has two jobs. The first, plan, only shows what would change. The second, apply, uses the chosen environment, so for prod it waits for approval. The reviewer reads the first job's log, then decides.

GitHub 环境（dev、test、prod）是一个有名字的目标，可以有自己的规则。在仓库设置里给 prod 加上必需的审批人：任何用到这个环境的任务都会暂停，直到有人批准。下面的手动工作流有两个任务。第一个 plan 只显示将会改什么。第二个 apply 使用所选的环境，所以对 prod 来说它要等批准。审批人先读第一个任务的日志，再做决定。

Choose the branch in the "Run workflow" menu with care. The role trusts only main, so a run from any other branch is refused.

在“Run workflow”菜单里选分支要当心。这个角色只信任 main，所以从别的分支发起的运行会被拒绝。

# .github/workflows/manual.yml name: manual on: workflow_dispatch: inputs: environment: { description: Which environment, type: choice, options: [dev, test, prod], required: true } action: { description: What to do, type: choice, options: [deploy, destroy], required: true } permissions: id-token: write contents: read env: ENVIRONMENT: ${{ inputs.environment }} ACTION: ${{ inputs.action }} STATE_BUCKET: ${{ secrets.STATE_BUCKET }} jobs: plan: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: hashicorp/setup-terraform@v3 - uses: aws-actions/configure-aws-credentials@v4 with: role-to-assume: arn:aws:iam::${{ secrets.AWS_ACCOUNT_ID }}:role/wharf-pipeline aws-region: ${{ vars.AWS_REGION }} - working-directory: infra run: terraform init -backend-config="bucket=$STATE_BUCKET" -backend-config="region=$AWS_REGION" -backend-config="dynamodb_table=wharf-tf-locks" - name: Show the plan run: | if [ "$ACTION" = "deploy" ]; then ./deploy.sh "$ENVIRONMENT" plan else cd infra terraform workspace select "$ENVIRONMENT" terraform plan -destroy -var="environment=$ENVIRONMENT" fi apply: needs: plan runs-on: ubuntu-latest environment: ${{ inputs.environment }} # for prod, this line makes the job wait for a person steps: - uses: actions/checkout@v4 - uses: hashicorp/setup-terraform@v3 - uses: aws-actions/configure-aws-credentials@v4 with: role-to-assume: arn:aws:iam::${{ secrets.AWS_ACCOUNT_ID }}:role/wharf-pipeline aws-region: ${{ vars.AWS_REGION }} - working-directory: infra run: terraform init -backend-config="bucket=$STATE_BUCKET" -backend-config="region=$AWS_REGION" -backend-config="dynamodb_table=wharf-tf-locks" - run: | if [ "$ACTION" = "deploy" ]; then ./deploy.sh "$ENVIRONMENT"; else ./destroy.sh "$ENVIRONMENT"; fi
What I got wrong我犯过的错Three slips. My trust policy named the wrong repository, so every run said "not authorized to assume role". I typed a secret with a trailing space, and the state bucket was "not found". And a manual run started from a branch I did not mean, which the trust policy rightly refused.三个失误。我的信任策略写错了仓库名，所以每次运行都报“无权扮演该角色”。我输入密钥时末尾多了一个空格，于是状态存储桶“找不到”。还有一次手动运行是从我没打算用的分支发起的，信任策略正确地拒绝了它。

Now make it yours现在把它变成你的

What changed这一课之后Now a push from Mei Ling sets the conveyor belt moving: dev deploys itself with a day-pass token, and prod waits for Mr Ong's approval. The next problem is that the pieces have only been shown one at a time, and Mr Ong wants to see all three environments from one push, then all of it gone.现在 Mei Ling 一推送，传送带就动起来：dev 用当日通行证令牌自己部署，prod 则等 Ong 先生批准。下一个问题是这些零件只是一个个演示过，Ong 先生想看到一次推送带出三套环境，然后全部清空。

Common errors常见错误

• Error: Not authorized to perform sts:AssumeRoleWithWebIdentity The role trust policy does not match this repository or branch. Fix: Check the sub line: repo:OWNER/REPO:ref:refs/heads/main.
• Credentials could not be loaded id-token: write is missing from the workflow. Fix: Add it under permissions.
• Error: Backend configuration changed The pipeline ran init without the bucket settings. Fix: Pass the -backend-config values as in the workflow step.

• Error: Not authorized to perform sts:AssumeRoleWithWebIdentity 角色的信任策略和这个仓库或分支不匹配。 解决：检查 sub 这一行：repo:所有者/仓库:ref:refs/heads/main。
• Credentials could not be loaded 工作流里缺少 id-token: write。 解决：在 permissions 下加上它。
• Error: Backend configuration changed 流水线运行 init 时没有带桶的设置。 解决：像工作流那一步一样传入 -backend-config 的值。

Recap小结A push to main deploys dev with no password stored anywhere.
The pipeline borrows a short-lived identity through OIDC, limited to this repository.
A manual workflow plans first, then applies, and prod waits for a person.推送到 main 就部署 dev，任何地方都不存密码。
流水线通过 OIDC 借用短期身份，且只限这个仓库。

Plain words白话词汇Pipeline: steps a robot runs for you after every push. OIDC: a way for GitHub to prove who it is to the cloud, without a saved password. Secret: a value GitHub keeps hidden from logs.流水线（pipeline）：每次推送后由机器人替你执行的一系列步骤。OIDC：让 GitHub 向云证明身份、而不用保存密码的方式。密钥（secret）：GitHub 在日志里隐藏的值。

Takeaways要点回顾

• Put the project in git with a careful ignore file: state, packages, env files and keys stay out.
• A workflow is a text file in .github/workflows/: when this happens, run these steps.
• One workflow deploys dev on every push to main; another deploys or destroys a chosen environment by hand.
• Account-specific values live in repository secrets and variables, never in the files.
• OIDC replaces stored keys: GitHub proves who it is, and the cloud lets one named repository assume a role.
• Let the trust policy accept both the old and the newer subject pattern GitHub may send.
• GitHub environments can require approval before prod, and the reviewer should read the plan first.

• 把项目放进 git，并写好仔细的忽略文件：状态、包、环境文件和密钥都留在外面。
• 工作流是 .github/workflows/ 里的一个文本文件：发生这件事时，运行这些步骤。
• 一个工作流在每次推送到 main 时部署 dev；另一个手动部署或销毁所选环境。
• 因账号而异的值放在仓库的密钥和变量里，绝不放进文件。
• OIDC 取代了存放的密钥：GitHub 证明自己是谁，云只让一个指名的仓库扮演角色。
• 让信任策略同时接受 GitHub 可能发送的新旧两种主体写法。
• GitHub 环境可以要求上 prod 前先批准，审批人应当先读 plan。
