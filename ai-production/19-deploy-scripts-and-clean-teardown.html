Deploy scripts and teardown部署脚本与拆除

Wrap the steps in two scripts so deploying and destroying are one command each, and leave nothing running behind you · ~30 min · hands-on把步骤包进两个脚本，让部署和销毁各是一条命令，并且不在身后留下任何还在运行的东西 · 约 30 分钟 · 动手实践

The story故事

Mei Ling can now make three environments, but each one takes eight commands in the right order. Kumar wants one button for going up and one for coming down. Mr Ong has a harder question: "When you are finished with the test copy, can you prove nothing is still running and billing us?" She starts by writing the two scripts.

Mei Ling 现在能建出三个环境了，但每一个都要按正确顺序敲八条命令。Kumar 想要一个“上去”的按钮和一个“下来”的按钮。Ong 先生有个更难的问题：“测试那份用完之后，你能证明没有东西还在跑、还在向我们收费吗？”她先动手写这两个脚本。

Step 1 · A deploy script第 1 步 · 一个部署脚本

Learn先学

A deploy has an order, and the order matters. Build the backend package first, because the function resource reads the zip. The first line, set -euo pipefail, means stop at the first error. The pip flags build the package for Lambda's Linux, even if your laptop is a Mac. Build the front end. Select (or create) the workspace and print it. Apply (with -auto-approve, which skips the yes/no question Terraform normally asks). Then upload the site files and print the addresses. Put all of it in one script that takes the environment name. The script reads five names from outputs.tf (site_bucket, site_url, api_url, cdn_id and memory_bucket); each is a short output block that points at a resource from the last lesson (shown below, with the resource names from your main file), and Terraform prints it after apply. After the upload the script also tells the CDN to forget its old copies, so the stale-page problem from the live-twin lesson does not return. A second mode, plan, builds and shows the plan but changes nothing; this lesson does not use it, but it is there for checking changes.

部署有顺序，而且顺序很重要。先构建后端包，因为函数资源要读那个 zip。脚本第一行 set -euo pipefail 的意思是：遇到第一个错误就停下。pip 那几个参数是为 Lambda 的 Linux 环境构建包，哪怕你的笔记本是 Mac。再构建前端。选中（或新建）工作区并把它打印出来。apply（加上 -auto-approve，它会跳过 Terraform 平时问你的 yes/no 确认）。然后上传网站文件，打印出地址。把这些全放进一个接收环境名的脚本里。脚本读取的五个名字（site_bucket、site_url、api_url、cdn_id 和 memory_bucket）来自 outputs.tf：每个都是一个指向上一课某个资源的输出块（见下面，资源名以你的主文件为准），apply 之后 Terraform 会打印出来。上传之后脚本还会让 CDN 忘掉旧副本，这样上线的分身那一课里的旧页面问题就不会再回来。再加一个 plan 模式：构建并显示计划，但什么都不改；本课不用它，但它可以用来检查改动。

One more thing: a script written on your machine may not run on a friend's operating system. This one is for macOS and Linux; this lesson does not cover Windows, which needs its own PowerShell version.

还有一点：在你机器上写的脚本，未必能在朋友的操作系统上运行。这个是给 macOS 和 Linux 的；本课不讲 Windows，它需要自己的 PowerShell 版本。

# infra/outputs.tf output "site_bucket" { value = aws_s3_bucket.site.bucket } output "memory_bucket" { value = aws_s3_bucket.memory.bucket } output "site_url" { value = "https://${aws_cloudfront_distribution.site.domain_name}" } output "api_url" { value = aws_apigatewayv2_api.twin.api_endpoint } output "cdn_id" { value = aws_cloudfront_distribution.site.id }
#!/usr/bin/env bash # deploy.sh <dev|test|prod> [plan] set -euo pipefail ENV="${1:?usage: ./deploy.sh dev|test|prod [plan]}" MODE="${2:-apply}" ( cd backend && rm -rf package twin.zip \ && pip install --platform manylinux2014_x86_64 --target package --only-binary=:all: -r requirements.txt \ && cp *.py package/ && ( cd package && zip -qr ../twin.zip . ) ) ( cd frontend && npm ci && npm run build ) cd infra terraform workspace select -or-create "$ENV" echo "workspace: $(terraform workspace show)" if [ "$MODE" = "plan" ]; then terraform plan -var="environment=$ENV" exit 0 fi terraform apply -auto-approve -var="environment=$ENV" aws s3 sync ../frontend/dist "s3://$(terraform output -raw site_bucket)" --delete aws cloudfront create-invalidation --distribution-id "$(terraform output -raw cdn_id)" --paths "/*" > /dev/null echo "site: $(terraform output -raw site_url)" echo "api: $(terraform output -raw api_url)"

Step 2 · A destroy script that empties first第 2 步 · 先清空的销毁脚本

Learn先学

Going up is half the job. Terraform will not delete a bucket that still holds files, so destroy fails at the buckets. The destroy script empties them first, then lets Terraform remove everything else. (If your buckets keep old versions of files, those block deletion too. Setting force_destroy = true on the bucket resource in dev and test lets Terraform empty them itself.)

上去只是一半的活。Terraform 不会删除还装着文件的存储桶，所以 destroy 会在存储桶那里失败。销毁脚本先把它们清空，再让 Terraform 移除其余所有东西。（如果你的存储桶会保留文件的旧版本，这些旧版本也会挡住删除。在 dev 和 test 里给存储桶资源设上 force_destroy = true，Terraform 就会自己去清空。）

#!/usr/bin/env bash # destroy.sh <dev|test|prod> set -euo pipefail ENV="${1:?usage: ./destroy.sh dev|test|prod}" cd infra terraform workspace select "$ENV" echo "workspace: $(terraform workspace show)" for name in site_bucket memory_bucket; do aws s3 rm "s3://$(terraform output -raw "$name")" --recursive # a bucket with files will not delete done terraform destroy -auto-approve -var="environment=$ENV"
$ ./destroy.sh test workspace: test delete: s3://wharf-twin-test-site-111122223333/index.html ... Destroy complete! Resources: 8 destroyed.

Step 3 · Run it for dev, check the twin, then test第 3 步 · 先跑 dev，检查分身，再跑 test

Learn先学

Run the script for dev and open the printed address. Chat with the live twin: does it answer, and does it remember you? Only then run the same script for test. Each environment has its own workspace and its own names, so deploying test does not touch dev.

给 dev 运行脚本，然后打开打印出来的地址。和上线的分身聊几句：它能回答吗？它记得你吗？确认了再给 test 运行同一个脚本。每个环境都有自己的工作区和自己的名字，所以部署 test 不会碰 dev。

./deploy.sh dev # workspace: dev # ... # site: https://d1example.cloudfront.net # api: https://abc123.execute-api.ap-southeast-1.amazonaws.com # (open the site, chat with the twin, say hello twice) ./deploy.sh test # workspace: test the same steps, a different set of names

Step 4 · Delete cleanly, then prove it第 4 步 · 干净地删除，然后证明它

Learn先学

"It said destroy complete" is not proof. Check three ways. Terraform's own list of what it still manages should be empty. The cloud's command line should find no leftover buckets, functions, CDN distributions, gateways, roles or log groups with that environment's name. And the console should show nothing under the same name. A deploy you cannot undo is a risk; a teardown you cannot verify is nearly the same one.

“它说 destroy complete”不算证据。用三种方式检查。Terraform 自己管理的清单应该是空的。云的命令行应该找不到带那个环境名字的、遗留的存储桶、函数、CDN 分发、网关、角色或日志组。控制台里同样的名字下也应该什么都没有。无法撤销的部署是风险；无法验证的拆除，几乎是同一种风险。

./destroy.sh test cd infra && terraform workspace select test terraform state list # should print nothing aws s3 ls | grep wharf-twin-test # should print nothing aws lambda list-functions \ --query "Functions[?starts_with(FunctionName, 'wharf-twin-test')].FunctionName" # should be [] aws cloudfront list-distributions --query "DistributionList.Items[].Origins.Items[].DomainName" | grep wharf-twin-test # nothing aws apigatewayv2 get-apis --query "Items[?starts_with(Name, 'wharf-twin-test')].Name" # [] aws iam list-roles --query "Roles[?starts_with(RoleName, 'wharf-twin-test')].RoleName" # [] aws logs describe-log-groups --log-group-name-prefix /aws/lambda/wharf-twin-test --query "logGroups[].logGroupName" # [] # then search the console for "wharf-twin-test" and see nothing
$ terraform state list $ aws s3 ls | grep wharf-twin-test $ aws lambda list-functions --query "..." []

Step 5 · Cost: delete between sessions第 5 步 · 费用：每次用完就删

Learn先学

Because both directions are one command, you can afford to tear down a test environment every time you stop work, and rebuild it next session. That is the real saving. The budget alarm from the safe-account lesson is still there, but it is the last line of defence: it tells you after the money is spent. The first line is your own habit of running destroy.

因为两个方向都只要一条命令，你就能负担得起每次收工都拆掉测试环境，下次再重建。这才是真正的节省。账号安全那课设的预算警报还在，但它只是最后一道防线：钱花出去之后它才告诉你。第一道防线，是你自己运行 destroy 的习惯。

# end of every working session ./destroy.sh test # and dev too, unless you are still using it # prod stays up, because the public is using it
What I got wrong我犯过的错Three slips. Destroy failed because the buckets still held files, so the script now empties them first. The scripts I wrote for my own machine broke on a friend's operating system, so I keep a version for each. And I forgot to destroy test after I finished, and found out from the cost page.三个失误。destroy 失败了，因为存储桶里还有文件，所以现在脚本先把它们清空。我为自己机器写的脚本，在朋友的操作系统上跑不起来，所以我每种系统各留一个版本。我还忘了在用完后销毁 test，是在费用页面上才发现的。

Now make it yours现在把它变成你的

What changed这一课之后Now Mei Ling brings an environment up with one script and takes it down with another, and a check lists what is left, so Mr Ong can see that nothing it built is left (a check is only as good as its list, so add any new kind of resource to it). The next problem is that the state still sits on her laptop, so a robot cannot read it and two people deploying at once would both write in the book.现在 Mei Ling 用一个脚本上线、另一个脚本下线，再用检查列出剩下的东西，Ong 先生能看到它建的东西一样不剩（检查只和它的清单一样可靠，所以新增了资源类型，就要把它加进清单）。下一个问题是状态仍然放在她的笔记本上，机器人读不到，两个人同时部署也会同时往簿子上写。

Common errors常见错误

• bash: ./deploy.sh: Permission denied The script file is not marked as runnable. Fix: Run chmod +x deploy.sh destroy.sh.
• ./deploy.sh: line 4: 1: usage: ./deploy.sh dev|test|prod [plan] You ran it without an environment name. Fix: Add one: ./deploy.sh dev.
• BucketNotEmpty A bucket still holds files, so it cannot be deleted. Fix: Keep the aws s3 rm --recursive step before terraform destroy.

• bash: ./deploy.sh: Permission denied 脚本文件没有被标记为可执行。 解决：运行 chmod +x deploy.sh destroy.sh。
• ./deploy.sh: line 4: 1: usage: ./deploy.sh dev|test|prod [plan] 运行时没有给环境名。 解决：加上环境名：./deploy.sh dev。
• BucketNotEmpty 桶里还有文件，所以无法删除。 解决：保留 terraform destroy 之前的 aws s3 rm --recursive 步骤。

Takeaways要点回顾

• A deploy has an order: build the backend, build the front end, pick the workspace, apply, upload the site, print the addresses.
• Print the current workspace every time, before anything changes.
• A destroy script empties the buckets first, because a bucket with files will not delete.
• Keep a script version for each operating system your team uses.
• Prove a teardown: the state list, the command line and the console should all show nothing.
• Delete test environments between sessions; the budget alarm is the last line of defence, not the first.
• A deploy you cannot undo is a risk, so script both directions.

• 部署有顺序：构建后端、构建前端、选工作区、apply、上传网站、打印地址。
• 每次在任何东西改变之前，先打印当前的工作区。
• 销毁脚本先清空存储桶，因为还有文件的存储桶删不掉。
• 团队用到哪种操作系统，就保留哪种系统的脚本版本。
• 要证明拆除干净：状态清单、命令行和控制台都应该什么都没有。
• 测试环境每次用完就删；预算警报是最后一道防线，不是第一道。
• 无法撤销的部署是风险，所以两个方向都要写成脚本。
