Live digital twin上线的数字分身

Finish the digital twin: personality, memory in a bucket, backend in a function and front end behind a CDN, all on a public address · ~50 min · project把数字分身做完：性格、放在存储桶里的记忆、函数里的后端、CDN 后面的前端，全都放到一个公开地址上 · 约 50 分钟 · 项目

Step 1 · Local first, then list the pieces第 1 步 · 先本地，再列零件

Learn先学

A digital twin here is a chatbot that answers as one person: a persona prompt, plus a memory of each conversation saved as a file. The backend is a small Python API; the front end is a Next.js page that npm run build exports as plain files into out. Get chat, persona and file memory (USE_BUCKET off, so memory is a local file) working on your laptop before touching the cloud. A local bug is far cheaper to find. Then write down the five cloud pieces:

这里的数字分身是一个替某个人回答的聊天机器人：一段人设提示词，加上把每次对话存成文件的记忆。后端是一个小 Python API；前端是一个 Next.js 页面，npm run build 会把它导出成普通文件放进 out。先在笔记本上跑通聊天、人设和文件记忆（USE_BUCKET 关闭，记忆就是本地文件），再碰云。本地的 bug 便宜得多。然后写下五个云零件：

1. memory bucket wharf-twin-memory 2. function wharf-twin (the backend as a zip, USE_BUCKET=true) 3. API gateway → function (the public front door) 4. site bucket wharf-twin-site 5. CDN → site bucket (caches files near visitors; on AWS it is called CloudFront)

Step 2 · Wire back to front, testing each piece第 2 步 · 从后往前连，逐块测试

Learn先学

Build memory bucket, function, gateway, site, then CDN. Test each piece alone before adding the next, so a break is always in the newest piece. The function and gateway need only one curl, with no page yet.

依次建记忆桶、函数、网关、网站、CDN。每块先单独测，再接下一块，出问题就一定在最新那块。函数和网关只要一条 curl 就能测，还不需要页面。

API=https://abc123.execute-api.ap-southeast-1.amazonaws.com # your gateway address curl -s -X POST "$API/api/chat" \ -H "Content-Type: application/json" \ -d '{"session_id": "test-1", "message": "Hi, what do you work on?"}' # expect: {"reply": "..."} and a new object "test-1.json" in the memory bucket

Step 3 · Publish the front end and prove memory第 3 步 · 发布前端并验证记忆

Learn先学

Read the API address from a build-time variable (NEXT_PUBLIC_ names reach the browser), build, upload with s3 sync (--delete also removes files from the bucket that are no longer in out), then invalidate the CDN cache (the cloudfront line), or it serves the old page for minutes. Finally force a fresh start of the function (upload the same zip again, which throws away everything it held in memory) and ask your name again: it must still be there, because memory lives in the bucket.

构建时从变量读 API 地址（NEXT_PUBLIC_ 开头的名字才会进浏览器），构建，用 s3 sync 上传（--delete 会把存储桶里已不在 out 中的文件也删掉），然后让 CDN 缓存失效（cloudfront 那一行），否则它会把旧页面发好几分钟。最后让函数重新启动（把同一个 zip 再上传一次，它内存里的东西就全丢了）再问名字：必须还在，因为记忆在存储桶里。

NEXT_PUBLIC_API_BASE=$API npm run build # static export → "out" aws s3 sync out/ s3://wharf-twin-site --delete aws cloudfront create-invalidation --distribution-id YOUR_DISTRIBUTION_ID --paths "/*" # the id is on the CDN's page in the console, or: aws cloudfront list-distributions

Now make it yours现在把它变成你的

Common errors常见错误

• {"message":"Internal Server Error"} The function crashed. Fix: Run aws logs tail on its log group and fix the first exception.
• The page still shows the old version Fix: Run the create-invalidation line and wait a minute.
• Failed to fetch NEXT_PUBLIC_API_BASE was empty at build time. Fix: Set it on the same line as npm run build and rebuild.

• {"message":"Internal Server Error"} 函数崩溃了。 解决：对它的日志组运行 aws logs tail，修复第一条异常。
• The page still shows the old version 解决：运行 create-invalidation 那一行，等一分钟。
• Failed to fetch 构建时 NEXT_PUBLIC_API_BASE 是空的。 解决：在 npm run build 同一行设置它，再重新构建。

Takeaways要点回顾

• Get it working locally before touching the cloud.
• Five pieces: memory bucket, function, gateway, site bucket, CDN.
• Wire back to front and test each piece before the next.
• Read the API address from a build-time variable; invalidate the CDN after every upload.
• Restart the function to prove memory lives in the bucket.

• 先在本地跑通，再碰云。
• 五个零件：记忆桶、函数、网关、网站桶、CDN。
• 从后往前连，每块先测再接下一块。
• 构建时从变量读 API 地址；每次上传后让 CDN 失效。
• 重启函数，证明记忆在存储桶里。
