The story故事

The twin has a voice and facts, and its memory code can use a bucket. Now Mei Ling puts it all on one public address, so that Auntie Siti can open it on her phone at the canteen and chat. Mr Ong wants one thing: when the twin is idle, the bill should be close to nothing. Kumar wants it done in an order that never leaves a half-working mess.

分身已经有了声音和事实，它的记忆代码也能用存储桶了。现在 Mei Ling 要把所有东西放到一个公开地址上，让 Siti 阿姨在食堂里用手机就能打开聊天。Ong 主管只想要一件事：分身闲着的时候，账单应该接近零。Kumar 希望按一个不会留下半成品烂摊子的顺序来做。

Step 1 · Local first第 1 步 · 先在本地做好

Learn先学

Do not touch the cloud until it all works on your laptop: the chat, the persona, and the file memory (with USE_BUCKET off). If it is broken locally, the cloud only adds more places to look. Test the three things that matter.

在笔记本上全部跑通之前，不要碰云：聊天、人设，以及文件记忆（USE_BUCKET 关闭）。如果本地就是坏的，云只会多出更多要查的地方。测试这三件要紧的事。

Local checklist (server and page both running on your laptop) [ ] it answers in her voice [ ] it admits what it does not know [ ] I say my name, ask again in the next message, and it remembers

Step 2 · List the cloud pieces第 2 步 · 列出云上的零件

Learn先学

Write down every piece before you create any. It is five small, boring things: a bucket for memory, a function with the packaged backend, an API gateway in front of it (the public front door that hands each web request to the function), a bucket for the static site, and a CDN (a worldwide copy-and-serve layer that caches your files near visitors) in front of that. This is a practice twin on its own addresses, not the one Auntie Siti already uses; later lessons repeat it with account-id bucket names. Each one is easy. The work is in how they connect.

在创建任何东西之前，先把每一块写下来。一共是五个小而无聊的零件：一个存放记忆的存储桶、一个装着打包后端的函数、它前面的 API 网关、一个存放静态网站的存储桶，以及它前面的 CDN。API 网关是前门，把每个网络请求交给函数；CDN 是把文件缓存到离访客更近处的分发层。这是一个独立地址上的练习分身，不是 Siti 阿姨已经在用的那个；后面的课会用带账号 id 的存储桶名字重做一遍。每一个都很简单，难的是它们怎么连起来。

1. memory bucket wharf-twin-memory 2. function wharf-twin (zip from the last lesson, MEMORY_BUCKET + USE_BUCKET=true) 3. API gateway → function 4. site bucket wharf-twin-site 5. CDN → site bucket

Step 3 · Wire them in order, testing as you go第 3 步 · 按顺序连接，边连边测

Learn先学

Go from the back to the front: memory bucket, then the function, then the gateway, then the site, then the CDN. After each piece, test it by itself before adding the next. The function and gateway can be tested with one command, before any page exists. That way, when something breaks, you know it is the newest piece. Set API to your gateway address first.

从后往前做：先存储桶，再函数，再网关，再网站，最后 CDN。每做完一块，先单独测它，再加下一块。函数和网关可以在页面存在之前，用一条命令来测。这样出了问题，你就知道是最新加的那一块。先把 API 设成你的网关地址。

API=https://abc123.execute-api.ap-southeast-1.amazonaws.com # your gateway address curl -s -X POST "$API/api/chat" \ -H "Content-Type: application/json" \ -d '{"session_id": "test-1", "message": "Hi, what do you work on?"}' # expect: {"reply": "..."} and a new object "test-1.json" in the memory bucket

Step 4 · Point the front end at the API, rebuild, upload第 4 步 · 让前端指向 API，重新构建，上传

Learn先学

Do not hard-code the API address in the page. Read it from an environment variable at build time (the front end is a Next.js app; names starting with NEXT_PUBLIC_ reach the browser, and the static export build writes the finished files into the out/ folder), so each environment gets its own. Rebuild the static files, upload them to the site bucket, and then tell the CDN to forget its old copies. If you skip that last step, it keeps serving the old page for minutes.

不要把 API 地址写死在页面里。在构建时从环境变量里读（前端是一个 Next.js 应用；以 NEXT_PUBLIC_ 开头的名字才会进到浏览器，静态导出构建会把成品文件写进 out/ 文件夹），这样每个环境都有各自的地址。重新构建静态文件，上传到网站存储桶，然后让 CDN 忘掉旧副本。如果跳过最后一步，它会继续把旧页面发给人好几分钟。

# in the page: fetch(`${process.env.NEXT_PUBLIC_API_BASE}/api/chat`, ...) NEXT_PUBLIC_API_BASE=$API npm run build # static export → "out" aws s3 sync out/ s3://wharf-twin-site --delete aws cloudfront create-invalidation --distribution-id YOUR_DISTRIBUTION_ID --paths "/*"

Step 5 · Test the whole thing, including a restart第 5 步 · 测试全部，包括重启

Learn先学

Open the CDN address on your phone. Send a first message and say your name. Send a second message that tests memory. Then force a fresh copy of the function (upload the zip again, or wait until it has been idle: the cloud shuts an unused function down, and the next request starts a fresh copy with nothing in its own memory) and ask once more. The name must still be there, because it lives in the bucket and not in the function.

在手机上打开 CDN 地址。发第一条消息，说出你的名字。再发第二条消息来测试记忆。然后强制换一个新的函数副本（重新上传 zip，或者等它闲置一阵：云会关掉没人用的函数，下一次请求会启动一个自身内存里什么都没有的新副本），再问一次。名字必须还在，因为它存在存储桶里，而不是函数里。

1. "Hi, I am Siti." → twin greets her 2. "What is my name?" → Siti 3. (upload the function zip again, so a fresh copy starts) 4. "Do you still remember my name?" → Siti (memory is in the bucket)

Step 6 · Cost check and a clean-up plan第 6 步 · 成本检查和清理计划

Learn先学

Open the bill page a day later. A small twin should cost cents, mostly the model calls. Check the budget alarms are still set, set a short retention on the logs, and write the clean-up plan now: which five things to delete, in which order (CDN, site bucket, gateway, function, memory bucket). A plan written while it works is much better than one written while you are annoyed.

一天之后打开账单页。一个小分身应该只花几分钱，主要是模型调用。检查预算警报还在，给日志设置较短的保留期，并且现在就写好清理计划：要删哪五样、按什么顺序（CDN、网站存储桶、网关、函数、记忆存储桶）。在一切正常时写的计划，比在你恼火时写的好得多。

What I got wrong我犯过的错Three slips. The CDN served the old front end for minutes, until I invalidated its cache after each upload. I hard-coded the API address instead of using a variable at build time. And I did all the console clicking from memory, then could not repeat it later. A later topic fixes that.三个失误。CDN 把旧前端发了好几分钟，直到我每次上传后都让它的缓存失效。我把 API 地址写死了，而不是在构建时用变量。我还全凭记忆在控制台里点来点去，之后就没法重复了。后面的一个主题会解决这件事。

Takeaways要点回顾

• Get it all working locally before touching the cloud.
• Five small pieces: memory bucket, function, gateway, site bucket, CDN.
• Wire back to front and test each piece before adding the next.
• Read the API address from a variable at build time, never hard-code it.
• Invalidate the CDN cache after every upload.
• Test memory across a fresh copy of the function.
• The pieces are boring. The work is wiring them in a safe order, and having a clean-up plan.

• 先在本地全部跑通，再碰云。
• 五个小零件：记忆存储桶、函数、网关、网站存储桶、CDN。
• 从后往前连，每加一块之前先测上一块。
• 构建时从变量读 API 地址，绝不写死。
• 每次上传后都要让 CDN 缓存失效。
• 用一个全新的函数副本来测试记忆。
• 零件都很无聊，难的是按安全的顺序把它们连起来，并且备好清理计划。
