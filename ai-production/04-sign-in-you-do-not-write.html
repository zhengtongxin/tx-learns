Step 1 · Who does what第 1 步 · 谁来做什么

Learn先学

A hosted sign-in service is a company that handles logins for you. You create an app in its dashboard and pick the sign-in methods: email, Google, GitHub. It stores the passwords, sends reset emails and shows the sign-in screens. Your product only needs to know one thing: who is this request from? Think of the gate pass office: someone else prints the passes, you only check them.

托管登录服务是替你处理登录的公司。你在它的后台创建一个应用，选好登录方式：邮箱、Google、GitHub。密码由它保存，重置邮件由它发送，登录界面由它展示。你的产品只需要知道一件事：这个请求是谁发的？就像通行证办公室：证由别人印，你只负责查验。

Step 2 · Two keys, and where they live第 2 步 · 两把密钥，各放在哪

Learn先学

The service gives you two keys. The public (publishable) key identifies your app and is safe in the browser. The secret key can act as your server, so it must stay on the server. Put both in a local env file, and add that file to .gitignore first so it can never be committed. In Next.js, a name that starts with NEXT_PUBLIC_ is sent to the browser. Anything else is not.

服务会给你两把密钥。公开（publishable）密钥用来标识你的应用，放在浏览器里是安全的。秘密密钥能代表你的服务器行事，必须留在服务器上。两者都放进本地的环境文件，并且要先把这个文件加进 .gitignore，保证它永远不会被提交。在 Next.js 里，以 NEXT_PUBLIC_ 开头的名字会被发到浏览器，其他的不会。

# .gitignore (do this first) .env.local # .env.local NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_... CLERK_SECRET_KEY=sk_test_... CLERK_JWKS_URL=https://... # shown in the dashboard

Step 3 · Wrap the app and show the right thing第 3 步 · 把应用包起来，并显示对的内容

Learn先学

Install the service's React package and wrap the whole app in its provider: a component that quietly shares "who is signed in" with every page. Then show different things to different visitors. Signed-out people get a sign-in button that opens a modal (a pop-up). Signed-in people get the product and a user button (their avatar and sign-out).

安装服务的 React 包，把整个应用包进它的提供者（provider）：一个悄悄把“谁已登录”共享给每个页面的组件。然后给不同的访问者显示不同内容：没登录的人看到一个会弹出模态窗（modal）的登录按钮，已登录的人看到产品和一个用户按钮（头像与退出登录）。

npm install @clerk/nextjs // pages/_app.tsx import type { AppProps } from "next/app"; import { ClerkProvider } from "@clerk/nextjs"; export default function App({ Component, pageProps }: AppProps) { return ( <ClerkProvider {...pageProps}> <Component {...pageProps} /> </ClerkProvider> ); } // pages/index.tsx (inside the page) <SignedOut><SignInButton mode="modal" /></SignedOut> <SignedIn><UserButton /> ...the product...</SignedIn>

All of them come from @clerk/nextjs (SignedIn, SignedOut, SignInButton, UserButton); import the ones you use at the top of the page.

这几个组件都来自 @clerk/nextjs（SignedIn、SignedOut、SignInButton、UserButton），用到哪个就在页面顶部导入哪个。

Step 4 · Carry the pass to the API第 4 步 · 把通行证带给 API

Learn先学

Once signed in, the browser holds a session token, a signed text called a JWT. It says "this is user X". The page sends it with every API request in an Authorization header. Tokens are short-lived, about a minute, so a stored old one fails like a random glitch. Ask for a fresh token right before each request.

登录后，浏览器里有一个会话令牌（session token），是一段带签名的文本，叫 JWT，内容是“这是用户 X”。页面在每次 API 请求里，用 Authorization 头把它带上。令牌有效期很短，大约一分钟，所以存着的旧令牌会像随机故障一样失败。每次请求前都要取一个新的。

import { useAuth } from "@clerk/nextjs"; // inside your page component const { getToken } = useAuth(); async function ask() { const token = await getToken(); // fresh, every time const res = await fetch("/api", { headers: { Authorization: "Bearer " + token }, }); return res.json(); }

Step 5 · Check the pass on the server第 5 步 · 在服务器上验通行证

Learn先学

Anyone can send an Authorization header, so the API must check it. The service publishes its public keys at a web address called JWKS. These are a different thing from the publishable key in step 2: they only check signatures, and they do not identify your app. A token is stamped with a signature that only the service could make, and the public keys let your server verify the stamp without phoning the service every time. If it checks out, the user id is inside, under the name sub (short for "subject"). A bad token gets a 401, the web's code for "unauthorized", the same way a missing page gets a 404. The browser-side check from step 3 is only for looks.

任何人都能发 Authorization 头，所以 API 必须验证。服务会在一个叫 JWKS 的网址公开它的公钥。这些公钥和第 2 步的公开密钥不是一回事：它们只用来验签名，不用来标识你的应用。令牌上盖着只有服务才能盖出的签名，有了公钥，你的服务器就能验这个章，不用每次都打电话问服务。验过了，用户 id 就在令牌里，字段名叫 sub（subject 的缩写，意思是“主体”）。令牌不合格就会得到 401，这是网页里“未授权”的状态码，就像找不到页面时的 404。第 3 步里浏览器上的检查只是为了好看。

import os from fastapi import Depends, FastAPI from fastapi_clerk_auth import ClerkConfig, ClerkHTTPBearer, HTTPAuthorizationCredentials app = FastAPI() guard = ClerkHTTPBearer(ClerkConfig(jwks_url=os.environ["CLERK_JWKS_URL"])) @app.get("/api") def hello(creds: HTTPAuthorizationCredentials = Depends(guard)): user_id = creds.decoded["sub"] return {"message": "Welcome aboard, " + user_id} # add fastapi-clerk-auth to requirements.txt

Step 6 · Deploy it with the same keys第 6 步 · 用同样的密钥部署

Learn先学

Your .env.local file stays on your laptop, so the host has never seen it. Add the same variables in the host's settings, then redeploy. Settings are read at deploy time, so adding them without redeploying changes nothing.

你的 .env.local 只留在笔记本上，托管平台从没见过它。在平台的设置里加上同样的变量，然后重新部署。设置是在部署时读取的，只加不重新部署等于没改。

vercel env add NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY vercel env add CLERK_SECRET_KEY vercel env add CLERK_JWKS_URL vercel --prod
What I got wrong我犯过的错I kept getting "unauthorized". The key in the host settings was not the same as my local one. Then tokens, which last about a minute, made a stale one look like a random failure, so now I fetch a fresh one per request. And I almost committed the secret key: put the env file in .gitignore before you create it.我一直收到“unauthorized”。平台设置里的密钥和本地的不一样。后来又发现令牌只有大约一分钟的寿命，过期的令牌看上去像随机故障，所以现在我每次请求都取新的。我还差点把秘密密钥提交了：要在创建环境文件之前就把它加进 .gitignore。

Now make it yours现在把它变成你的

What changed这一课之后Now only signed-in visitors reach the model, and the API checks the stamp every time, the way Sergeant Lee does at the gate. The next problem is that signed in does not mean paid: a free account still rides free on Mr Ong's model bill.现在只有登录的访客才能用到模型，接口每次都检查印章，就像 Lee 警官在闸口那样。下一个问题是登录不等于付费：免费账号仍然在白用 Ong 先生的模型额度。

Takeaways要点回顾

• Do not write password handling. Let a hosted sign-in service do it.
• The public key may go to the browser. The secret key stays on the server and out of git.
• The browser holds a short-lived signed token (a JWT) and sends it with each API request.
• Fetch a fresh token per request. A stale one fails like a random glitch.
• The server verifies the signature with the service's public keys (JWKS) and reads the user id.
• A check in the browser is only for looks. Verify on the server for every request.
• The host needs the same environment variables as your laptop, then a redeploy.

• 不要自己处理密码，交给托管的登录服务。
• 公开密钥可以给浏览器，秘密密钥留在服务器上，也不要进 git。
• 浏览器持有一个短寿命的签名令牌（JWT），每次 API 请求都带上它。
• 每次请求取新令牌，旧的会像随机故障一样失败。
• 服务器用服务的公钥（JWKS）验签，并读出用户 id。
• 浏览器里的检查只是为了好看，每个请求都要在服务器上验证。
• 平台需要和笔记本一样的环境变量，然后重新部署。
