State, workspaces and three environments状态、工作区与三套环境

Run development, test and production as three copies of the same stack from one set of files, without copy-pasting configs · ~35 min · hands-on用同一套文件把开发、测试和生产跑成同一个架构的三份副本，不用复制粘贴配置 · 约 35 分钟 · 动手实践

上回，产品已经写成了文件。今天 Ong 先生想要开发、测试和生产三套环境，而 Mei Ling 的第一个主意，把文件夹复制三份，到周五就会各走各的。我们的办法是用一份配置、一个变量，每套环境一个带独立状态的工作区。

Step 1 · One folder, and a variable called environment第 1 步 · 一个文件夹，和一个叫 environment 的变量

Learn先学

Keep one folder of config: a provider file, a variables file, a main file with the resources (memory bucket, site bucket, function role, function, gateway and CDN) and an outputs file (the code below leaves out the gateway, CDN and outputs blocks to keep it short; the next lesson reads their outputs). Then add a variable called environment and feed it into every name. That is what stops dev and prod from colliding: they are the same files with a different word in the names.

只留一个配置文件夹：一个提供者文件、一个变量文件、一个放资源的主文件（记忆存储桶、网站存储桶、函数角色、函数、网关和 CDN），再加一个输出文件（下面的代码为了简短，省略了网关、CDN 和输出的部分；下一课的部署脚本会读取它们的输出）。然后添加一个叫 environment 的变量，把它放进每一个名字里。这样 dev 和 prod 才不会撞车：它们是同样的文件，只是名字里的那个词不同。

infra/ (next to the backend/ and frontend/ folders) providers.tf which cloud, which region variables.tf the knobs (below) main.tf memory bucket, site bucket, function role, function, gateway, CDN outputs.tf the addresses we want to print
# variables.tf variable "environment" { type = string description = "dev, test or prod" validation { condition = contains(["dev", "test", "prod"], var.environment) error_message = "environment must be dev, test or prod." } }

Step 2 · Names that never clash第 2 步 · 永远不会撞车的名字

Learn先学

A bucket name must be unique across everybody's accounts, not only yours. So build each name from three parts: the project, the environment and your account id. A local value is a named shortcut inside the config, so the pattern is written once. The data block asks the cloud for a fact (here, your account id) instead of creating something.

存储桶的名字必须在所有人的账号里都唯一，而不只是在你的账号里。所以每个名字由三部分拼成：项目、环境和你的账号 id。local 值是配置里一个起了名的快捷方式，这样命名规则只要写一次。data 块是向云查询一个事实（这里是你的账号 id），而不是创建东西。

# main.tf data "aws_caller_identity" "me" {} locals { prefix = "wharf-twin-${var.environment}" suffix = data.aws_caller_identity.me.account_id } resource "aws_s3_bucket" "memory" { bucket = "${local.prefix}-memory-${local.suffix}" } resource "aws_s3_bucket" "site" { bucket = "${local.prefix}-site-${local.suffix}" }

Step 3 · State, and one state per workspace第 3 步 · 状态，以及每个工作区一份状态

Learn先学

The state is a file where Terraform writes down which real resources match which lines of your config. On every plan it compares three things: your files, the state, and what really exists. A workspace is a named copy of the state. You start in one called default. Make one per environment, and each keeps its own state file.

状态是一个文件，Terraform 在里面记下哪些真实资源对应你配置里的哪几行。每次 plan 它都会比较三样东西：你的文件、状态，以及实际存在的东西。工作区是状态的一份有名字的副本。你一开始在一个叫 default 的工作区里。每个环境建一个，各自保管自己的状态文件。

With local state, the files sit under terraform.tfstate.d/, one folder per workspace.

用本地状态时，这些文件放在 terraform.tfstate.d/ 下面，每个工作区一个文件夹。

terraform init terraform workspace new dev terraform workspace new test terraform workspace new prod terraform workspace list # default # dev # test # * prod the star marks the one you are in ls terraform.tfstate.d/ # dev prod test (each holds its own state file)

Step 4 · Switch, check, apply第 4 步 · 切换、检查、再 apply

Learn先学

To deploy an environment you do two things that must agree: select its workspace, and pass its name as the variable. If they disagree, the plan compares dev-named files with prod's state, and it wants to replace prod's things with dev's. So always print the current workspace first, and read the plan before you apply.

部署一个环境要做两件必须一致的事：选中它的工作区，并把它的名字作为变量传进去。如果两者不一致，plan 会拿 dev 名字的文件去和 prod 的状态比较，结果是想把 prod 的东西换成 dev 的。所以永远先打印当前工作区，apply 之前先读 plan。

terraform workspace select -or-create dev terraform workspace show # always print it before you apply terraform plan -var="environment=dev" terraform apply -var="environment=dev"
dev Plan: 8 to add, 0 to change, 0 to destroy. Apply complete! Resources: 8 added, 0 changed, 0 destroyed.

Step 5 · Per-environment settings第 5 步 · 每个环境自己的设置

Learn先学

Environments should share a shape but not every setting. Dev can use a small, cheap model and prod a bigger one. Put the choice in a map (a lookup table) keyed by environment name, and pick from it with one line. The function below also needs its role, so that is included. The role has two parts: assume_role_policy says who may wear it (only the function service, lambda.amazonaws.com), and the separate aws_iam_role_policy says what it may do: call the model, read and write its own memory bucket, and write logs. Without that second part the function cannot call the model.

各环境应该结构一样，但不必每项设置都一样。dev 可以用小而便宜的模型，prod 用更大的。把这个选择放进一张以环境名为键的映射表（map，查找表）里，再用一行去取。下面的函数还需要它的角色，所以也一起写出来。角色分两部分：assume_role_policy 说谁可以穿上它（只有函数服务 lambda.amazonaws.com），另一个 aws_iam_role_policy 说它能做什么：调用模型、读写自己的记忆存储桶、写日志。没有这第二部分，函数就调不了模型。

Optional: a custom domain through DNS is one more resource per environment, with the environment name in the address.

可选项：用 DNS 配自定义域名，每个环境再多一个资源，地址里带上环境名。

variable "model_ids" { type = map(string) default = { dev = "apac.amazon.nova-micro-v1:0" test = "apac.amazon.nova-lite-v1:0" prod = "apac.amazon.nova-pro-v1:0" } } locals { model_id = var.model_ids[var.environment] }
resource "aws_iam_role" "twin" { name = "${local.prefix}-twin-role" assume_role_policy = jsonencode({ Version = "2012-10-17" Statement = [{ Effect = "Allow", Action = "sts:AssumeRole", Principal = { Service = "lambda.amazonaws.com" } }] }) } resource "aws_iam_role_policy" "twin" { name = "${local.prefix}-twin-access" role = aws_iam_role.twin.id policy = jsonencode({ Version = "2012-10-17" Statement = [ { Effect = "Allow", Action = ["bedrock:InvokeModel"], Resource = "*" }, { Effect = "Allow", Action = ["s3:GetObject", "s3:PutObject"], Resource = "${aws_s3_bucket.memory.arn}/*" }, { Effect = "Allow", Action = ["logs:CreateLogGroup", "logs:CreateLogStream", "logs:PutLogEvents"], Resource = "*" }] }) } resource "aws_lambda_function" "twin" { function_name = "${local.prefix}-twin" role = aws_iam_role.twin.arn handler = "server.handler" runtime = "python3.12" filename = "${path.module}/../backend/twin.zip" source_code_hash = filebase64sha256("${path.module}/../backend/twin.zip") timeout = 30 memory_size = 512 environment { variables = { MODEL_ID = local.model_id MEMORY_BUCKET = aws_s3_bucket.memory.bucket } } }

Step 6 · Never hand-edit what the config owns第 6 步 · 配置管着的东西，别手工去改

Learn先学

If you change a resource by hand in the console, the real thing no longer matches the files. The next plan notices and proposes to undo your hand edit. The healthy habit: change the file, plan, apply. And when nothing has changed, running plan twice in a row should say "No changes". That is how you know the files and reality agree.

如果你在控制台里手工改了某个资源，真实的东西就和文件对不上了。下一次 plan 会发现，并提议撤销你的手工改动。健康的习惯是：改文件、plan、apply。而什么都没改的时候，连续跑两次 plan 应该都说“No changes”。这样你就知道文件和现实是一致的。

$ terraform plan -var="environment=dev" # aws_lambda_function.twin will be updated in-place ~ resource "aws_lambda_function" "twin" { ~ memory_size = 1024 -> 512 # someone set 1024 in the console; the file says 512 } Plan: 0 to add, 1 to change, 0 to destroy.
What I got wrong我犯过的错Three slips. I once applied in the wrong workspace; now the deploy script prints the current workspace every time. My bucket names clashed, because they must be globally unique, so I added the account id. And I edited a resource by hand in the console, so the next plan wanted to undo it.三个失误。我有一次在错误的工作区里 apply 了；现在部署脚本每次都会打印当前的工作区。我的存储桶名字撞了，因为它们必须全局唯一，所以我加上了账号 id。我还在控制台里手工改了一个资源，结果下一次 plan 想把它改回去。

Common errors常见错误

• Error: Invalid value for variable The environment is not one of dev, test or prod. Fix: Pass -var="environment=dev" exactly.
• Error: Workspace "test" doesn't exist The workspace was never created. Fix: Run terraform workspace new test, or use select -or-create.
• Error: reading ZIP file twin.zip is not built yet. Fix: Build the zip first, then plan again.

• Error: Invalid value for variable 环境不是 dev、test、prod 之一。 解决：准确传入 -var="environment=dev"。
• Error: Workspace "test" doesn't exist 这个工作区还没有创建。 解决：运行 terraform workspace new test，或使用 select -or-create。
• Error: reading ZIP file twin.zip 还没有构建。 解决：先构建压缩包，再重新 plan。

Takeaways要点回顾

• One folder of config drives all environments: same code, three states.
• A variable called environment feeds every name, so dev, test and prod never collide.
• Bucket names are global, so add the account id.
• State records which real resources match the config, and each workspace has its own.
• Select the workspace and pass the same environment name, and print the workspace before you apply.
• Use a map for per-environment settings, such as a smaller model in dev and a bigger one in prod.
• Never hand-edit what the config owns: the next plan will try to undo it.

• 一个配置文件夹驱动所有环境：同样的代码，三份状态。
• 一个叫 environment 的变量进入每一个名字，所以 dev、test、prod 永远不会撞车。
• 存储桶名字是全局的，所以要加上账号 id。
• 状态记录哪些真实资源对应配置，每个工作区有自己的一份。
• 选好工作区，传同样的环境名，apply 之前先打印工作区。
• 每个环境不同的设置用映射表，比如 dev 用小模型、prod 用大模型。
• 配置管着的东西别手工改：下一次 plan 会想把它改回去。
